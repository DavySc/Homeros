# Review of PR 42: the frame after a key recomputes only what the edit can change

Reviewed head 906f14e on base 5c034fb (main at the time of review), 2026-11-18.
Repro files: `reviews/pr-42-repro/`.

## Verdict

**Changes requested, one small fix and one decision.** The idea holds: across
1.42 million probed frames the widening to whole matches never left a stale
colour behind a predicate, a multi-line construct or an injection. The
speedup is as claimed. But two cases show colours that differ from a full
recompute and from Neovim:

1. **Blocking, one line.** After two edits before one frame, the second at
   byte 0 of the file, byte 0 keeps no colour until the next parse.
2. **To fix or to record.** The partial recompute starts its query in the
   middle of the window, and tree-sitter's order between two captures of one
   priority depends on where the query starts. In C with a syntax error a `*`
   can show `@operator` where the full recompute and Neovim show
   `@variable.parameter` (or the reverse) until the next parse.

## The differential probe

`reviews/pr-42-repro/diff.c` includes `syntax.c` to reach the cache. It
applies random steps to a file (typing at a cursor, tokens that open and
close multi-line constructs, deletions of up to 400 bytes, several edits
before one frame, edits outside the window, scrolls, parses stopped after 1
to 5 asks or run whole) and after every step draws the frame twice from the
same state: once as is, and once with the cache emptied, which is what main
did in every frame after a key. The two must agree byte for byte. The trees
are the same on both sides, so this isolates exactly what the PR changes.

Files: DESIGN.md, README.md, Emacs 31.1's coding.c, Neovim's lsp.lua, and
three generated files (`gen.py`: far.lua, far.c, far.md) dense in the
constructs where a predicate on one node decides another node's colour
(`s:find("%d+")`, `string.match(x, "%a+")` over several lines, `__label__`,
`#undef`), inside fenced blocks, block quotes and `ffi.cdef` injections.

**The probe can fail (measured, 1 run each of 2,000 to 3,000 frames per
file).** With each of the PR's six plants applied it reports mismatches: no
widening (84 frames), widening to the edited capture only (45, on far.lua and
far.c only: the real files never showed it, as the PR found), cache not
shifted (1,872), no padding before (317) or after (235) the edit, a new tree
keeps the cache (382).

**Result at the PR head (measured):**

|---|---|---|---|---|---|
| coding.c | 40 | 80,000 | 47,394 | 0 | 0 |

Window heights 12, 20, 50, 120 and 400 lines, so windows both smaller and

## Finding 1 (blocking): an edit at byte 0 does not lower the seeds

`syntax_edit`, when seeds from an earlier edit are pending:

```c
if (p && p - 1 < s->sa) s->sa = p - 1;
```

With `p == 0` the guard skips the line, so `sa` stays above 0, the byte the
edit wrote is zeroed in the cache by the `memset`, and nothing recomputes it.

Reduced case (**measured**, `directed zero.c n 8 1 c 0 1 /`): text
`// a\n// b\n`, parsed and drawn; replace byte 8 by `c`; replace byte 0 by
`/` (the same text); draw. Byte 0 shows face 0, a full recompute and the
frame after the parse show 57 (comment). Against Neovim (**measured**, 1 run
of `tests/test_syntax.lua` on `int x;\nint y;\n` with ops `e 8 0 7a`,
`e 0 1 75`, `f`): Neovim gives face 26 on byte 0, the PR gives 0.

It needs two edits before one frame, the later one at the first byte of the
file: an undo of two changes, a paste after a key, or a command that edits
bottom-up. The wrong byte lasts until the next parse finishes. The PR's
2,700 random cases did not find it because an edit lands on byte 0 about
once in 2,500 edits.

Fix that the probe accepts (**measured**, the 18 failing runs):

```c
if (!p) s->sa = 0;
else if (p - 1 < s->sa) s->sa = p - 1;
```

It needs a directed test and a plant, like `edit_far_capture`.

## Finding 2 (fix or record): the recompute's start changes which capture wins

`syntax.c` gives a byte the face of the last capture among those of the
highest priority, as Neovim does. tree-sitter does not return captures in a
fixed order: `ts_query_cursor_next_capture` holds back a finished capture
while an unfinished match has an earlier one, and which matches are in
progress depends on where the query's byte range starts. The full fill
starts at the first line the frame asks for. The partial recompute starts at
the widened seed, in the middle of a line.

Reduced case (**measured**, `directed order.c 6 1 ""`): text
`d f(u*s)\n*A;\n`, parsed and drawn; delete the `s`. The `*` at byte 5 is
captured by pattern 15 (`"*" @operator`) and by pattern 62
(`(parameter_declaration declarator: (pointer_declarator) @variable.parameter)`).
A query over the window returns `@operator` first, so the parameter face (3)
wins. A query from byte 5 returns it last, so the operator face (38) wins.
Neovim's frame before the parse gives 3 (**measured**, 1 run of
`tests/test_syntax.lua` with ops `e 6 1`, `f`); the PR shows 38.

How often (**measured**): 37 of 1,420,000 frames, all on far.c, all a `*`
between faces 3 and 38, all inside an `ERROR` node (checked on the six runs
that show it: 35 of 35 printed ancestor chains have one). 0 on coding.c in
80,000 frames. 31 of the 37 were in frames drawn from an edited cache; the
other 6 were scroll frames where the cache starts above the window. Main has
those for a scroll with no update in between; for a scroll followed by an
update that replaces no tree the PR adds them, because it removes
`s->cz = 0` from `syntax_update` (**hypothesis**, not run on main).

So the struct's comment, "a face can change only under a match that has a
capture over these bytes", is true of which captures apply and false of
their order.

Starting the recompute at the start of the seed's line (as Neovim redraws
from the changed line) is not a full fix (**measured**): it removes the
mismatches in 3 of the 7 runs that have them and none in the other 4.

Options, for the author to choose with evidence:

- Fix it: start the partial query where no match that can reach the seed is
  already in progress. That costs part of the speedup and needs measuring.
- Record it: `test_syntax` already accepts that windows starting elsewhere
  differ where the tree has a syntax error (1 of 80 cases). Then the comment
  must say so, the reduced case goes in as a listed known difference with a
  directed test that pins it down, and the PR text drops "0 differences" for
  this class.

I think recording is acceptable under Davy's known-difference bar: it is one
character's colour, in text that does not parse, until the next parse.

## Finding 3 (minor): one cache-emptying line has no check, another has one waiting

- `free_region`'s `s->cz = 0`: the PR says no check covers it and keeps it on
  a hypothesis. The probe shows it is needed (**measured**): with it removed
  (and finding 1 fixed), at least 7 of 72 runs differ, for example
  `diff far.md 7 3000 12` (9 frames): a scroll frees injected regions, the
  parse is stopped, and the frame shows faces of the freed trees. That run is
  a ready directed test and plant.
- `set_regions`' `s->cz = 0` ("faces are clipped to the ranges") is not in
  the PR's plant list and not mentioned. With it removed the probe found
  nothing in 72 runs (216,000 frames). Under the top rule it needs either a
  failing case or a line in the plants file saying why none can be planted.

- The PR's claims hold: the key-frame median drops on every real file (5 to
  30 times), DESIGN.md's p99 is not measurably lower (one seed's window is
  over 8 KB, and one seed's median stays at 1.38 ms here), and the frame after a parse is
  unchanged.
- The worst case I could think of for the new code, an edit inside a capture
  as large as the window so that the widening covers everything, is not
  slower than main (big.md: no measurable difference).
- Against the 2 ms budget the open items are the ones the PR lists: windows
  over 8 KB, and the full fill in the frame after a parse (p99 1.4 to 1.7 ms
  on DESIGN.md here).

## Smaller notes

- The reference: Neovim itself redraws only the changed lines after an edit
  and the rest after `on_changedtree`; the comment names Emacs's jit-lock,
  which is the closer match for widening to whole constructs. Fine as is.
- The probe is a candidate for the package's own checks: it found both
  findings and catches all six plants, where the 2,700 Neovim cases caught
  neither finding.
