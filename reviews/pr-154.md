## What the PR does

- The oracle's INC flow has a token `Y` whose foldexpr value is ">-1" (a
  start with an undefined level), which `syntax_foldexpr` can answer since
  PR 121 (**hypothesis**, from reading `fold_levels()`: a row computed from
  an added row's level -1 that also starts a fold; not run here).
  `tests/test_fold.c` replays it as `*start = 1; return -1`.
- `tests/fuzz_fold.c` draws levels `% 64` instead of `% 56`, so 63 is ">-1".
- It carries PR 122's review report (9f907e27).

Why Neovim agrees (read in v0.12.6 `fold.c`, then measured as above):
`foldlevelExpr()` sets `lvl = n` and `start = 1` for ">n"; each later
`getlevel()` call clears `start` first, and both the back-up in
`foldUpdateIEMS()` and the skip of undefined lines in
`foldUpdateIEMSRecurse()` end on a call for a defined line, so the start of
an undefined line is never read. `lvl_next` differs (-1 against the previous
level) but only "a1"/"s1" read it.

## Findings

1. **No plant for the new coverage (asked, applied in 9895956).** The first
   head left `tests/plants/fold.txt` alone, so nothing showed the Y tokens
   or the fuzzer's 63 failing. The two plants given (the back-up loop
   stopping at a start; the first-line rule skipping a start) survive main's
   trace and fuzzer and are caught by this PR's.
2. **A parse never gave ">-1" (suggested, taken).** `U` drew from
   `itoks[1..#itoks-1]`, which used to leave out `y`; with `Y` appended it
   left out `Y` and gave `y` 991 times, though a parse is where PR 121
   produces ">-1". Now `itoks[math.random(#itoks)]`: 794 `U` lines carry a Y.
3. Nit: the PR body said 182 Y tokens; the first trace had 363.

## Residual risk

The levels of the oracle stop at 4 and its buffers at about 40 lines, as
before. That PR 121 really emits ">-1" is not shown by a run here; if it
never does, this PR's coverage is harmless.
