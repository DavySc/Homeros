## Findings

### 1. A lone operator or register is not "pending": `d` Ctrl-C `j` during a run deletes (follow-up, package 5; on main before this PR)

The PR text says keys.c offers keys to `sql_key` "except while a count or operator is
pending". **measured:** false for a lone operator and a lone register. An instrumented
build that logs `e->ks.pending` in `keys_input` shows 0 after `d` and after `"a`
(1 after `3`, `d2`, `g`, `f`, `r`, and in the command line): `normal_pending()` is
`npend > 0`, and `d` alone completes `run()` with the operator kept in `oa`.
`include/keys.h` says `pending` covers "a count, register, operator or its motion".

Effect with this PR, 3 of 3 runs (a895e680 twice, 0a7462b1 once): F5, `d`, Ctrl-C,
`j` on the two-line buffer: the query is cancelled, `d` stays armed, `j` deletes both
lines (`u` brings them back). With no query running `d` Ctrl-C `j` only moves, as in
Neovim. Alt+Break, F5 and Ctrl+. take the same road after `d`; Ctrl-C is the first of
them that a Vim user presses in exactly that state, to drop the `d`.

Not this PR's to fix (the flag is `src/keys/`). Proposed for package 5:
`ks.pending` also set while `oa.op_type != OP_NOP` or a register name is owed, with a
test; then Ctrl-C after `d` is Vim's, as after `3`, and the PR text becomes true.

### 2. The condition is written twice (could be shorter)

`sql_key` now tests `!s || !s->q.n || s->cancel` on two adjacent lines. One line does
both keys: `if (!s || !s->q.n || s->cancel) return s && key == KEY_BREAK;`.
`shorter.patch` is that change with the second plant re-aimed. **measured:**
`test_sql_editor` 5 of 5 with it; 33 of 33 plants caught at a895e680 (the 32 listed and one of
mine, "Ctrl-C taken while the cancel waits"). One line less in `sql.c`.

## Notes

a. No test sends Ctrl-C through `keys_input` or `main.c`: `test_sql_editor` calls
   `sql_key` itself. The pty runs above are the evidence for the road from the
   terminal; `drive.py` could become a test when the editor gets a pty harness.
b. Reviewer plant rv7 (Ctrl-C drops the connection where Alt+Break sends a cancel) is
   not caught: after a cancel the test does not check that the session is the same
   one. The code cannot do this short of a per-key branch, so a note only.
c. `run()`'s message still reads "a query is running (Alt+Break cancels)", and a
   terminal cannot send that key. `include/sql.h` and `include/keys.h` (KEY_BREAK:
   "a terminal sends no key for it") name Alt+Break only: thread 0's.
d. **hypothesis** (read from `main.c:107`, not run: my slow-regex attempt ended in
   E363 at once): a Ctrl-C that interrupts a long command is also queued as a key, so
   one press would stop the command and then cancel the query.
e. **hypothesis** (read from `wl.c:176` and `win/backend.c:173`, not run): both GUI
   backends deliver Ctrl+C as 3 through their character path, so the GUI gets the
   same key. `test_wl` and `test_win` do not list it.
f. Insert mode: Ctrl-C during a run cancels and leaves Insert mode on. Inside the
   contract; said here because some Vim users leave Insert mode with Ctrl-C.
