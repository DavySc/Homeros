## Blocking

### B1. A long token is lexed again for every 256 bytes drawn (frame budget)

`tsql_faces` starts at a token start at or before `a` and lexes that token
to its end, every call. `core_draw` calls it once per 256 bytes of every
visible line. So when the window lies inside one long token, a frame costs
(lines on screen) x (token length). Typing `/*` at the top of a file does
this until the comment is closed: SQL Server nests comments, so with the
file's own balanced comments the new one runs to the end of the text.

**Measured** (`bench FILE REP open`: warm, `/*` inserted at byte 0, a
50-line frame at the top; 5 runs; file is `reviews/pr-51-repro/tsql.sql`
repeated):

| Text | Frame, median | Range |
|---|---|---|
| 42 KB | 1.84 ms | 1.43 to 2.42 |
| 280 KB | 13.0 ms | 9.8 to 13.2 |
| 981 KB | 46.2 ms | 34.9 to 48.5 |
| 2.8 MB (on 8825270) | 135 ms | 103 to 158 |

The same frame without the open comment: 0.04 to 0.13 ms (`bench ... key`,
5 runs). The 2 ms gate (DESIGN.md) is passed from about 40 KB, and every
key typed inside the comment pays it again. A plain long block comment
(a file header) pays the same in proportion.

Fix (hypothesis, not built): keep the end and face of the token at `q->at`
beside it, and when `a` lies inside that token, paint from it without
lexing. Two fields, cleared by `tsql_edit` with `at`.

### B2. Two categories differ from Davy's SSMS screenshot

`/mnt/project-files/syntax/ssms-screenshot.png` shows `ssms-check.sql` in
SSMS's dark theme. Commit 0bdb7ee says every word of it already had SSMS's
category and makes its lines directed cases. I sampled the ink colour of
each word (`shot2.py` for the cells, output in `ssms-cells.txt`; the hex
values below are the mean of a word's 8 strongest pixels) and compared
with this head's faces (`toks`). Two of the new directed cases encode the
wrong category. **Measured, 1 screenshot, 22 lines:**

- **Numbers are coloured.** `0`, `10`, `30` are a light green (#9ab493,
  #a4a96e, #9ead79; plain text beside them is #bec6c5 to #cecfcd, with no
  green cast). The PR leaves numbers plain "as in SSMS", and the directed
  case for `DECLARE @n int = 0;` expects plain. They need `FACE_NUMBER`.
- **`day` in `DATEADD(day, -30, ...)` has the function colour** (#ae6dbe,
  as `DATEADD` #bb6dc4), not the keyword colour. The PR's rule "a function
  that is also a keyword is a function only when called" is wrong for
  `day`, and the directed case for that line expects keyword. The screenshot has no other word of that class (the table has 26:
  `char`, `convert`, `year`, `month`, `left`, `right`, ...), so which of
  them follow `day` is still a hypothesis. `LEFT JOIN` is grey there, so
  the operator words do win over the function class.

Everything else in the file agrees: keywords (including `status`, `name`,
`type`, `NOCOUNT`, `GO`, the types), `OR`/`AND`/`NOT IN`/`NULL`/`LEFT JOIN`
grey, `ISNULL`/`COALESCE`/`GETDATE`/`@@ROWCOUNT` magenta, `sp_executesql`
maroon, `sys.objects` green, strings, comments, variables and `[note]`
plain, punctuation grey.

Settled (coordinator, 12:04 UTC): Davy wants SSMS's categories with
Homeros' own Catppuccin colour per category, so the hues stay. For the
record: the screenshot is SSMS's own dark theme (blue
keywords, red strings, green comments). The PR maps categories to Homeros'

That keeps one look across languages; if Davy wants SSMS's hues in

### B3. `fuzz_tsql` never reaches the kept token starts

Its header says "a window read through the kept token starts equals a
fresh read from 0". The Makefile runs fuzzers with `-max_len=256`; the
text built from 256 bytes stays far under `CK` = 4,096, so no start is
ever kept. **Measured:** with `abort()` in place of the store
(`q->ck[q->n++] = ...`), `make fuzz FUZZERS=tsql FUZZ_SECONDS=60` passed,
775,391 runs (first plant of `extra-plants.txt`). The index, the binary
search and `tsql_edit`'s drop are checked only by `test_tsql`'s fixed seed.
Either the fuzzer reaches them (for example a run of spaces whose length
the input picks, in 1 KB steps) or its header stops claiming it.

### B4. `tsql_faces` clears the faces twice

`syntax_faces` already does `memset(face, 0, z - a)` before it hands over;
`tsql_faces` does it again. **Measured:** with the second removed,
`make test TESTS=tsql` passes (second extra plant). One of the two goes
(CLAUDE.md, top rule). If `tsql_faces` keeps its own for callers outside
`syntax.c`, then `syntax_faces` should branch before its memset.

### B5. A far read costs 3 ms per MB inside the redraw (frame budget)

All lexing happens in `tsql_faces`; `tsql_update` only allocates. A first
jump to the end, or the window at the end after an edit near the top,
reads the text between in the frame. **Measured** (`bench ... end`, 5 runs):
280 KB 0.66 ms (0.64 to 0.89), 981 KB 2.7 ms (2.1 to 2.8); on 8825270
2.8 MB 6.5 ms (6.4 to 20.2). The PR reports the same shape (33 ms at 11.3 MB) and rests
on the hypothesis that Davy's T-SQL files are far smaller. It is over the
2 ms gate from about 600 KB. The contract's place for such work is
`syntax_update` with `stop`: filling the index there in slices would close
it. Blocking since 12:08 UTC: asked whether he opens SQL files over about
600 KB, Davy answered "Yes I do", so the hypothesis the PR rests on is
false. (This was N1, not blocking, in the first version of this report.)

## Not blocking

### N1. Shorter code

- Lower-casing is written three times: `tsql_word`, `is()`, and the
  `sp_`/`xp_` test with both cases spelled out. `word_face` copies the word
  into `w[40]` and `tsql_word` copies it again into `l[40]`. One lower-case
  copy in `word_face`, compared with `strcmp`/`strncmp`, and a static lookup
  both share, is shorter.
- `test_tsql.c` has the snippet-append loop twice (`gen` and the edit's
  insert).
- `syntax_open` tests the `.sql` suffix by hand two lines above
  `lang_of_path`, which does the same compare.

### N2. Rules no check sees (extra plants 3 to 7, all not caught)

- A called keyword-function with a space before `(`, such as
  `CONVERT (int, x)`: the directed line has only `COUNT (*)`, which is a
  function either way.
- `(` being `TQ_PUNCT` and not `TQ_OP`: only `.` is tested. The formatter
  will depend on the kind.
- `sp_` alone staying plain; words of 20 to 39 bytes being looked up; the
  schema name read from byte 0.

### N3. Smaller things (all measured with `toks` or `longid`)

- `<<` and `>>` (SQL Server 2022) are two tokens each. Colours are the
  same; the formatter must not space them.
- A NUL byte before `=` is one two-byte operator: `strchr(s, 0)` finds the
  terminator.
- A name of 1 MB before `.y`: the faces of `y` take 80 ms (3 runs, 80 to
  91), because `word_face` walks back a byte at a time and each step reads
  a fresh 4 KB window. 20 KB: 0.9 ms. Only a pathological file.
- `X.SQL` is not coloured (suffix compare is case-sensitive, as
  `lang_of_path` is). Davy tests on Windows.
- The index is grown by exactly what is missing, so typing adds one
  `realloc` per 4,096 bytes of growth, in `syntax_update`, not in the
  redraw. A gap in the index (text grown past `cap` before an update) is
  never filled; reads there start further back. Colours are the same.
- Double-quoted text: SSMS may colour `"x"` as a string (red). Hypothesis;
  the check file has none. Worth a line in `ssms-check.sql`.

## What holds

- **Edits (argument, then measured).** Where a token ends depends on at
  most the two bytes after it (the `e` and sign of an exponent), so a
  start more than two bytes below the edit stays valid; `tsql_edit` drops
  from `pos - 2`. `test_tsql`: 36 lines, 30 tokens, 12,000 edits and
  windows, 3,732,925 bytes, 0 differ (1 run).
- **Case.** `select`, `Select`, `SELECT`, `sElEcT` all keyword (`toks`).
- **Word table** (`words`): 1,280 words, strictly ascending by byte, all
  lower case, longest 35 bytes, 1,280 classes, 94 with `TQ_RECASE`, each
  of those a keyword or operator word. 19 operator words.
- **Allocation.** `tsql_faces` and `tsql_edit` do not allocate (read).
- **Against PR 51's bar** (`reviews/pr-51-repro/first.sh`, 5 runs): open,
  first faces and first update all 0.00 to 0.01 ms (PR 51: 54.6 ms); RSS
  after first use 1,992 to 2,052 KB (PR 51: 29.5 MB); `tsql.o` is 20.6 KB
  of code and 10.2 KB of data at -O2 (PR 51's parser: 11.7 MB).
- **A key in the window:** 0.04 to 0.13 ms a frame (5 runs each at 42 KB
  and 280 KB).
- `make test TESTS=tsql` under ASan and UBSan: passes. `tsql_free` leaking
  the index is caught by LeakSanitizer (planted).
