## Verdict: CHANGES REQUESTED

The port is careful and the author's claims hold (first table). It is not ready because of one
read outside the text and one half of an Org expression that was not ported, both small to fix,
and because the fixed gate (`test TESTS=org` and `org-conform -o ORG_N=2000 SEED=1`) lets 41 of
my 68 planted bugs through, 22 of which I showed to be real behaviour nobody tests. Nothing calls
`org_open` yet (the keys come with core and keys), so nothing here reaches Davy today.

## Required

### 1. A read one byte past the text (measured, ASan)

`global()`, `src/org/org.c:3424`: `S[x] == '<'` is read with `x == N` when `pos == n` and the
text ends in a comment, keyword or property line with no newline. Smallest case: the three bytes
`# x` (`texts/oob.org`), `org_open(s, 3, 3, &o)`:

    ==19465==ERROR: AddressSanitizer: heap-buffer-overflow ... READ of size 1
        #0 global src/org/org.c:3424   #1 org_open src/org/org.c:3490

`pos == n` is a position the PR's own driver, fuzzer and test ask at, and an empty buffer's only
one. The driver and the fuzzer hold the text in a large static array, so ASan cannot see a read
at `s[n]`; `rv/exact.c` copies each text into a heap block of exactly its length. With the one
comparison guarded (`x < N &&`), 1,085,647 calls (every character of 3,000 bent texts) read
nothing outside.

Asked: the guard; `check_open` in `tests/fuzz_org.c` (or test_org) calling on an exact-size heap
copy, so the check can see this class; a plant for it.

### 2. Half of org-open-at-point-global's line count is not ported (measured against Emacs)

Org searches for a link around a comment, keyword or property line over

    (max (count-lines (backward-paragraph) origin) (count-lines origin (forward-paragraph)))

lines each way. `global()` counts only the forward half (`k`). So a link that began more lines
above the cursor than the paragraph has left below is not found:

    #+A: [[https://x.org/a][one
    #+B: x
    #+C: two]] y            <- on this line Org: link https //x.org/a   ours: error No link found

(`texts/back1.org`, `back2.org` the same in a `#` comment.) The author's own generator reaches
it when asked at every character instead of six: 2 of 1,500 texts (seed 14, `texts/back3.org`,
an angle link left open two lines above a `#+NAME:` line), 3 of 600 and 3 of 1,500 with general
element lines mixed in.

Asked: the backward count; a generator shape that reaches it at the fixed seed; a plant.

### 3. Two more answers that differ from Org: fix or list (measured, each position in a fresh Emacs)

- Blank lines before the text's first headline (`texts/lead.org`, `"\n\n\n* a\nb\n"` at 0, 1, 2):
  Org "No link found", ours `offer`. `at_point` never asks whether `pos` is before the first
  element. 61 of 1,500 mixed texts; the open generator never starts a text with a blank line.
- A planning or clock line followed by a last line of only blanks with no newline, at the end
  (`texts/tail.org`): Org "No link found", ours `offer`. Org's parse there gives a one-blank
  paragraph (ours too, `org_conform` agrees), but `org-element-at-point` answers the clock.

Either is fine as a listed known difference in `org.c`'s comment if the fix costs more than it
is worth; today neither is listed.

### 4. The gate lets most planted bugs through (measured)

I planted 68 bugs of my own in the new code (`my-plants.txt`, one changed line each), then ran
each against `org_conform -o 2000 1` and the survivors against test_org (`logs/my-plants.log`,
`logs/my-survivors.log`). The other org-conform modes never call `org_open`, and the fuzzer only
checks that it ends.

| | plants |
|---|---|
| caught by the gate | 27 (26 by `-o`, 1 by test_org) |
| survive, and answer differently from the tree on 3,000 bent texts (`mutants.py`, 1,085,647 positions) | 13 |
| survive, same on those texts, shown different by a text written for them (`mt.sh`) | 9 |
| survive, no difference found | 19 |

For all 22 in the middle rows the tree is the one that answers as Org (asked at the differing
position, fresh Emacs each), so the code is right and untested. They are, by what breaks:
`_*` scripts; a `$` fragment closing after a blank; an inline call's end header; tags of one colon
pair; a line break in a headline; blanks before a newline in a path; halving backslashes
(178 of 3,000 texts, the widest gap); the `ftp.` guess; a bare scheme; a blank-only radio match;
a radio link ending inside a word; a custom id by prefix; a description running past its
container; `-` in a snippet's back end; `_` in a macro's name; `[[~x]]`; `file:///x` and
`file://c:/x` losing their slashes (what the editor will hand to proc_open); an address whose
domain starts with a dot; the counter before an item's tag; `COMMENT` before a title;
`<<<words>>>` inside verbatim taken for the radio target.

Asked: generator shapes (or test_org cases with Emacs's answers) and plants for these 22. Asking
at every character of fewer texts found more than six positions of many: consider it for `-o`.

Of the last 19, these look unobservable through `org_open`, so the code could go (hypothesis,
each checked on one or two texts only): the newline alternative of `words_at`'s `sep == 2` (a
radio target holds no newline, so `rsearch`'s context check never passes with one); the checkbox
line of `itag` (a checkbox holds no object and is followed by a blank); `at_point`'s
`type != ORG_PLAIN_LIST && type != ORG_TABLE`; the timestamp-before-link order at `<` (the two
never both match).

## Could be shorter (CLAUDE.md: a review flags these)

- **`tail()` is a second matcher for a regexp `tags()` already matches** (measured). With
  `title()` calling `tags()`, `tail()` goes and `org.c` is 11 lines shorter
  (`title-with-tags.diff`). Same answers as the tree on the 3,000 bent texts and on 4,000
  headline shapes at every character; 0 of 2,000 differ from Org (`-o`, seed 1); builds with
  `-Wall -Wextra -Werror`.
- **`itag()` is a third copy of org-list-full-item-re's counter and checkbox** (read; the
  saving is a hypothesis). The item parser (`org.c:494` to 500) and the colours (1697 to 1702)
  already read them, and Org's own org-element-context takes the tag from the item parser. Each
  copy is under `make dupes`' 50 tokens. One function giving where the counter and checkbox end
  would serve all three.
- **The comment over the section is stale** (measured): it lists "link types and the TODO
  keywords match case and all" as a known difference, but with `FOLD` they agree with Org
  (`[[HTTP:x]]`, `* todo Task`: 0 of 150 positions differ). The differences that do exist are
  not there: the 64-object nesting limit (in `context_in`'s comment), the footnote definition
  after an affiliated keyword and Org's stale tags match (only in `org_conform.py`'s filters).

## Smaller findings (not blocking)

- **Quadratic in a paragraph's length when the note has a radio target** (measured, -O2, whole
  process, median of 5, `perf.py`, `perf2.py`). `lex()` calls `radio_search` from the point for
  every object, and a search that finds nothing runs to the paragraph's end each time. One radio
  target elsewhere, a link at the paragraph's end: 200 lines 56.7 ms (56.4 to 58.4), 1,000 lines
  1,386 ms (1,336 to 1,408), 4,000 lines 22.3 s (21.8 to 22.9); without the radio target 1.4,
  3.1 and 9.1 ms. At sizes notes have it does not show: 50 radio targets and 30 lines 5.9 ms,
  100 lines 53 ms. Remembering a failed search for the region would end it; or record the cost.
  Everything else I timed on 1.7 MB is under 115 ms (20,000 paragraphs 7 ms; 2,000 radio targets
  113 ms; 20,000 footnote references 6 ms).
- **A message over 511 bytes is cut inside a UTF-8 character** (measured, `cut.c`: a fuzzy link
  of `x` and 300 `é` ends in the byte C3). The header's promise is about targets; the message
  goes to the status line later.
- **Org loops forever** on `texts/hang.org` (a one-character radio link at a line's start with
  an object glued to it, asked on the object: Emacs at 100% for 9 minutes until killed). Ours
  ends with "No link found". No reference to copy; worth a line among the known differences.
- **The oracle answers some positions from Org's element cache** when asked in a row
  (`texts/cache.org`: at 12 Org says `link HTTP /x` alone, and "No link found" after being asked
  at 3). The port agrees with the fresh answer. 9 of 5,700 probe texts; with six positions a text
  it rarely shows, but a one-in-a-thousand red seed in the nightly run may be this. `probe.py`
  asks again in a fresh Emacs before counting a difference.
- `org_conform.py`'s first `-o` filter drops a whole text when it holds a footnote definition
  after an affiliated keyword, whatever differs in it; the second filter is per line. Rare
  (2 "no answer" in 20,000), so little hides there, but a per-line filter would hide nothing.
