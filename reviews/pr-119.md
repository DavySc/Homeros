## Findings

### 1. An outside change during a selection turns `s` into "stage the whole hunk" (blocking)

**measured** (1 headless trace run, 1 run of the real editor on a pty).
Steps: `region-stage`'s setup, `C-j C-j`, `Tab`, `j`, `jj`, `V`, `j`, then from outside `printf zz > zz.txt`, then `s`.
The watch refresh runs `git_show`, which calls `git_unmark`: Visual ends. `s` then acts on the hunk at point and stages all 8 changed lines. magit (recorded: `rv-outside-change`) stages the 2 selected lines, because it only refreshes after its own commands. In the real editor the mode line goes from V-LINE to NORMAL and `git diff --cached` then shows 8 changed lines. With `x` the question becomes "Discard hunk?" instead of "Discard region?".
Nothing tells the user; a build or another tool writing in the work tree between `V` and `s` is enough. This is the "views refresh on inotify" divergence meeting "Visual ends on refresh".
Ask: a refresh that the user's own write did not cause must not turn a line selection into a whole-hunk action. One way: end Visual only on the refresh that follows our own write (magit's case), and on a watch refresh keep Visual and carry `ks.vline` through `git_successor` as the cursor is. Add `rv-outside-change` to the traces and a plant.

### 5. In the real editor Visual mode does not really end (blocking; in 716da9f too)

**measured** (2 pty runs of `build/san/homeros` at 20828af).
`e->ks.visual`, `ks.vline` and `ks.vcol` are copies that keys writes after every key it handles (`src/keys/keys.c:197-199`, from `VIsual_active`, `VIsual_mode`, `VIsual`). `git_unmark` clears the copy; keys still has Visual on.
Steps: `SPC g g`, `C-j C-j`, `Tab`, `j`, `jj`, `V`, `j`, `s`: two lines staged, mode line NORMAL. Then `j`: the mode line is V-LINE again, with the old anchor. Then `j`, `s`: "-four" alone is staged (3 changed lines in the index), where magit, with no selection, stages the whole hunk. A `V` typed right after the stage is swallowed: it turns the still-active Visual off.
`git_remark`'s write to `ks.vline` is lost the same way at the next key keys handles.
`test_git` cannot see any of this: its `motion()` sets `ks.visual` and `ks.vline` itself, and keys never runs.
Ask: end Visual through keys (`keys_feed(e, KEY_ESC, 0)` may be enough; otherwise a function of keys, through thread 0), move the anchor in a way keys keeps, and add a check that runs real keys (`keys_feed` in `test_git`, or a pty test like `tests/start.py`), with a plant.

### 6. A selection begun while a write runs is ended by that write (hypothesis)

Read from `finish()`, not run: finding 5 masks it on a pty. Visual ends when the write ends, not when it is queued. With a slow `git apply` (Windows process start), `s` then `V j` typed before the write ends loses the new selection, and the next `s` takes the whole hunk. The patch is built at the key, so ending Visual when the write is queued does the same job and matches magit's order of events.
