## Findings

### 1. In a C buffer the float is not what Neovim shows, and its last line is cut off (blocking, measured)

`nvk.sh` types `3G04lK` into Neovim in an 80 x 24 tmux with the repo's own `test_core_markdown.lua`, on a C file whose fake server answers with clangd's shape (heading, rule, list, rule, a ```` ```c ```` block). Neovim's screen (2 runs, and 2 more with a Markdown buffer opened first: the same):

```
3   int foo(int x);
~       ### function foo
~       ────────────────────
~       → int
~       Parameters:
~       - int x
~
~       Adds one.
~       ────────────────────
~       int foo(int x)
```

Homeros on the same answer (`p4_first.c`, 2 runs; `p6_cpp.c` with the real clangd 18.1.3 shows the same shape):

```
|3   int foo(int x);
|~         󰲥 function `foo`
|~       ────────────────────
|~       → `int`
|~       Parameters:
|~       ● `int x`
|~
|~       Adds one.
|~       ────────────────────
|~       c███████████████████
```

Neovim does not draw the float with render-markdown's look when K is typed in a C buffer: plain treesitter Markdown, backticks concealed, both fence lines hidden, 9 rows, the signature visible. Homeros takes the 9 rows (the size matches) but draws render-markdown's look into them (heading icon, bullet, a language row), so the signature `int foo(int x)`, the line a C hover is for, falls off the end.

Why the tests did not see it: `tests/test_core_float.txt` (the only test that compares the float's screen) opens every float over a Markdown buffer (`f.md`), where render-markdown does draw it. `test_lsp_locs` runs K in a C buffer but compares only the float's text and its place and size.

Asked: a screen comparison of K's float in a C buffer against Neovim, and the float drawn as Neovim draws it there. If that turns out to be the plain treesitter float, most of the render-markdown sizing in `core_float` (the second pass, `fence()`, `rm_attached`) may not be needed for K at all, which the minimal-code rule would welcome. I did not look for the cause inside render-markdown.

### 2. A second float in one session is one row taller than Neovim's (blocking, measured)

`rm_attached |= md` makes every float after the first skip pass 0. `p4_first.c`: first K height 9, second K (same place, same answer) height 10. Neovim: 9 every time (`nv4.sh api`: 6 K in one session, 9 each, also after a Markdown buffer was opened and left; `rec.py`, the PR's own recorder, 4 times: 9, 9, 9, 9).

The test cannot see this: `tests/test_lsp_locs.c` calls `core_free()` after every case, which resets `rm_attached`, while the recorder runs all cases in one Neovim. So each replayed hover is a "first float". Replaying the PR's file plus those 4 recorded cases passes (`locs_plus_clangd4.txt`, 1 run), and the editor still shows 10 on the second K.

### 3. An earlier K's answer is shown at a later K's place (blocking, measured)

`keys.c` keeps one `asked` position for all requests, overwritten by each `lsp_go`. K at line 0, cursor to line 1, K again before the first answer comes: the first answer (for line 0) passes the check, because the cursor is where the *second* K was typed. `p1_stale.c` (2 runs): the float "ANSWER FOR LINE 0" stands under line 1, whose own answer was null, with "No information available" on the command line. Neovim (`nv.sh p1`, 2 runs): no float, "No information available" (each request carries its own position).

### 4. The float stays over another buffer; ordinary wrapped windows draw slower (blocking, measured)

a. `core_popat` holds the window, line and column, not the buffer. K at 0,0, then `:e o.c` (cursor 0,0 there): the float stays over the other file (`p2_buf.c`, 2 runs). Neovim closes it (BufLeave; `nv.sh p2`, 2 runs). `keys.c`'s `asked` (buffer, line, column) and core's `core_popat` (window, line, column) are two records of "the cursor is where it was"; fixing 3 and 4a is a chance to keep one.

b. `lbr_cellw` does its bookkeeping (`win_numw`, three `isbreak` scans, the indent count) for every cluster before it tests `w->lbr`. `bench_draw.c` (core_draw of a 60 x 200 window on `src/core/core.c` saved as .txt, 3000 frames a run, main and PR alternating, 2 series of 7; the machine was also running tests):

| | main, median (range) | PR, median (range) |
|---|---|---|
| wrap on, series 1 | 140.1 us (137.5 to 164.9) | 215.0 us (193.9 to 227.9) |
| wrap on, series 2 | 147.5 us (140.3 to 155.6) | 212.0 us (199.1 to 259.3) |
| wrap off, series 1 | 78.1 us (73.2 to 86.2) | 86.2 us (85.3 to 89.4) |
| wrap off, series 2 | 80.4 us (76.1 to 109.0) | 89.5 us (88.3 to 108.3) |

With wrap on the ranges do not overlap: about 45 to 50 % slower per frame in a window that has no float. With wrap off the ranges overlap: no measurable difference by the rule. Asked: the `!w->lbr` return first, so a window without lbr runs main's code.

### 5. DESIGN.md says a superseded hover is cancelled; the PR removes that and its check (blocking unless the design row changes, measured)

DESIGN.md, "Sources of truth": "Hover, then an edit 200 ms later | ... | Chosen: cancel the old request, drop a stale reply (LspSync model)". `lsp_ask` sent `$/cancelRequest`; hover through `lsp_locs` never does. `p5_edit.c` (2 runs): K then `x`, then K K: the server's log has three hovers and no cancel. The stale reply is still dropped (the re-aimed plant is caught). The PR also deletes test_lsp's check "a new request cancels the last" and its plant. Either `lsp_locs` cancels a hover it will no longer use (`cancel()` is still in lsp.c), with the check and plant kept, or the DESIGN.md row is changed by its own rules. Thread 0 agreed to the header lines; I found no agreement to drop the chosen behaviour.

### 6. Smaller points (not blocking)

- **The hovered range is not highlighted.** Neovim marks the answer's `range` with `LspReferenceTarget` while the float is open (`nv.sh range`: extmark 0,4 to 0,5, background 45475a in catppuccin). `hover()` in lsp.c never reads `range`. Not in the PR's known differences. Build it or list it.
- **Untested branches** (my plants, not caught): the float closing when another window becomes current (plant 1); the clamp to the screen's right edge (4); all of `split()`'s `@param` / `@return` handling, both the blank-line dropping (5) and the kept blank before an indented code block (6): the generator `md()` makes no such lines; `E->buf != asked.b` (7); `d K` (10); K in a buffer without a server (11).
- **Equivalent code:** `wc = (wc - W) % W` equals `wc %= W` whenever `wc >= W` (plant 17 not caught, and cannot be). One term shorter.
- **A known difference only in a comment:** a hover of only blank lines makes Neovim fail ("Invalid 'width'") and Homeros show an empty float (`tests/test_lsp_locs.py`, `md()`). The PR body should list it.
- `draw_pop` closes the float (frees) inside the draw. It allocates nothing, so the redraw rule holds; noted only because draw otherwise changes no editor state.
