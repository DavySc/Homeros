# Review of PR 53: CR LF files, Neovim's 'fileformat'

**Verdict: APPROVE** at a8cec64. No blocking finding is left.

The one blocking finding (1) was true of the head I started on, 89efb91: the PR broke an existing plant, so `make planted` failed (386 of 387 caught, 1 did not apply). The author pushed a8cec64 while I was reviewing, which moves that plant's anchor and changes nothing else; I ran the plant on a8cec64 and it is caught. So every plant is caught: 387 of 387.

The feature held up. Nothing I ran loses or changes a byte of a file, and a CR LF file opens with clean lines and `[dos]` and saves CR LF, on Linux and under Wine. Findings 2 to 8 do not block. 2 and 3 are places where the PR says "as Neovim" and Neovim does something else; I would keep the PR's behaviour in both, but the comment in `include/file.h` should say so (`reviews/pr-53-repro/suggested.diff`), in this PR or the next one that touches the file.

Reviewed at 89efb91, then a8cec64 (base c82e009, which both heads already contain: `git merge-base --is-ancestor origin/main pr53`), 2026-11-18. Everything below was run at 89efb91 unless it says otherwise; a8cec64 differs from it in one line of `tests/plants/core.txt` (`git diff 89efb91 a8cec64 --stat`), so the sources measured are the ones to be merged. Run on a 4-vCPU cloud guest, gcc 13.3, clang 18.1.3, Neovim 0.12.6 (`nvim --headless --clean -n`, `nofixendofline`), Wine from `tools.nix`. Repro files are in `reviews/pr-53-repro/`; `run.sh` reruns the differential tests, the journal cases, the undo and syntax checks and the fuzzer (about 15 minutes).

### 2. Not blocking, to record: Neovim decides from its first 8,192 bytes; the PR decides from the whole file (**measured**)

`include/file.h` and `src/file/eol.c` say the format is chosen "as readfile() decides: dos when the data has a LF and every LF follows a CR". Neovim 0.12.6 does that only when the first LF is within the first 8,192 bytes. A CR LF file whose first line is 8,191 bytes or longer is `unix` in Neovim, with `^M` on every line; here it is `dos`.

`firstline.sh` (1 run per length; first line of N bytes, then `b\r\n c\r\n`):

| first line | Neovim | PR |
|---|---|---|
| 100, 8,000, 8,190 bytes | dos | dos |
| 8,191, 8,192, 16,000, 65,000, 65,534 to 65,537, 70,000, 480,000 bytes | unix, line 2 is `b^M` | dos |

In my random test, 26 of 4,000 files had the first LF past byte 8,192, and 12 of those 26 got another format than Neovim's (the other 14 are unix by either rule). The author's test cannot reach this: its lines are at most 12 pieces of 1 byte, and its three "over 64 KiB" files are 9,000 short lines.

Both editors write such a file back byte for byte (measured in the same script), so no bytes are at stake, only what is shown and what a new line gets. The PR's rule is the one Neovim's help states (`:help 'fileformats'`: "If all lines end in <CR><NL>, and 'fileformats' includes "dos", 'fileformat' is set to "dos""), and it is the better one for Davy: no `^M` in a CR LF file with a long first line, and a line added to it gets CR LF like the others. I would keep it. But CLAUDE.md asks that a departure from the reference be stated and not claimed as a copy. Asked for: correct the comment (wording in `suggested.diff`), say so in the PR, and add one such file to `tests/test_file_eol.c` so the choice is pinned (expecting `dos`, with Neovim's answer named in the comment).

On Windows ("dos,unix") I expect no difference, since a first chunk with no LF takes dos there and a later bare LF sends Neovim back to unix: **hypothesis**, I had no Windows Neovim to run.

### 3. Not blocking, to record: a CTRL-Z that ends a dos file (**measured**)

Neovim hides a CTRL-Z (0x1A) that is the last byte of a dos file ('endoffile') and writes it back at the end. The PR shows it as text: a last line `^Z`, or `b^Z`.

| file | Neovim | PR |
|---|---|---|
| `a\r\nb\r\n\x1a` | dos, 2 lines, `[dos] 2L, 7B` | dos, 3 lines (`a`, `b`, `^Z`), `[noeol][dos] 3L, 7B` |
| `a\r\nb\x1a` | dos, lines `a`, `b` | dos, lines `a`, `b^Z` |
| `a\nb\n\x1a` (unix) | 3 lines, same as the PR | same |

Opened and written with no edit, both write the file's own bytes (0 of 800 random files with CTRL-Z in the alphabet differed in bytes; 11 differed in lines, all of this kind). After an edit the bytes can differ: with a line added at the end, Neovim writes `x\r\n\x1a` and the PR writes `\x1a\r\nx` (2 of 800 files with keys differed in bytes, 11 in lines; seeds 21 and 22). Nothing is lost silently, since the `^Z` is on screen. Such files are rare now (old DOS tools). Asked for: a line under "Not done" and in the comment; the author's generator has no 0x1A, so this was never compared.

### 5. Not blocking: the core's Windows side works, but only my run shows it (**measured**, 1 run under Wine, `wine.sh`)

I built the driver with the Windows editor's sources (the Makefile's `WIN_SRCS` without the window) and ran it under Wine:

| file | format, read message | after `:w` |
|---|---|---|
| `a\r\nb\r\n` | dos, `2L, 6B` (no `[dos]`: it is the system's first) | byte for byte |
| `a\nb\n` | unix, `[unix] 2L, 4B` | byte for byte |
| `a\r\nb\nc\r\n` (mixed) | unix, `[unix] 3L, 8B` | byte for byte |
| `abc`, empty, `a\rb` (no LF) | dos | byte for byte |
| `a\r\nb` | dos, `[noeol] 2L, 4B` | byte for byte |
| `a\nb` | unix, `[noeol][unix] 2L, 3B` | byte for byte |

This is what Neovim's rule gives for "dos,unix"; I could not run a Windows Neovim beside it. `DOS_FIRST` in `core.c` repeats `FIRST` in `eol.c`, and nothing in the check fails if the two disagree on Windows (x9). One definition would remove the question, for example `file.h` naming the constant, or the core asking `file_eol` with no data.

Relayed by the coordinator, not measured by me: Davy opened a CR LF file (CLAUDE.md) in a trial build with this PR on real Windows, once, and saw no `^M`. That run did not cover saving.

### 6. Not blocking: a journal from before the PR, whose text is the file's, is "recovered" (**measured**, 1 run, `crash.sh`)

A journal written by main for a CR LF file holds the CRs in its text and no `J_DOS`. If its edits were undone before the kill, the journal saves exactly the file's bytes, and main would drop it. The PR compares the journal's text with the stripped data and its format with the file's, so they differ, and the buffer opens as "recovered", modified, unix, with `^M` on each line. Saving it writes the file's own bytes, so nothing is lost. It can happen once, for a journal left by a kill before the update. With an edit left in the journal the recovery is right (`xa\r\nb\r\n` after `:w`). No change asked for; noted so it is not a surprise.

### 7. Not blocking: smaller code (by reading, **hypothesis** that it is equivalent)

- `bytes` in `buf_load` and in `:e` is the file's size at the load, which `id.size` already holds; `core_write` prints `(size_t)b->id.size` for the same purpose. Two locals could go.
- `DOS_FIRST` (finding 5).

### 8. For thread 0: `design/DESIGN.md` line 306

It lists "CRLF ... and a missing final newline must survive a save byte for byte" under "Scenarios listed but not yet designed or tested". After this PR both are designed and tested (a byte-order mark and invalid UTF-8 are not part of it). The PR rightly leaves `design/` alone.

## The headers

`include/` is thread 0's. The PR says thread 0 agreed; I cannot check that, only the change:

- `include/file.h`: `file_eol` added, `file_save` gains `int dos`. Needed: the core must learn the format at load and pass it at save, and `src/file` is where both systems' file code lives. `file_save`'s comment now says the identity's size is the bytes written, which is what finding "a second `:w`" relies on. All callers are updated (`grep file_save`: `core.c`, three tests).
- `include/core.h`: `Buf.dos`, one line. Needed for the message, the journal and the save.

That is minimal for the design chosen. The comment on `file_eol` needs the correction of finding 2.
