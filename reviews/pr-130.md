## Blocking

1. **On Windows a close that comes with the server's last bytes is never seen.** **measured**
   - `net_read` resets the socket's event with `WSAEnumNetworkEvents` and then calls `recv` once. Windows reports FD_CLOSE once. When the reset takes FD_CLOSE together with FD_READ, the `recv` returns the data, and nothing signals the event again: the `recv` that would return 0 is never made.
   - `close.c` is that sequence alone (same socket flags, same event mask, one 64 KB `recv` per wake) against a server that sends N bytes and closes. On the Windows runner, 18 runs: the close was seen in 3 (10 bytes with no pause, where the data and the close woke the event separately) and **never seen in 15** (10 bytes after a 300 ms pause; 100 KB and 1 MB with and without the pause; 3 s wait each). Under Wine the same 6 cases: seen in 6 of 6, and again in 2 of 2 later. Wine signals the event again after the data is read; Windows does not. This is why `src/sql/check.sh` cannot show it.
   - What it means in the editor: the session stays in its state. Where the reply already ended (a refused login, SQL Server's `KILL`, which sends Msg 596 and a DONE) nothing is lost but the news, which comes with the next query. Where it did not, the run never ends: PostgreSQL's "terminating connection due to administrator command" (a restart, `pg_terminate_backend`, an idle timeout) comes as a message and then the close, measured above, and any server that goes away mid-reply does the same. `net_read`'s own comment relies on the lost read: "the closed socket is the next read's".
   - A fix that holds on Windows: remember FD_CLOSE when `woke()` sees it, and from then on set the event again (`WSASetEvent`) after each read, so every wake reads until `recv` returns 0. `close.c` with a third argument does that; under Wine it sees the close (1 of 1). On the Windows runner it saw the close in 11 of 11 runs (second section, below). **measured**
   - It needs a test that can fail, which means one on Windows itself. The `windows` job has zig but no OpenSSL, so it cannot link `net.c` today (thread 0 knows: project memory names it as open). The Linux job already builds and caches `build/openssl-win`; `actions/cache` can restore a cache across systems (`enableCrossOsArchive`), which would let the `windows` job build and run a small `net.c` test (a local server that sends and closes, as `srv.py`; no database needed). Whatever the route, the plant "FD_CLOSE forgotten" must be caught there and not under Wine.

## Same push (small)

2. **A write wake can be lost: the flush comes before the reset.** `io()` calls `net_flush` and then `net_read`. If the `send` would block and the socket turns writable before `net_read`'s `WSAEnumNetworkEvents`, the reset clears FD_WRITE; Winsock signals it again only after another `send` that would block, and nobody sends. The queued bytes stay.
   - `wwake.c` is that sequence with the gap widened by a pause. Under Wine: with the reset after the socket turned writable, "bytes still queued, the socket is writable, and no wake for 5 s" (2 of 2); with the reset before, the wake comes (2 of 2). **measured, Wine**
   - On the Windows runner the first version of the probe never got a `send` to block: 64 MB and then 9 more bytes were taken at once with the server reading nothing (10 of 10). A second version that keeps sending until one blocks shows the stall there too, 5 of 5 (second section, below).
   - With the unmodified client I did not get a stall (the `big.c` runs above): one `send` takes a whole batch, so a `send` blocks only for a second message while the first drains (a cancel right after a very large batch), and the gap is microseconds. So this is a correctness hole, not something Davy will meet this week. **hypothesis** for how rare.
   - Fix: reset first, then send. For example `net_read` on Windows flushes after `woke()` (`if (woke(c) || net_flush(c)) return -1;`), so a writable socket after the reset keeps its wake. One line; add a plant if a test can hold the socket full.

3. **The Windows wake rules have no model.** CLAUDE.md asks for a TLA+ model of a timing question, with the property stated first and a broken variant that fails. The PR's argument is that SqlRun.tla still holds because the order of the bytes is unchanged; that is true, and it is not the question. The new mechanism is one event for connect, read, write and close, whose records a reset clears and which only a `recv` or a blocked `send` arms again. Findings 1 and 2 are both states of that mechanism the prose did not reach. Asked for: a small model (socket: data waiting, close arrived, room to write; event: set or not; the records; the client's steps reset, recv, send) with the properties "data or a close that has arrived is read in the end" and "queued bytes are sent in the end", and today's two orders as the broken variants.

## Notes (not blocking)

4. **Nothing in CI makes a Windows login.** My plants in the Windows login pass every check (`make win WIN=sql` and `make test TESTS=sql` exit 0 with each): LOGIN7 without the INT_SECURITY flag (both systems), the SSPI token's length left out of LOGIN7, the server's token answered with a prelogin message instead of an SSPI one, the SPN built from the short name. Three more outside the login also pass: `net_read` never resets the event (the loop then spins), `tds_cancel` without its flush (the PR's two flush plants cover `send_msg` and `pg_query` only), and WSAENOTCONN not taken as still connecting. The test's only Windows-login check is the refusal off Windows. The evidence is by hand: the lab runs above and in the PR, and Davy's NTLM run. Two things would make it repeatable:
   - `lab.sh`, its Dockerfile and `krb5.conf` belong in the repo (for example `src/sql/lab/`), with the one command that runs the login through them; today they are only in the project files.
   - A CI job that runs the lab (thread 0's; it needs a Wine with krb5, a 1.5 GB download) is the real answer. Until then, a change to `net_sspi`, the 0xED case or LOGIN7's SSPI fields should come with a lab run in its PR text.

5. **The Windows login runs before the server is known to answer, and it blocks.** `tds_open` calls `net_sspi` right after starting the connect. SSPI's calls are synchronous; for Kerberos the first one asks the domain controller for a ticket. Measured under Wine: about 10 ms more than a SQL login when the controller answers; with the controller paused and no ticket for the server cached, `tds_open` had not returned after 120 s (1 run) and after 900 s (1 run), and the editor would be frozen for that time. Wine's Kerberos is MIT's, so Windows's own waiting time is a **hypothesis** (it falls back to NTLM after its own time-outs). Two cheap improvements, neither blocking: make the first token when the prelogin reply arrives (the server then is known to be reachable, so an unreachable server never costs SSPI's time), and say in `tds.h` that `tds_open` may block for the domain controller. The name lookup (`getaddrinfo`) blocks the same way; PR 133's review noted it.

6. Small things:
   - `net.c`'s `#define H(fd)` is `src/loop/win.c:48`'s, letter for letter. A one-line macro is below `make dupes`' sight; if loop.h ever gets a name for it, use that.
   - `say()` uses `FormatMessageA`, whose text is in the system's ANSI code page: on a Windows that is not English a message with an accented letter lands in `err` as bytes that are not UTF-8. `FormatMessageW` and a conversion, or `FORMAT_MESSAGE_FROM_SYSTEM` with language 0x409, would avoid it. **hypothesis** (not run on such a system).
   - `roots()` leaves OpenSSL's error queue as `d2i_X509` left it if a certificate in the store does not parse; `fail()` and `net_shake` then report the oldest error, which may be that one. `ERR_clear_error()` after the loop. **hypothesis** (the test store has no such certificate).
   - `tds_open` puts the SSPI token's length in LOGIN7's 16-bit field with a comment that Windows's MaxTokenSize is 48,000. The registry allows 65,535; `off + sp.n` above 65,535 would also set the next field's length. A refusal ("Windows login token too long") costs one line.
   - `src/tools/check.sh` (package 15's) is edited here; the comment says thread 0 agreed. It follows from `wincc` gaining src/sql, and the check fails without it, so it is right; the tools thread should hear of it.
   - `src/sql/README.md` still says "SQL login" only and does not list `check.sh`, `openssl.nix` or the Windows login.
   - The PR text counts "7 new plants"; the file has 7. Its "CI was green at 09dfb14" is two heads back.

## Second section: the Windows runner's later run (2026-11-24, run 45383924269, same head)
