## Findings that block the merge

**1. Does not build on current main.** `uni_width` changed in package 3 (PR
12, merged): it now takes `(s, n, i)` and counts a whole cluster.
`src/tools/pick.c:580` still calls `uni_width(cp)`. Repro: merge PR 18's head
into the PR head, `make compilers`. GitHub shows the PR as conflicting, so CI
has never run on it (0 check runs). After the merge the whole check has to run
again, and `text()` in pick.c should be read again against the cluster rules
(`thread-0/grid-clusters.md`).

**2. oil: an entry line whose name is only `/` becomes an action on the
directory itself.** oil.nvim reports "No filename found". oil.c tests for the
empty name before `parsedir` strips the slash (`oil.c:260`), so the line
passes and the entry is copied or moved to `/tmp/oc/` (the directory's own
path, an empty name). Repro: `oil-differ.txt` cases 7018407 and 1069
(`build/san/test_tools_oil - < reviews/pr-23-repro/oil-differ.txt`); 154
fresh cases hit it. (measured)

**3. oil: a link whose target ends in `/` is rendered with `//`.** `ln -s sub/
x` shows as `x/ -> sub/` in oil and `x/ -> sub//` in oil.c (`oil.c:156` adds a
slash for a link to a directory without looking at the target). 60 of 494
cases with such links differ. Saving the unedited buffer is still a no-op
(`linkslash.c`: 0 actions), so this is the display only. Repro:
`oil-differ.txt` case 1002. (measured)

**4. Signed overflow (undefined behaviour) on typed input, and no fuzzer.**
- `match.c:201` (`num`): the prompt `a.c:99999999999999999999` overflows
  `long`. Under the test build's UBSan the editor aborts.
- `oil.c:244`: an id line `/28888888888888888888888 x y` does the same.
- `pick.c:252,254` parse rg's line and column the same way (rg's output, so
  less likely).

Repro: `fuzz_match.c` and `fuzz_oil.c` stop on these in under a minute. The
package has no `tests/fuzz_tools*.c`, though it parses typed text and file
names; CLAUDE.md asks each package to add its fuzzers. Please add both (mine
can be taken as they are) and a plant for each.

**5. `oil_list` has no test.** The oil test fills the cache from the
recording's `K` lines through `oil_entry`; nothing calls `oil_list`. Three
plants in it survive (measured: `extra-plants.sh` runs `extra-plants.txt`
through `tools/planted.sh`, 7 plants, all NOT CAUGHT, 1 run):
every entry typed as a file; names starting with `.` skipped; entries that are
gone kept. A test that lists a real scratch directory and compares the render
with the oracle's `R` lines would cover it. Also surviving: the natural-order
cut-off at 5,000 entries, and "Cannot move or copy parent into itself" (see 9).

**6. The buffers picker does not follow snacks and has no test.** The PR text
says the buffers picker is checked against snacks; `test_tools_pick` only
opens smart and grep.
- Order with an empty prompt: snacks lists the last used buffer first
  (`sort_lastused`); `buffers()` walks `e->bufs`, which `core.h` says is by
  number. With four buffers opened in turn snacks gives `docs/a.md |
  src/core/core.c | README.md | Makefile`, pick.c gives them in number order
  (`buffers.lua`, `pick_probe buffers`; ref/core.c has one buffer, so the
  probe links the others in by hand). `Buf` has no last-used time, so this
  needs a header ask to thread 0.
- The matched text: snacks' is `"<nr> <path> <filetype> <buftype>"`
  (`3 /tmp/pp/src/core/core.c c `), pick.c leaves the filetype out. So ties
  break differently (prompt `e`: snacks `Makefile, core.c, README.md`, pick.c
  `Makefile, README.md, core.c`), and a prompt that matches the filetype
  (`markdown`) finds nothing. The same text is used for buffers in the smart
  picker.

This cannot show with ref/core.c's single buffer, so I would accept it being
moved to a later part, if the PR says so, the header ask is made, and
`tests/plants/tools.txt` gets a buffers plant when the test comes (a plant
that empties every buffer's text in the buffers picker passes all three
tests today).

## Findings that do not block

**7. oil: a new entry with an empty path part (`sub//`, `a//b`).** oil.nvim
answers "Detected cycle in desired paths"; oil.c creates `/tmp/oc/sub` and
then `/tmp/oc/sub/`. `oil-differ.txt` case 7002259. (measured)

**8. oil: two brace groups in one name.** `p{1,2}{3,4}`: oil.nvim creates
`p11` and `p22` (its `gsub` puts the same alternative in every group); oil.c
creates `p1{3,4}` and `p2{3,4}`. `oil-differ.txt` case 1076. (measured)

**9. oil: the "parent into itself" message.** oil.nvim says "Cannot move or
copy parent into itself: oil:///tmp/op/sub -> oil:///tmp/op/sub/deep/sub";
oil.c says only the first part. No recorded or fresh case reaches it (0 in
about 13,500), because it needs a buffer two levels down; `parent.lua` and
`parent.c` reach it. (measured)

**10. A `g` typed in the prompt's normal mode outlives the picker.** `key()`
keeps it in a static. Esc, `g`, CTRL-C, open the picker again, Esc, `j`: the
`j` is swallowed (`pick_probe g`; the control `pick_probe show DIR "~j"` moves
the cursor). (measured)

**11. More than 16 terms match nothing.** `a a a ... a` (17 times) on `abc`:
snacks scores 714, match.c 0. `match.h` says so; the prompt can hold it (33
bytes). (measured)

**12. Live grep does not split rg arguments.** `pick -- -g*.md` in snacks
greps `pick` in the Markdown files (README.md, docs/a.md); pick.c searches for
the whole prompt and finds nothing. pick.c's comment says "not kept"; the PR
text should say it too. (measured)

**13. Speed with many files** (100,000 files, `pick_probe time`, -O2, 5 runs):
a key in the prompt spends 12 to 26 ms inside `tools_key` (rematch of every
item); filling the list takes about 240 ms inside callbacks (range 231 to
304), the worst single callback 7 to 12 ms. With 2,000 lines in the frecency
store the fill takes about 950 ms (933 to 1,047, 3 runs) and one callback up
to 42 ms, because `fr_find` is a linear search with a `strlen` per entry, done
once per item. snacks matches in the background. None of this is near a 2 ms
frame; it should be on the list for the phase 0 latency gate, and `fr_find`
wants a sorted table or a hash. (measured)

**14. No finder, no message.** Without `fd` and `rg` the smart picker shows
only the buffers and grep shows nothing, silently; snacks reports "No
supported finder found". snacks also tries `fdfind` (Debian's name) and
`find`. (measured)

**15. `test_tools_pick` needs `rg`.** Neither CI's apt line nor `tools.nix`
installs it. Whether GitHub's ubuntu-24.04 image has it is a **hypothesis**
until CI runs on this PR; without `rg` the test fails (measured). Ask thread 0
for `ripgrep` in the apt line.

**16. The frecency store is never read in a test.** The test starts without a
store, so `fr_load` parses nothing: a plant that reads every deadline as 0
passes (`extra-plants.txt`, measured, 1 run). Frecency with a history is not compared with snacks
at all (hypothesis that it matches). Two known differences: snacks counts a
visit on every BufWinEnter, pick.c only when the picker opens a file; snacks'
cwd bonus is a plain prefix test (`/home/a` also matches `/home/ab/x`), pick.c
asks for a `/` after it.

**17. Small.**
- A new entry longer than 4,095 bytes with path parts is cut silently
  (`oil_long.c`: 5,000 bytes give 1 action for a path that was never typed);
  `url + u` is formed past the array before `snprintf` refuses.
- At 1 row, or 4 columns or fewer, `tools_draw` puts the cursor outside the
  grid (`pick_probe tiny`); no memory error.
- The prompt's normal mode has `h l 0 $ i a I A j k gg G q` only (no `x`,
  `dd`, `w`, `b`): snacks' prompt is a Vim buffer. Smart has no "recent"
  source yet (the PR says so).

- The oil action order (`enforce_action_order`, the move cycle through a

## New findings

**A. The oil test depended on the order `readdir` returns (fixed in b0e5d6b).**
After an apply the test lists the directory again; entries new to the cache
got their ids in `readdir` order, the recording has oil.nvim's. On CI's file
system two cases differed. b0e5d6b rewrites ids above the largest known one to
`n` on both sides before comparing, and adds a plant so the rewrite cannot
hide a reused id. The rewrite does not weaken the check: ids of entries the
recording knows are still compared, and the plant fails. (measured)

**B. The branch carries PR 15's loop from before its review.** See the verdict.

**C. `oil_apply`, for part 2, before `tools_write` calls it** (it is not
reachable from the editor in this PR; `tools_write` still refuses):
- Deleting a listed directory that has since been replaced by a symlink to a
  directory deletes the contents of the link's target (`apply.c swap`:
  "/tmp/oa/keep/precious IS GONE"; measured, 1 run). oil.nvim's code reads the
  same to me (hypothesis, not run against oil). The cache says OIL_DIR, the
  file system says link: `lstat` before the recursive delete and unlink a link.
- Copying a FIFO never returns (`apply.c fifo` timed out at 5 s; measured).
  oil.nvim copies on libuv's thread pool, so its editor stays alive.
- Any copy is synchronous in the one event loop: a large file stops the editor
  for as long as the copy takes. This wants a decision (chunks per loop turn,
  or a child `cp`) and, being a timing question, a TLA+ model.

**D. CI at b0e5d6b is red in `test_tools_pick`, because CI's image has neither
`fd` nor `rg`** (finding 15, no longer a hypothesis). The job log shows the
`find` order (`./Makefile|...`) against the recording, which was made with
`rg`. Reproduced here with a PATH without `fd`, `fdfind` and `rg`: the same
output; with `rg` on that PATH the test passes (measured, 1 run each). Live
snacks with only `find` gives exactly pick.c's list, so the code is right and
the test's environment is not. `ripgrep` has to be in CI's apt line (thread 0's
file) before this PR can be green.
