## Findings

### 1. (required) Emphasis matches past the 64th on a line are forgotten, so a script inside them is raised

`emphasis()` records each match in `ea/ez` only `if (*ek < 64)`; `scripts()` uses that list to leave a script inside emphasis or verbatim as typed. From the 65th match on a line, a script inside one is raised, which Org never does. Nothing says so (not in the known differences, not in the header).

Repro (`directed/emph65.org`, `org_drv_big.c` = the driver with room for 4,096 spans so the driver's own cap of 64 is out of the way):

    '*a* ' * 65 + '=x^{2}=\n'
      org:  a a ... a x^{2}
      ours: a a ... a x²

With 63 matches both agree. **measured**, 1 run each (deterministic). Fix: remove the limit (the author picks how; matches can overlap, so a single "last match" is not enough), or, if a limit stays, list it as a known difference and give it a plant.

### 2. (required) orgfx_conceal walks from the headline above for every line: a frame over the 2 ms gate in a long section

`orgfx_conceal` calls `scan_at(f, pl)` per line, which steps `meta()` from the line's headline (or the buffer's start). `paint` does that once per call for a whole window, so faces pay it once a frame; conceal pays it once a line. Measured with `tail.c` / `tail2.c` (no sanitizers, -O2), 50 lines at the end of a buffer without headlines:

| buffer | faces of ~60 lines | conceal of 50 lines |
|---|---|---|
| 10,000 lines `a` | 0.08 to 0.14 ms | 3.74 to 4.84 ms, median 4.2 (10 runs: 5 faces first, 5 faces and conceal interleaved per line) |
| 100,000 lines `a` / `*a` / `#+a` | 0.8 to 3.3 ms | 64 / 41 / 142 ms (1 run each) |

Interleaving faces and conceal line by line does not help: conceal asks for the line above, which is before `f->c`. DESIGN.md's frame gate is 2 ms. How often Davy has thousands of lines under one headline is a **hypothesis** (preambles, long notes sections), but the cost is a repeated walk that a cached scan state (as `f->c` does for faces) removes; CLAUDE.md's "no clock cycle wasted" asks for it. Please add a gate to test_org's frame test: 50 consecutive lines' conceal at the end of a long headline-less buffer, under a bound that the per-line walk breaks.

### 3. (required) Three planted bugs survive every check: generator gaps

Of my 16 plants, 11 are caught by `org-conform` (show), and these 3 survive `org-conform`, test_org and test_syntax_org, though each changes what Org shows on a short directed text (repro `survivors/`):

| plant | survives because | text that catches it |
|---|---|---|
| `[` dropped from `post()`'s closer set | no `[` in MATH | `*a*[x] /b/[y]` |
| `%%(` dropped from `separate()` | no diary sexp line | `a *b\n%%(x) c* d` |
| a table rule `+-+` taken at 2 characters (`x >= b + 2`) | no `++` line | `++\n+a+ b` |

Each needs a token in `gen_show` (for example `[`, a `%%(x) ` line start, a `++` line) and a plant line in tests/plants/org.txt. Two more plants (brace depth 4 instead of 3; mixed flat and nested groups accepted) change nothing I could find shown: a script holding a `{` shows as typed anyway, since `{` has no Unicode superscript, unless it is a `\name{}` (`x^{\alpha{}}`). **Hypothesis:** the depth and group-kind rules in `braces()` decide only where a match ends, which then only moves the scan by one script; either name a text where they show, or keep them for being Org's regexp (my vote: keep, it is a transcription) and say in the comment that they rarely change what shows.

## Notes (not blocking)

- A. The 2 differences of 23,000: a script whose braces span a line, after a `#+begin_src` line with no end (`span-after-src-line.org`). Org takes display and invisible off the first line only, so the closing `}` on the next line stays hidden; ours shows it, as the listed known difference says ("as typed when its braces span lines"). The oracle's `shown()` unhides only a run's `^`, `{` and `}` when the run is whole, so a run Org cut in two is compared. Either count such texts as not compared (as `long_script` does) or list the class; 1 in 11,500 texts.
- B. The driver's cap of 64 spans per line means a line with more spans is compared wrongly (`directed/ent70.org`: 70 `\alpha` show 6 as typed). Only my directed texts reach it, but the core's eventual caller must size `cap` from the line's bytes; worth one line in syntax.h ("at most one span per byte").
- C. Nothing draws `syntax_conceal` yet; the core's drawing is a later step. Fine as thread 0 agreed, but until then Davy sees no change, so the PR body should say so.
- D. `script()` and `entity()` are two more hand-written binary searches beside `in()`; `script()` is shorter with libc `bsearch` and a comparator on `c` (as src/syntax/tsql.c and src/undo/undo.c do), about 4 lines saved.
- E. entities.h and scripts.h say "generated" but the generator is not in the repo. `org_conform.py -s` already builds the scripts table; a few lines there (or a make target) that print both headers would let a later Org or Unicode update be regenerated and diffed. The oracle builds its script table from the running Python's Unicode data: a CI Python with another Unicode version could report differences that are not bugs (**hypothesis**; Python 3.13 here matches scripts.h exactly).
- F. syntax.h's new comment has one line far past the file's width ("x^{2} is three spans ... sub- and superscripts in").
- G. PR 98's notes: the property drawer's `:END:` column (one condition, the redundant `lit(":END:")` gone), the unclosed repeating stamp on a planning line (test, three generator lines) and the sibling's same-parent rule (test) are in, each with a plant and a test that fails without it. The fourth note was the PR 98 body's wording, not code. The PR 98 report rides along unchanged.
