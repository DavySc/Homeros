## Findings at ca6093e

### 1. Blocking: CHAR(65) and NCHAR(66) are keyword blue in the screenshot, not function magenta (measured)

The PR's new rule (`after_name`, `name_before`, 36 lines in tsql.c) makes
CHAR and NCHAR a keyword after a variable and a function elsewhere, and
the directed case expects `= CHAR(65)` as `FFFF`. In the screenshot's line
2, `CHAR(65)` and `NCHAR(66)` have the same blue as `DECLARE` and
`char(10)`: no pixel of the function colour (201,117,213) is in that line.

Reproduce: `python3 reviews/pr-64-repro/colours.py
/mnt/project-files/syntax/ssms-screenshot-2.png` (1 run; line 2 prints
only K, ., N and o; line 3's CURRENT_TIMESTAMP prints F, so the reader
does tell the two apart). Counted by hand too: the box of `CHAR` in line 2
holds (57,135,214) and (86,156,214), the box of CURRENT_TIMESTAMP holds
(201,117,213) 86 times.

So SSMS colours CHAR and NCHAR by word list alone, as a keyword, wherever
they stand. The fix is the one the PR made for IDENTITY: drop the function
class from `char` and `nchar` in tsql_words.h, and delete `after_name`,
`name_before`, the line in `word_face`, the changed comment, the two
"hypothesis" test lines and the four new plants. That is shorter and has
no rule that is a hypothesis (CLAUDE.md: the shorter solution that meets
the requirement wins; SSMS is the reference).

### 2. Blocking: `at` is keyword blue, the PR makes it plain (measured)

Line 3, `at datetime`: `at` has (86,156,214), the same as `datetime`;
`id` before it is plain. colours.py line 3 prints `405:K` for it. The PR
sets AT's class to 0 and expects plain. AT should stay a keyword (class 1,
as on main).

### 3. Blocking: OPENJSON is keyword blue, the test expects a function (measured)

Line 9: `CROSS APPLY` is grey (the PR has that right), `OPENJSON` is blue
(colours.py: `182:K 208:K 222:K 240:K`). The directed case expects
`FFFFFFFF`. OPENJSON should lose its function class. Whether OPENQUERY,
OPENROWSET, OPENXML and OPENDATASOURCE follow it is a hypothesis; say so
in the word list's comment or ask Davy for a line.

### 4. Goes away with finding 1: the walk back over spaces costs 64 to 82 ms a frame behind 1 MB of blank lines (measured)

`after_name` steps back over spaces one byte at a time with no bound, and
`tsql_byte` reads a 4,096-byte window forward from each byte it is asked
that lies before its window. `reviews/pr-64-repro/blank.c`: a text of
1 MB of newlines and then `char(10)`, `tsql_faces` on the last 200 bytes,
best of 20 calls, 5 alternating runs: 64.1 to 81.8 ms (median 72.8) with
`char(10)`, 0.48 to 0.53 ms (median 0.51) with `print(10)`. 64 KB of
blank lines: 3.8 ms (1 run); 4 MB: 304 ms (1 run). The frame budget is
2 ms. If any look-behind stays, it needs a bound, as `name_before` has
(40 bytes).
