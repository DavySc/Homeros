# Review of PR 49: org timestamp, planning and clock readers, head 1cf5b69

Independent review against the contract in `include/org.h` (`OrgTs`, `org_ts`, `org_planning`, `org_clock`: each "as org-element reads it") and against `org-element.el` of Org 9.8.7 in Emacs 31.1 (`tools.nix`). Everything below was run by the reviewer on one machine (4 cores, gcc 13.3, clang 18.1). The reviewer's drivers are in `reviews/pr-49-repro/` (README there). Tags as CLAUDE.md asks.

**Verdict: approved.** The three readers agree with Org everywhere I looked, including `org_ts` at every position of 28,000 random texts, which the PR's own checks never compare with Org. Two notes for the next org PR (section 3); neither is a wrong result. Nothing here needs Davy.

## 1. Does it read what Org reads?

| Check | Result | Tag |
|---|---|---|
| `make org-conform` (the PR's generator: planning and clock lines, planning keywords run together, diary sexps, ranges, repeaters, warnings, odd brackets) | 0 of 2,000 differ (seed 1); 0 of 20,000 differ (seed 1) | measured, 1 run each |
| `org_ts` at every byte against `org-element-timestamp-parser` at every character, `case-fold-search` t (`ts_dump.el`, `ts_drv.c`, `gen_ts.py`: 1 to 40 pieces from a pool of brackets, dates, times with hours 0 to 39, diary sexps, ranges, repeaters and warnings in both cases, `\r`, newlines, `é`); driver under ASan+UBSan with the text in an exact-size buffer | seeds 2 to 8, 28,000 texts, 69,409 timestamps found by Org: 0 differ, clean (hours 30 to 39 and the diary `39:30` piece joined the pool from seed 7) | measured |
| The same with 10- and 11-digit repeater values in the pool (seed 1, 2,000 texts, 4,864 timestamps) | 19 texts differ, all in the repeater value: `num()` holds a value at 9 digits, Org keeps the bignum (`+12345678901d` is 12345678901 in Org, 123456789 here) | measured, 1 run |
| `make test TESTS=org` | 38 texts agree with Org | measured |

By reading, each piece follows `org-element.el`: the raw value ends at the first `]` or `>` (so `<%%(a]b) 9:00>` ends after `]`, as in Org), the time range is searched in the start part only, the repeater and warning in the whole raw value including the range's second stamp, `org-parse-time-string` takes the first `org-ts-regexp0` match (always at the date), `[012]?[0-9]` has one reading at each place, planning's keyword search stops at the node's end but its timestamp does not, a keyword whose stamp fails clears an earlier one, and the clock's `=> ` search stops at the first one.

The value cap is the only difference found. It needs a repeater, deadline-repeater or warning of 10 or more digits, which no agenda will hold; the code's comment says it is meant ("held at a bound instead of growing"). The header does not say it: worth one line in `include/org.h` the next time thread 0 touches it.

## 3. Notes for the next org PR (not blocking)

1. `org_ts` itself has no check against Org in the repository. It shares `ts()` with `org_clock`, so only its own line (case folding on) goes unchecked today, and section 1 shows it right; but the paragraph timestamps that will call it (agenda, display) depend on it. `reviews/pr-49-repro/ts_dump.el` and `ts_drv.c` are a ready oracle to fold into `org_conform.py` with a plant (the first one above).
2. The generator never writes a diary time whose first hour digit is 3 or more, so the `[012]?` bound in `hm()` is unchecked (second plant above). One more choice in `org_conform.py`'s diary times (` 39:30-10:00`) and that plant catch it.
