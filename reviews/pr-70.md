## Findings to fix

### 1. Discarding staged changes fails while any file is unmerged (regression)

`apply()` now runs `git update-index -q --refresh` before `git apply
--index`. With an unmerged file in the index that command prints `a.txt:
needs merge` and exits 1, so the write stops with "git failed" and the
staged change stays. On main the same keys discard it.

**measured**, 1 run each side: `sh reviews/pr-70-repro/f1.sh DRIVE REPO`
(a merge with a conflict in a.txt, a staged change in b.txt, `x` `y` on
b.txt under Staged changes). main: b.txt discarded. PR: `[msg] git failed`,
`M  b.txt` still there. With `--unmerged` added to the `update-index`
command the PR discards it (1 run).

### 2. `git_counts` reads past the end of the path for an event on the work tree's own directory

os.c now builds the path of an event without a name as `dir` (main: `dir/`).
For the work tree's top directory that is exactly `r->top`, and
`rel = path + tl + 1` points one byte past the terminator: what is tested is
whatever the previous event left in `path[]`.

**measured**, 1 run each side: `sh reviews/pr-70-repro/f2.sh DRIVE REPO`.
`touch x.o; touch .` with `*.o` ignored: main moves the version by 1, the PR
by 0, because it reads the stale `x.o` and calls the event ignored. `touch .`
alone moves it on both. The effect here is harmless; the read is outside
the string. Building the path as main did (`"%s/%s"`) gives 1 again (1 run).

### 3. The work tree diff (`d w`) no longer shows renames (regression)

magit runs `git diff HEAD`; `diff.renames` is on by default there.
`git diff-index -p HEAD` is plumbing and does not detect renames, so the
PR's claim "the output is the same" does not hold for a staged rename.

**measured**, 1 run each side: `sh reviews/pr-70-repro/f3.sh DRIVE REPO`
(`git mv a.txt z.txt`, then `d w`). main: `renamed    a.txt -> z.txt`, 1
file changed. PR: `deleted    a.txt` and `new file   z.txt`, 2 files, 24
lines. With `-M` added to `diff-index` the output is byte for byte `git
diff HEAD`'s (1 run) and the view shows the rename again (1 run). No trace
covers a rename in this view; one should, with a plant.

### 4. `src/git/check.sh` fails on a fresh Wine prefix, so in CI and in every plant

`tests/test_git_win.c:122: CHECK(GetFileAttributesA(kept) !=
INVALID_FILE_ATTRIBUTES) failed`: on the run that creates the prefix, the
trashed file is not in `$XDG_DATA_HOME/Trash/files` (it is nowhere on the
disk). The next run on the same prefix passes.

**measured**: fresh prefix 4 of 4 fail; the same prefix again 4 of 4 pass
(`sh reviews/pr-70-repro/fresh-prefix.sh`). With `wine wineboot -i;
wineserver -w` before the test, a fresh prefix passes 2 of 2
(`fresh-prefix.sh boot`). **hypothesis** for the cause: the Wine server
started while the prefix is made does not have the script's
`XDG_DATA_HOME`.

Consequences: `make check` fails at `make win` in a clean checkout, which is
what CI and the merge train have. `tools/planted.sh` copies the tree without
`build/`, so each of the 7 `win WIN=git` plants runs on a fresh prefix and
is "caught" by this failure (it matches planted.sh's `CHECK\(`), whatever
the plant does. The PR's "each caught, 1 run each" for those 7 proves
nothing until this is fixed; they need a rerun.

### 5. On Windows one `git_drain` takes one batch, so a write can act on a repository it did not show (Git.tla ActsOnSeen)

Linux's `git_drain` reads until the queue is empty. win.c's takes the one
completed `ReadDirectoryChangesW` result per root and arms again; changes
that arrived meanwhile complete the new read at once and are not taken.
write.c's gate is one `git_drain` and then `r->w.ver != r->ver`.

**measured** under Wine, 5 of 5 rounds
(`reviews/pr-70-repro/drain_win.py`): a change under ignored `build/`, 200
ms, a change to `a.txt`, 200 ms, then `git_drain`: the version does not
move; a second `git_drain` moves it by 1. So a write queued at that moment
passes the gate with a.txt changed after the view was read. Real Windows
completes the first read with the first change in the same way
(**hypothesis**, by Microsoft's description of the call; not run). Fix:
loop on a root until its result is `ERROR_IO_INCOMPLETE`. A check and a
plant belong with it; the probe above is most of the check.

### 6. A new 50-token copy: `make dupes` will fail once PR 66 is on main

`on_inotify` (os.c:79) and `on_change` (win.c:92) are the same function.
**measured**, 1 run: PR 66's `tools/dupes.py` on this tree reports `FAIL
copied: src/git/os.c:79 src/git/win.c:92`, and `tests/dupes-known.txt` may
only shrink. With `on_change` removed the report is gone (1 run). One
callback in git.c that both halves pass to `loop_watch` is the fold.

### 7. The Windows half watches nothing for a linked work tree's common directory in any check

**measured**, 1 run: with `root(r, r->common)` deleted from `git_watch`
(win.c), `src/git/check.sh` still passes: `test_git_win` and the 61 traces
with the work tree check. The second root is new code that no check
reaches; it needs a check and a plant (a ref written in the common
directory of a linked work tree must move the version).

## Smaller, may be folded in or listed as owed

8. **Shorter**: `git_repo`'s five-line `#ifdef` around `_putenv` and
   `setenv` can be one line, `putenv((char *)"GIT_EDITOR=" EDITOR);`.
   **measured**: compiles under `-Wall -Wextra -Werror -std=c17` with gcc,
   clang and `zig cc -target x86_64-windows-gnu`, and sets the variable (1
   run each). Note what the move changed: every child of the editor (rg,
   later the language servers) now inherits `GIT_EDITOR`, where main set it
   for `git commit` alone. Nothing in the tree runs a git through another
   route today (`proc_spawn` has one other caller, the picker's rg).
9. **Dead lines** left by the move: `#include <errno.h>` and `<time.h>` in
   write.c, `<unistd.h>` in git.c (each file compiles without, gcc, 1 run),
   and a doubled blank line in write.c.
10. `git_real` on Windows is `GetFullPathNameW`, which does not correct the
    letter case. **measured** under Wine, 1 run
    (`reviews/pr-70-repro/real_win.c`): a directory made as `RvMixedCase`
    and asked for as `rvmixedcase` comes back as typed. A file opened by a
    path typed in another case gets a `top` and a relative name that differ
    from git's, so its gutter signs match nothing and the same repository
    can be opened twice (**hypothesis**, not run in the editor). Neovim's
    realpath on Windows (libuv) is `GetFinalPathNameByHandleW`, which
    returns the stored case.
11. `git_drain` (win.c) reads `n` after a `GetOverlappedResult` that failed
    for another reason than `ERROR_IO_INCOMPLETE`; `DWORD n = 0;` makes that
    a change, as the comment says an empty batch is. Not reproduced:
    **hypothesis**.

For thread 0, not this PR: each `win WIN=git` plant downloads MinGit again
(planted.sh does not copy `build/`), seven downloads and a network
dependency inside `make planted`; a fixed-output fetch in `tools.nix` with
the same hash would cache it. `pick()` and the runtime-directory lines are
now in a fourth `check.sh`.

  `gitint.h` only.
- `git diff` does write the index where the PR says (**measured** by the
  PR's own `lock_check`, which passes with `diff-files`; the plant that puts
  `diff` back was not rerun here).
- The two shell scripts as a git alias fit `cmd_sh`'s 2048 bytes (the longest
  is about 700).
- The watch, the Recycle Bin and the traces do pass under Wine once the
  prefix exists, as the PR says.
- Nothing in the PR touches Davy's Windows machine; MinGit under Wine is
  what he approved.
