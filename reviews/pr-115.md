## Findings

### A. Surround of `v$` on the last line deletes the buffer's final line break (blocking)

`snip_insert` clamps the area's end to `text_len()`, which still includes the buffer's
last `\n`. Measured (1 run each, `pr-115-repro/test_zprobe115.c` and `test_zprobe115b.c`, run as `make test TESTS=zprobe115b` from `tests/`):

| step | buffer text | `core_lines` | file on disk |
|---|---|---|---|
| keys' own `v$cX<Esc>:w` on `ab` | `X\n` | 1 | `X\n` |
| surround `wrp` (`begin\n\t$0\nend`) after `v$` on `ab` | `begin\n    ab\n    \nend` | **3** (4 lines shown) | |
| `:w` | same | 3 | `begin\n    ab\n    \nend` (**no final newline**) |
| `Go<Esc>` | `begin\n    ab\n    \n\nend` | 4 | `o` opens the new line **above** `end` |

Same with `aé` (multi-byte last character). Neovim keeps the last line break for `v$c` on
the last line (`jv$cX` on `abc\ndef\n` gives `abc\nX\n`, measured). Fix: the area never
holds the text's last byte, e.g. `if (z >= text_len(t)) z = text_len(t) - 1;`, and a case in
`insert()` for it. My plant "an area past the text's end is not clamped" shows the current
clamp is not tested either.

On a line that is not the last, `v$` takes the line break and the next line joins `end`
(`enddef`): that is what Neovim's `v$c` does (`v$cX` gives `Xdef`, measured), so it is right.

### B. With a prompt typed, the picker forgets the file's group (should be fixed in this PR)

`rank()` puts the file's group first for the popup and for the picker's empty prompt, but
once a letter is typed the picker sorts by `match_score` alone (pick.c `rematch`/`cmp`).
Measured with the real catalogue, 7 file names x 10 prompts typed into both:
**23 of 70 first picks differ** between the popup and SPC i s. Examples:

- `x_task_a.sql`, `s`: popup `task-update-selected`, picker the helper `set @error_text =`.
- `x_trigger_a.sql`, `set`: popup `iot-view-insert`, picker `prc-next-or-stop`.
- `x_default_a.sql`, `if`: popup `def-initial-fill`, picker `exists-guard`.

The author's notes list this as a known gap. It is the PR's feature (Davy: the group comes
from the file name), SPC i s is the path Davy reaches for with a prompt, and two orders for
one catalogue is two mechanisms (Davy, 2026-11-21). One way: `rank()` stays the only order,
and the picker asks it with the prompt (snip_get with the query, thread 0 for the header);
another: pick.c's sort keeps `add()` order between equal group classes. Author's choice.

### C. CTRL-V surrounds the text from corner to corner (nit)

`abc\ndef`, `<C-v>j`, `wrp`: `begin\n    abc\n    d\nendef`, the block's columns are not
used (measured). Treat CTRL-V as `V` (one condition) or say in snip.h that it is charwise.

### D. `V` from a line of blanks indents `begin` one short (nit)

`    \n    b`, `Vj`, `wrp`: `   begin\n         \n        b\n    end` (3 spaces before
`begin`, measured). `core_first_nonblank` backs up onto the last blank outside Insert mode,
while `expand()` counts all 4 as the base.

### E. The list is ranked again on every redraw (nit)

`snip_get(e, 0, ...)` re-runs `rank()`, and `tools_draw` and `preview` call it for the first
row: counted 2 `rank()` calls to open the picker and **10 more for 10 redraws**
(`pr-115-repro/test_zcnt.c` with `rank-counter.diff`, 1 run). Each row also calls `body_of`,
now a `strcmp` scan of the catalogue (it was a pointer compare). Rank once in `tools_pick`
and let `snip_get(i)` only read `items[i]`; keep the Snip in the item to drop the scan.

### F. `snip_insert` before any `snip_get` says "no snippet" (nit)

The catalogue loads in `snip_get` and the popup only; a first `snip_insert` returns -1 with
"no snippet wrp" (measured). SPC i s always calls `snip_get` first, so Davy cannot hit it;
load in `body_of`, or say it in snip.h.
