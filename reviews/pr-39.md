## The replace (fix 4)

`MoveFileExA(tmp, path, MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH)`
after `fflush` and `_commit` is the same mechanism as `file_save` in
src/file/win.c (temp file in the same directory, FlushFileBuffers, one
rename with write-through), with the same flags; `file_save` leaves out
REPLACE_EXISTING only where the file must still be new, which an undo file
never needs.  An undo file needs no identity check either: it is keyed by the
text's hash and a stale one is refused on read.

What the kill test shows is Wine's rename, which is Linux's.  That NTFS
replaces a name atomically across a crash is the same **hypothesis** as
DESIGN.md's "Save, Windows" row, to be measured on Davy's laptop in phase 1.
Neither the write-through nor the flush has a plant that can fail (both
removed, the check still passes: `extra-plants.txt`), as on Linux, where no
test crashes the machine either.

## Findings

1. **The hook can call a plant caught when nothing was checked** (fixed in
   this branch).  Make echoes the recipe, and the echoed lines hold `-Werror`
   and `echo "FAIL ..."`; planted.sh looks for `error` and `FAIL` in the log
   and drops only lines that start with gcc, clang or cc.  So every failure of
   `make compilers`, whatever the cause, counts as a catch, for the harness's
   compilers plant too.  Measured: with Wine off PATH all six plants above
   were "caught", the two that the check cannot see included; and a clean tree
   printed `FAIL test_undo_win (Windows, under Wine)`.  The recipe also sent
   Wine's stderr to /dev/null, which is where check.h writes the failed CHECK,
   and used package 9's Wine prefix without a display, which
   src/file/check.sh avoids on purpose.
   Fix (commit "Package 2: the Windows check reports only its own failures"):
   the recipe is `@bash src/undo/win.sh`, a script shaped like
   src/file/check.sh (tools checked first with exit 2, own prefix, own
   runtime directory, stderr kept).  With it: the PR's 3 plants and the magic
   plant are caught with the compiler's or the test's own line, the other two
   are NOT CAUGHT, and without Wine all six are FAILED OTHERWISE (measured, 1
   run each).
2. **Where the hook lives.**  It has to be part of `compilers`, not
   `make win`: planted.sh counts a compile error as a catch only for
   `compilers` targets, and two of the three plants are compile errors.  A
   prerequisite added from build.mk does that in two lines and stays in the
   package's directory, so I would keep it there for now; CLAUDE.md's build.mk
   sentence then needs "or a prerequisite of compilers" (thread 0).  The
   better end state is thread 0's: `compilers` builds the whole editor for
   Windows with zig once the Win32 backend's main is on main.  The trial zip
   is where these errors showed, and a per-package hook only covers undo.c.
   When that exists, this hook shrinks to the Wine run under `make win`.
3. **Non-ASCII file names** (not this PR's, follow-up for whoever wires undo
   files into the Windows editor).  The editor's paths are UTF-8 and
   src/file/win.c turns them into UTF-16; undo.c gives them to `fopen` and
   `MoveFileExA`, which read them in the ANSI code page.  Measured under Wine
   (code page 1252, 1 run, `name.c`): the undo file for `é.txt` is created as
   `Ã©.txt.un`.  It reads back, since both sides agree, so nothing is lost,
   and the PR is right to keep the two calls on the same kind of path.  The
   fix is `_wfopen` and `MoveFileExW` with win.c's conversion.  Nothing calls
   `undo_write` in the editor yet (grep of src/ and ref/).
4. **errno** (small).  A failed MoveFileExA always gives EACCES; win.c's
   `fail()` maps GetLastError (sharing violation, disk full).  No caller
   reads it yet.

Not findings: `MAGIC[]` is 9 bytes but both uses name 8; the parameter is
`n` in undo.c and `step` in undo.h, which C allows; `_commit` is
FlushFileBuffers on the handle (Microsoft's CRT documentation, not run here).
