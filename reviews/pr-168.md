Servers: SQL Server 2022 (mcr image) and PostgreSQL 17 in docker, as CI. Probes are in `reviews/pr-168-repro/`, built with `mk.sh TREE probe.c OUT` (ASan and UBSan, the Makefile's test line).

## What holds (measured)

- One thread: nothing new runs off the loop. The catalog's connection is a non-blocking socket the loop watches (`dial`, `catwake`), as F5's. No thread, no timer.
- One mechanism: `run()` and the catalog open through one `dial()`; `make dupes` is part of the check below.
- SQL Server `master`: 50 rows, the same count as `sqlcmd` gives for `INFORMATION_SCHEMA.COLUMNS`, in schema, table, ordinal order (`q2 list ms`, 1 run, compared by eye for the first 12).
- A large catalog (2,000 tables of 50 columns, 100,000 rows, 1 run each): read in 611 ms on SQL Server and 139 ms on Postgres; no loop turn longer than 11 ms (10 ms of which is the probe's own poll wait). The read does not hold up keys.
- fn NULL dropped 40 times at 40 different moments of the load, then one clean read: 50 rows, no sanitizer report (`q2 null`, 1 run).
- No message: a wrong password, a wrong Postgres password and a closed port all give 0 and leave `e->msg` (`q2 fail`, 1 run).
- With no connection for the folder a call costs 16.5 us (10,000 calls, sanitizer build): it opens the connections file each time, which is cheap enough.
- Plants: 38 of 38 `test_sql_editor` plants caught on f88dda11 (the PR's 6 and the re-aimed Ctrl-C plant among them), each against the test alone (`prun.py`). `test_sql_editor` passes 3 of 3 on 5c54708e and 1 of 1 on f88dda11.

## A. F5 on a host that cannot be opened shows an empty results split (blocking, regression)

`dial()` calls `db_close(d)` on failure, and `net_close` zeroes the `Net`, its `err` with it. `run()` then prints `db_net(&s->db)->err`, which is empty. `dial`'s comment ("d closed, its error set") cannot hold.

`q1` (a connection whose host is `nohost.invalid`, F5), 3 alternating runs each:

| | results split |
|---|---|
| base 0a7462b1 | `unknown host nohost.invalid` (3 of 3, both servers) |
| PR 5c54708e | empty line (3 of 3, both servers) |

The same loses "sql: too many watches". No test has an open that fails, so nothing caught it (plant 1 in `review-plants.txt`: not caught). Wanted: the message back, a test with an unknown host, and a plant.

## B. No columns on a case-sensitive SQL Server database (blocking)

The query names `information_schema.columns`, `table_schema`, ... in lower case. On a database with a case-sensitive collation SQL Server's names are case-sensitive:

```
create database cs collate Latin1_General_CS_AS
select count(*) from information_schema.columns
Msg 208: Invalid object name 'information_schema.columns'.
```

`q2 cs`: 0 rows (1 run; `sqlcmd` shows Msg 208, 1 run). Written in capitals (`INFORMATION_SCHEMA.COLUMNS`, `TABLE_SCHEMA`, `TABLE_NAME`, `COLUMN_NAME`, `ORDINAL_POSITION`) the same query returns the rows on that database and on Postgres, which folds unquoted names (1 run each through `sqlcmd` and `psql`). Wanted: capitals, and a test on a case-sensitive database.

## C. The first call can freeze the editor for seconds, and logs in before Davy asked (blocking)

The PR says the catalog "never blocks a key". The socket does not, but `dial()` starts with `net_open`'s `getaddrinfo`, which is synchronous. `q2 dns HOST` with a name server that does not answer (a laptop away from the server's network), in a private mount namespace:

- first `sql_catalog` call: 10.0 s (10,004 to 10,008 ms, 5 of 5 runs); with a name server that refuses at once: 1 ms.

F5 has the same wait on the base, but there Davy pressed a key that means "connect". Here package 19 will call at a word start, so the freeze comes while typing the first word in a .sql file under a `dir` line.

Two more things follow from dialling at the first call rather than at a login:

- The editor logs in to the server as soon as a word is typed in such a file, before any F5. SSMS's IntelliSense, the reference, only works in a connected query window.
- A read that fails is never tried again. `q2 late` (port closed at the first call, opened after, 3 of 3 runs): F5 then logs in and runs, the catalog stays 0 until fn NULL. No key calls fn NULL yet, and the failure shows no message, so the columns are silently gone for the session.

One change answers all three and is SSMS's behaviour: start the read when the buffer's own connection has logged in (its first F5), and start it again at a later login if the last read failed. The header's "with no connection, 0" already reads that way. What stays is a second `getaddrinfo` just after one that succeeded; passing the resolved address on would remove that too. If the author keeps the read at the first call instead, the lookup has to leave the key's path some other way, with the measurement.

## D. `:Connect` refreshes the catalog only in the buffer that happened to read it first (should fix)

The rows live in the first buffer that asked. `q2 share` (1 run; the code path has no timing in it):

- A reads `ms` (50 rows); a table is created; B, on `ms` too, runs `:Connect ms`: B still gets the old 50 at once. The same `:Connect ms` in A does re-read.
- A (the owner) runs `:Connect pg`: B's `ms` catalog is dropped with it, B gets 0 and reads all of it again (51).

Davy cannot know which buffer is the owner. Also the match is by name only: after an edit of the connections file, `:Connect ms` in a non-owner keeps the old host's columns. Simplest: keep the catalogs by connection in their own small array instead of in a `Sess` (three fields and the "first buffer" rule go), and let `:Connect name` drop that name's.

## E. The tests see little of the new code

My 13 plants on f88dda11 (`review-plants.txt`, each against `test_sql_editor` alone): 2 caught, 11 not.

Not caught, and worth a test each:
1. F5's open error lost (finding A).
2. Columns ordered by name instead of position (the test's columns k, "v w", z are in both orders).
3. Postgres's own schemas listed (the filter removed).
4. A line of four fields taken as a row (a name with a tab; the PR's own hypothesis).
5. The catalog of a buffer that is not .sql.
6. A failed catalog keeps its connection watched (no test has a catalog that fails).
7. A failed open read again on every call.
8. One catalog for every connection (the test drops the `ms` catalog before it switches to `pg`, so no other catalog exists at that moment).
9. The catalog's connection left open once read (a session leaked on the server per read).

Probably equivalent: the login's messages kept (no line of them has two tabs), rows handed out while loading (the rows are only stored at the end).

## F. No model for the catalog's states

CLAUDE.md asks for a TLA+ model for event-loop timing, the property first, with a broken variant. The catalog adds five states driven by the loop, and the bug the author found while writing it (the login's own batch taken for the rows) is a state bug of exactly that kind and a ready broken variant. My probes found no bad interleaving in the code as it is, so alone this would not block; with C's change (the read tied to the session's login, a retry) the states grow, and the model should come with it, in `SqlSess.tla` or beside it.

## Notes (not blocking)

- One `sql_catalog` call walks every row: 2.5 ms for 100,000 columns (sanitizer build, best of 20). Package 19 should take the rows once per read, not per key; a way to tell "nothing changed" (the count is one) would save it the walk.
- After one catalog call Alt+Break in a buffer that never ran a query returns 1 instead of 0 (`q2 early`), because the call makes the session. `:Connect` alone then shows the folder's connection instead of "not connected". Harmless.
- The header says "in schema, table and column order"; the code gives the table's own column order (ordinal position), which is what completion wants. The comment could say so.
- A database with no user tables reads as 0 for ever, the same as "still loading". After `use otherdb` in a script the catalog is still the configured database's.
- The state numbers 0, 1, 3, 2, -1 would read easier in order.
