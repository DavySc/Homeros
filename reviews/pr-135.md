# Review of PR 135: wallpaper behind the text

Head `926193ec` on main `10d8b65e`; the author pushed `4764a988` (the fuzzer, below) while the
review ran, and what was run on which is said where it matters. Reviewed 2026-11-23 by a separate thread, briefed with the
diff and the request (Davy, 2026-11-23: a wallpaper as in his WezTerm, "use the speed philosophy
as a base"), not with the author's conclusions. Repro files: `reviews/pr-135-repro/`.

**Verdict: changes requested.** The Wayland side holds its speed claim for the editor's own
process, and the design (decode once, let the platform scale) is right. Four things stand in the
way: two of the package's older plants no longer apply (item 0), which would turn the train red; on Windows a wallpaper makes every drawn cell cost about half as much again and a new window
size 12 to 81 ms (measured on Windows itself, items 1 and 2), which the PR left as a hypothesis;
three planted bugs pass the tests (item 4); and one drawing difference between the two windows
(item 3). Whether the picture shows at all on Hyprland with blur on is a hypothesis I could not
run (item 5) and needs one look on Davy's laptop.

## The check

0. **Two of the package's plants no longer apply** (run: `BROKEN PLANT` for both). Factoring
   `onto` out of `image_load` removed the text they replace:
   "image: the padding past the image is black, not bg" (`uint32_t v = bg;`) and "image: laid over
   bg without rounding" (`* (255 - q[3]) + 127) / 255)`). `tools/planted.sh` exits 1 on a broken

   The PR says its 14 new plants were run; the 46 older ones were not.

## Speed

### The editor's own frame time, Wayland: no measurable difference (measured)

`reviews/pr-135-repro/bench.sh`: main, the PR without a wallpaper, the PR with a 1920x1080 one,
alternating, 5 runs of 500 frames each, headless sway 1.9 with pixman, 1280x800, 128x36 cells,
`-O2`. `frame2.c` is the PR's `frame.c` plus a whole redraw with colour emoji on every row, the
worst case for the two changed blend functions (`mix`, `over`). Median of the 5 run medians and
their range, ms per `present()`:

| | main | PR, no wallpaper | PR, wallpaper |
|---|---|---|---|
| scroll a row a frame | 0.747 (0.648-0.766) | 0.738 (0.667-0.797) | 0.706 (0.638-0.769) |
| type a character a frame | 0.125 (0.124-0.133) | 0.148 (0.128-0.156) | 0.151 (0.142-0.158) |
| whole redraw with emoji | 2.753 (2.670-3.438) | 2.737 (2.612-3.204) | 2.718 (2.644-3.515) |

Scrolling and the whole redraw: inside the spread. Typing looked 0.02 ms slower on the PR in that
run, so it was run again on an idle machine, 10 alternating runs of 2,000 frames: main 0.136
(0.125-0.142), the PR without a wallpaper 0.138 (0.128-0.157), with one 0.143 (0.133-0.156): the
ranges overlap, no measurable difference.

So the alpha the colours now carry costs nothing measurable when no wallpaper is set, and the
wallpaper costs the editor's process nothing per frame. A new size without a wallpaper costs one
`stat` (the author's 0.5-0.7 microseconds; not re-measured).

### The compositor's time, Wayland: not free (measured under pixman; Hyprland a hypothesis)

The PR's "no measurable difference" is the editor's process only. The blend moved to the
compositor, and under a CPU renderer it shows. CPU ticks (10 ms) of the compositor's process over
1,000 frames, same bench, 3 alternating runs under weston 13 (800x600 window), 1 to 5 under sway
1.9 (1280x800):

| | no wallpaper | wallpaper |
|---|---|---|
| sway, typing, 500 frames (5 runs) | 6-8 | 115-135 |
| sway, scrolling, 500 frames (5 runs) | 47-60 | 106-135 |
| sway, typing, 2,000 frames (1 run) | 23 | 413 |
| weston, typing, 1,000 frames (3 runs) | 15-23 | 17-18 |
| weston, scrolling, 1,000 frames (3 runs) | 89-101 | 204-244 |

- Scrolling costs the compositor 2.2 to 2.4 times the CPU with a wallpaper on both (an ARGB
  surface blended over a scaled one, where it copied an opaque one).
- Under sway 1.9 (wlroots 0.17) one typed character costs what a whole scroll does: about 2 ms
  of compositor CPU a frame against 0.1 (17 times), whatever the picture's size (146 ticks per
  1,000 frames with a 1280x800 picture that needs no scaling, 180 with 1920x1080, 280 with
  3840x2160). Weston repaints only the damaged row, so this is sway's handling of the surface
  pair, not the editor's damage.
- On a GPU this is expected to be small. It stays a **hypothesis** for Hyprland: no DRM device
  exists in the review's container, so Hyprland cannot start there. README's residual risk says
  so for the blend; it should also carry the numbers above, since "a frame costs no more" (wl.c's
  comment) is true of one of the two processes that draw the frame.

### Windows: a per-cell cost and a per-size cost (measured on Windows itself)

README leaves both as "not measured on real Windows". `reviews/pr-135-repro/gdiprobe.c` makes
the GDI calls `backend.c` makes and times them; CI's `windows-latest` runner ran it twice (draft
PR 137, closed, never merged; job 137886802507), 9 runs each, median and range in ms:

| A new window size (`make_dib`): copy the picture into a DIB, `StretchBlt` to the window | HALFTONE (the PR) | COLORONCOLOR |
|---|---|---|
| 1920x1080 picture to 1280x800 | 17.2 (17.0-19.3) | 3.0 (2.9-3.0) |
| 1920x1080 to 1920x1080 | 12.3 (12.0-13.1) | 3.1 (3.1-3.3) |
| 1920x1080 to 2560x1440 | 50.1 (50.0-56.6) | 5.9 (5.9-6.0) |
| 1920x1080 to 3840x2160 | 80.6 (80.0-87.3) | 11.0 (11.0-11.1) |
| 3840x2160 to 1920x1080 | 54.1 (53.7-59.4) | 9.2 (9.1-9.4) |
| 3840x2160 to 2560x1440 | 76.8 (75.6-78.4) | 10.9 (10.7-11.0) |

| Drawing all 128x36 cells once (`draw_cell`'s calls, Consolas 9x19) | ms |
|---|---|
| opaque `ExtTextOutW` (no wallpaper) | 21.7 (21.5-22.4) |
| `BitBlt` from the wallpaper's bitmap, then transparent `ExtTextOutW` (wallpaper) | 31.9 (31.6-33.5) |
| `SetBkColor` alone, 4,608 calls | 0.046 (0.046-0.049) |
| `SetBkColor` and `SetBkMode`, 4,608 calls | 0.154 (0.096-0.165) |

The second run agrees within 2% on every row. Under Wine on the review's machine the same probe
gave 23 to 182 ms per size and 5.0 against 5.9 ms per grid, so Wine indeed says little.

1. **Per frame, Windows: every drawn cell costs 47% more with a wallpaper** (2.2 microseconds
   more per cell; 10 ms on a whole 128x36 redraw, which a scroll is on this backend). This is the
   per-frame cost the PR set out not to have, on the platform Davy works on. The Wayland side got
   its design from exactly this measurement (drawing into the text buffer: 3.3 ms, rejected).
   What to do is the author's: one `BitBlt` per run of default cells or per row instead of per
   cell is the obvious candidate, and the "Fix terminal font rendering on Windows" thread's
   painter draws on top of this, so the two should agree before either lands. Whatever is chosen,
   measure it on Windows (the probe and the CI job are there to reuse) and put the numbers in
   README.
2. **Per size, Windows: 12 to 81 ms with HALFTONE**, the cost the author rejected on Linux
   ("rescaling on the CPU at each size took 43-214 ms"). `make_dib` runs at each `WM_SIZE` step,
   so dragging the window's edge on a 2560x1440 monitor redraws at 20 frames a second at best.
   COLORONCOLOR is 5 to 8 times cheaper but aliases when shrinking. Options to weigh and measure:
   HALFTONE only once the drag ends (`WM_EXITSIZEMOVE`) with the cheap mode during it; keeping
   the source DIB instead of creating and filling it at each size (the copy alone is 3 ms of the
   12 at 1920x1080). Maximising and snapping (one size) are fine as they are.

`SetBkMode` is now called for every cell with or without a wallpaper: 0.1 ms per 4,608 cells
against 21.7 ms of drawing, 0.5%. Not worth a change on its own; it goes away if the mode is set
only where `back` changes.

## Correctness

3. **Wayland: the cursor's block shows the wallpaper on a face with base-coloured text**
   (reproduced, `sway.sh cursor.sh`: the screen's pixel inside the cursor's block is `1e1e2e`
   without a wallpaper and `4b1825`, the wallpaper's colour, with one). `colours()` clears a
   background equal to BG after the reverse swap, so the cursor on comment.error, .warning, .todo

   to no wallpaper". Fix: clear only when the cell is not reversed (an `else` on the swap), with

5. **Hyprland with blur: the picture may not show** (**hypothesis**, from reading Hyprland
   423da96 of 2026-11-22, not run: no DRM device here). `CWindow::shouldBlur` is true for any
   window when `decoration:blur:enabled` is on (Hyprland's default) unless a rule says otherwise.
   The window's surfaces are drawn lowest first (`bfHelper`), so the wallpaper's subsurface comes
   first, opaque, with no blur. Then the main surface: `CSurfacePassElement` blurs when the
   texture is not opaque, which the ARGB text buffer now is not, and
   `renderTextureWithBlurInternal` draws the blurred backdrop over the surface's whole box before
   the text, that is, over the wallpaper. With `new_optimizations` (default) that backdrop is the
   blurred desktop. If this reading is right, a Hyprland with blur on shows the blurred desktop
   where the wallpaper should be, and pays a blur pass per frame. The tests cannot see it (sway
   has no blur). It needs one look on Davy's laptop before the Wayland half is called done, and
   a line in README either way; if it does happen, the answers to compare are a window rule
   (`noblur`), or an empty blur region through ext-background-effect-v1, which `shouldBlur`
   honours.

## One mechanism, least code

- The decoder is reused: `decode` and `onto` are factored out of `image_load`, which now calls
  them, and `image_wallpaper` calls the same two; `pool_new` is factored out of `bufs_make` for
  the second shm buffer. `make dupes` passes. The config folder comes from `file_stdpath`, the
  file's identity from `file_id`. No second way to do any of it.
- tests/test_image.c's `wallpaper()` writes `model()`'s blend out again with the alpha scaled
  (6 lines). `model` taking the opacity serves both. A copy in `tests/`, which `make dupes` does
  not see.
- backend.c builds `0xRRGGBB` from BASE by hand at one place; no other place does, so nothing to
  share yet.
- `include/image.h`, `src/wl/wl.c` and `src/win/backend.c` are thread 0's (CLAUDE.md). The change
  to them is the hook the feature needs and nothing more; thread 0 has been asked to sign it off.

## The frames work

No conflict in design, some in text. The frames plan (`/mnt/project-files/frames/header-request.md`)
gives each tab page an OS window; `image_wallpaper` already suits that: one decoded picture for
the process, the cover rectangle computed per call for each window's size. What the frames thread
has to move into its per-window state is wl.c's `wsurf`, `wsub`, `wview`, `wall` and `wall_make`'s
static `up`; `wbuf` can stay one for all windows (a buffer may be attached to several surfaces).
`wl_present`, `bufs_make` and `wl_close` are touched by both, a few lines each.

One thing to settle there: image.h promises "a new picture comes at a new address", and wl.c
compares addresses to know whether its buffer is current. That holds for one window that sees
every change. With two windows, one that misses a change can in principle be handed its old
address for a newer picture (the old block freed and reused). **Hypothesis**: `address.c` tried
the sequence 12 times over four picture sizes and glibc did not reuse the address once. A change
counter from `image_wallpaper` would make it certain when frames arrive; not needed for this PR.

## Smaller notes

- Memory with a wallpaper: the picture stays decoded in the process (8 MB for 1920x1080, 33 MB
  for 3840x2160) and once more in the compositor's shm buffer or, on Windows, a window-sized
  bitmap. Wayland needs the process's copy only to upload it and when the base colour changes.
- A wallpaper that fails to map (`pool_new`) makes `wl_present` return before drawing anything,
  at every frame: the window stays blank instead of showing text without a wallpaper.
- The file is looked for only at a new window size, as documented. Under a tiling compositor
  that can be a long time; fine as a first version.
