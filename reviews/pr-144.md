## One mechanism for Lean's colours

**measured** (grep on main and on the head): no semantic-token code exists
in `src/lsp/`, `src/core/` or `include/`; this lexer is the only thing that
colours a `.lean` file. Package 13's plan (project memory, its branch is
not pushed) is the server's tokens laid over `syntax_faces`, which is VS
Code's own layering, and it asked package 12 for this lexer. So there is one
base mechanism and one planned overlay, not two ways to do one thing. The
overlay's PR must go through `syntax_faces` and not grow a second word list.

## Asks

### 1. A long line in a comment hangs the editor (blocking)

The Markdown rules look ahead to the line's end from each position, some of
them from each position again inside that. One line, in a `/--` comment,
`bench.c` (index time is `syntax_update`'s, the window is one frame's 50
`syntax_faces` calls), **measured**, best of 5:

| line of | 400 bytes | 800 bytes | 1,600 bytes | 20,000 bytes |
|---|---|---|---|---|
| `` ` `` repeated | 30 ms index, 92 ms a frame | 238 ms, 735 ms | over 60 s | over 120 s |
| `![a](` repeated | 1.8 ms, 5.7 ms | 9.8 ms, 29 ms | 56 ms, 170 ms | over 120 s |
| `[a` repeated | 1.4 ms, 4.2 ms | 5.5 ms, 16 ms | 22 ms, 65 ms | over 120 s |
| `*a ` repeated | 1.0 ms, 2.9 ms | 3.7 ms, 11.5 ms | 16 ms, 47 ms | over 120 s |
| `[a]((((` repeated | 0.2 ms, 0.7 ms | 0.9 ms, 2.6 ms | 3.5 ms, 10.5 ms | 531 ms, 1,584 ms |

Backticks grow with the cube of the line's length (`raw` tries each run
length against each later position, and `closes` calls it per position),
the others with the square. `syntax_update` asks `stop` only between
tokens, and a comment is one token, so nothing interrupts it: opening a
`.lean` file with such a line never shows a frame. VS Code does not have
this problem although its regexes backtrack the same way, because it stops
tokenising a line past `editor.maxTokenizationLineLength` (20,000) and on a
time limit. "Crashes never" covers a hang.

Ask: a bound that holds for any line (a line past some length in a comment
painted as plain comment, which is what VS Code shows past its limit, or
linear scans), a test that fails without it inside the test's time, a
plant, and `fuzz_tsql` reaching it (**hypothesis**, from reading it: its texts of at most 64
snippets and 1 KB space runs do not make an 800-byte line of backticks;
`make check`'s fuzz run did not report a timeout).
`gen.py` writes these files.

### 2. A frame of Lean costs more than the frame gate (blocking)

The PR has no timing. `survey.c` paints 50 lines, line by line as the core
asks, at 5 places in each of 150 of Lean's own files (598 windows, index
filled, best of 5 frames each), 5 alternating runs, **measured**:

| | median | p90 | p99 | max |
|---|---|---|---|---|
| Lean's lexer | 2.80 ms (2.76 to 2.85) | 5.6 (5.4 to 5.7) | 10.7 (10.7 to 11.9) | 33 to 39 ms |
| the T-SQL lexer on the same bytes | 0.034 ms (0.026 to 0.039) | 0.055 | 0.081 | 0.11 ms |

423 to 436 of the 598 windows are over the 2 ms gate by `syntax_faces`
alone, before the core draws anything. Over all 2,546 files (10,262
windows, 1 run): median 2.7 ms, p99 12.8 ms, 69% over 2 ms, worst 150 ms
(`Std/Tactic/BVDecide/Bitblast/BVExpr/Circuit/Lemmas/Expr.lean`, line 378:
an ordinary tactic proof). The index: 533 KB in 286 ms, 2 MB/s (comments
alone 20 MB/s); that part is deferred and asks `stop`, so it only delays
colour.

Two causes, both **measured**:

- Every line read lexes its token whole. `tsql_faces` keeps a long token's
  end between reads, but `paint` calls `lean_lex` from the token's start for
  each line, and a plain run is scanned to where the next rule matches even
  when the window ended long before. A proof with no keyword is one plain
  token: 5,604 bytes in the file above (`toks.c`), read 50 times a frame. A
  comment is the same: the last 50 lines of a 300-line doc comment cost
  55 ms a frame, of a 2,000-line one 470 ms, and a `def` head that runs
  5,000 lines 425 ms (`gen.py`'s `doc300`, `doc2000`, `c_def`).
- Each code point of plain text tries every rule: `wb` several times (two
  binary searches over the `\w` table each), then the word
  lists one word at a time through `tsql_byte`. A line of 20,000 `x` takes 9.7 ms to
  index and 19 ms a frame.

Ask: the frame cost of ordinary Lean under the gate with a measurement in
the PR (5 alternating runs, median and range, on Lean's sources), reads
that stop at the window, and a cost inside a long region that does not grow
with the distance from its start (kept starts inside a region with the
state they need, or the T-SQL lexer's way of finding state near the
window; the author's choice, DESIGN.md's "New approaches" row for the index
needs the scenario either way). A first-byte test before the word lists is
the cheap part.

### 3. Two differences from VS Code

- **a.** `def` (or any of the ten) at a line's end, `{..}` opening the next
  line: `def\n{a} foo`. VS Code's `\s+(\{[^}]*\})?` sees one line, so the
  `{` ends the head and `foo` is plain; `rule` skips the newline and then
  takes the braces, so `foo` is a definition's name (blue italic).
  **measured** (`diff-def-newline.lean`, found by seed 33 in a slice of
  Lean's own sources).
- **b.** `--[p]:<`: a link definition whose URL is the lone `<`. VS Code's
  `(<?)(\S+?)` gives the `<` back to the URL; `link_def` takes it as the
  opening bracket and finds no URL. **measured** (`diff-linkdef.lean`, seed
  55, shrunk by `t.py`). Cosmetic, but the claim is 0 bytes.

Both with a recorded case each.

### 4. The recorded cases miss rules

**measured** (`plants.log`, `plants2.log`, `plants3.log`): 12 of my 20
plants pass the recorded 600 cases. Two are caught by other seeds (the head
not stopping at `⦃`: 7 of 9,000 cases; the «name» in a head keeping the
plain face: 25 of 9,000), so 600 cases are thin for the rare tokens. Eight
change what is painted but no seed can see them, because the soups lack the
text; hand-written inputs in `hand/` catch each (and the PR's code agrees
with VS Code on all of them, 0 of 1,044 bytes):

| plant | caught by |
|---|---|
| `\s` without U+00A0 | `hand/nbsp.lean` |
| a link's title may be empty | `hand/title.lean` |
| a character right after `]` | `hand/charbr.lean` |
| no `<ftp://..>` autolink | `hand/ftp.lean` |
| a URL's items past 64 dropped | `hand/url64.lean` |
| an exponent's `+` not taken (`1e+3`) | `hand/expo.lean` |
| `deriving`, newline, `instance` as one keyword | `hand/derive.lean` |
| `==` as a setext underline | `hand/setext.lean` |

Two more ("a list's continuation of 5 spaces", "a quote's marker without
its space") changed nothing I could show; either they are equivalent or the
code they touch is not needed. Ask: the soups gain these tokens (or the
hand cases are recorded), and the two undecided lines get a case or go.

### 5. `src/sqlfmt/oracle/compare.sh` no longer links

**measured**: its `gcc` line links `tsql.c` without `lean.c` and fails on
the head with "undefined reference to `lean_lex`"; with main's `tsql.c` it
links. It is package 18's line and not in `make check`, which is why
nothing saw it. `tsql.c` is also the SQL formatter's lexer, so every user
of it now needs `lean.c` and `uni.c`. Either the line is fixed with package
18's agreement, as `src/git/check.sh` was, or better the dependency turns
round so the T-SQL lexer does not call Lean's.
