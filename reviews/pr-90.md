2026-11-20. Reviewer: a separate Fable 5.2 thread, briefed with the diff and package 5's contract
(include/keys.h, src/keys/README, DESIGN.md), not with the author's conclusions. Probes and how to

`make -f Makefile -f reviews/pr-90-repro/probe.mk probe P=reviews/pr-90-repro`, texts from
`gen.py`). Neovim is 0.12.6 (`tools-env/bin/nvim`). Machine: 4 cores, 8 MiB stack.

**Verdict: changes requested.** What the PR copies from Neovim it copies well: in 2,100 random
cases of my own, drawn from pieces the PR's tests do not draw, nothing differed from Neovim that
is not Neovim's two engines disagreeing with each other or a gap the README lists. But the
pattern engine recurses on the C stack once per repeat of a group and once per character of a
multi-line repeat, so ordinary patterns on ordinary text end the editor with SIGSEGV (finding 1),
and a pattern that runs into the step limit makes every later redraw take seconds once the core
draws `keys_hl` (finding 2). Finding 1 must be fixed before merge; 2 and 3 should be, since both
are in what this PR adds and "speed" is Davy's first priority; the rest are small.

## Findings

### 1. Must fix: a group repeat or a multi-line repeat overflows the stack (SIGSEGV)

`rep()` and `m()` in src/keys/regex.c call each other once per pass of a repeat whose body is not
one character (`\(..\)*`, `\v(..)+`) and once per character for `\_.*`, `\_.\{-}`, `\_s*` on
non-blank runs and `\_[..]*` (`MAGIC + '_'` returns with `*simple = 0`, so these never take the
looping branch). The depth is the length of the text matched. Neovim keeps this state on a heap
stack (`regstack`) and answers E363 when it is full; its default engine does not backtrack at all.

**measured** (`stack.sh build/probe`, bisection, 1 run per size; optimised build):

| text | pattern | fine at | SIGSEGV from | stack |
|---|---|---|---|---|
| SQL statements, `END` after them | `/select\_.\{-}END` | 25,489 bytes | 26,465 bytes | 8 MiB (Linux) |
| one line of `abab...` | `/\(a\|b\)*c` | 8,644 bytes | 8,888 bytes | 8 MiB |
| the same | `/select\_.\{-}END` | 3,151 bytes | 3,273 bytes | 1 MiB (`ulimit -s 1024`; Windows' default) |
| the same | `/\(a\|b\)*c` | 1,076 bytes | 1,106 bytes | 1 MiB |

**measured** (1 run each, `gen.py`'s big.sql, 746,670 bytes, the size of file Davy opens):
`/\_.*zzz`, `/select\_.\{-}table_9999`, `/\(.*\n\)*zzz` and `/col\(\d\+\)\_.*table_\1 ` each end
`build/probe` with exit 139. Neovim on the same file: 0.039 s, 0.220 s (E486) and 0.028 s for the
last three; `/\_.*zzz` did not finish in 120 s there, but it did not crash. On long.txt (one line,
300,000 bytes) `/\(a\|b\)*c`, `/\(ab\)\+$` and `/\v(a|b)+` crash; Neovim says E486 in 0.016 s.

A crash is never a known difference (Davy, 2026-11-17), and here it takes unsaved work with it:
`/select\_.\{-}from` typed in a 30 KB SQL file is enough on Linux, and a `\(..\)*` on a 1.1 KB
line on Windows. No check sees it: the fuzzers' inputs and the tests' lines are short. Wanted:

- no recursion whose depth grows with the text: `\_x` repeats through the same loop as one-line
  ones (the saved positions need the line too), and the group repeat's passes on a heap stack or
  under a depth limit that answers E363, as `MAXSTEPS` does;
- a test that searches a line and a buffer far past the limit (it runs under ASan, whose frames
  are larger, so the size must be chosen there), and its plant.

### 2. Should fix: a pattern at the step limit makes every frame take seconds ('hlsearch')

`re_exec()` gives up after 20,000,000 steps (about 0.5 s here), per call. `/` then says E363, but
the pattern stays the last search pattern, and `keys_hl()` runs it again for every line of every
frame, each line to the limit. Neovim's default engine has no such patterns to speak of, and its
'hlsearch' stops after 'redrawtime' (2 s) and switches itself off.

**measured** (`build/probe FILE KEYS h`: the keys, then `keys_hl` over 50 lines as the header
says the core calls it; 1 run each; Neovim through `nv.sh`):

| text | pattern | ours `/` | Neovim `/` | ours, one frame of 50 lines |
|---|---|---|---|---|
| aaa.txt: 60 lines of 60 `a` | `/\(a*\)*b` | E363 after 0.444 s | E486, 0.002 s | 25.1 s |
| the same | `/\v(a+)+b` | E363 after 0.676 s | E486, 0.003 s | 30.9 s |
| wide.txt: 60 lines of 20,000 `x` and ` foo` | `/x*foo` | E363 after 1.803 s | found, 0.004 s | 92.9 s |
| the same | `/ \@<=foo` | E363 after 1.284 s | found, 0.002 s | 68.8 s |
| w2.txt: 3 lines of 3,000 `x` and ` foo` | `/x*foo` | found, 0.369 s | found, 0.001 s | 1.2 s |

Nothing draws `keys_hl` yet (no caller in src/core or src/main.c: **measured**, grep), so today
the cost is the 0.4 to 1.8 s on the key and a wrong E363. The day package 4 draws it, the editor
stops answering after such a search until `:noh`, which itself waits for a frame. The second and
third rows are also plain differences from Neovim: the match exists and ours reports an error.
Wanted, in this PR or stated as owed before the core draws: a budget for one frame's `keys_hl`
(after it, matches are hidden as `:noh` does, Neovim's 'redrawtime' rule), and the leading `x*`
case not quadratic (a repeat that fails at column c fails at every column inside the run it
took; Neovim's backtracking engine has the same quadratic cost, 0.763 s with `\%#=1` on wide.txt,
which is why it is not the default).

### 3. Should fix: a plain search is about 20 times slower than Neovim's

**measured** (5 alternating runs each, big.sql, while `make check` ran on the same machine, so both
sides were loaded; optimised build; times inside the process, without start-up):

| keys | ours, median (range) | Neovim, median (range) |
|---|---|---|
| `/nosuchthing` (whole file, no match) | 0.104 s (0.080 to 0.109) | 0.004 s (0.004 to 0.006) |
| `/table_9999 ` (match on the last line) | 0.084 s (0.079 to 0.096) | 0.004 s (0.004 to 0.007) |
| `:%s/col\(\d\+\)/c_\1/g` (10,000 substitutions) | 0.095 s (0.091 to 0.126) | 0.045 s (0.025 to 0.046) |

A tenth of a second for a search that fails or wraps is past what a key should cost, on the file
size Davy uses, against priority 1 ("speed, superior to ... my-nvim"). **hypothesis** (from
reading `re_exec()`, not profiled): per start column it clears two 240-byte arrays, looks the line
up three times in the 4-slot ring, computes a grapheme length and enters `m()`; Neovim skips to
the pattern's first literal byte (`regstart`, `regmust`). A pattern that starts with a literal can
do the same with `memchr` on the line, and the arrays need clearing only when a group was set.

Also **measured** (1 run): with a multi-line pattern `keys_hl` searches again from the window's
top line for every line it is asked about, so a 50-line frame costs 0.010 to 0.013 s on big.sql
(`/\_s\+select`, `/;\n\zsselect col1\d`), most of a 16 ms frame, where a one-line pattern costs
under 0.001 s. Keeping the last match between consecutive lines of one frame would make it linear.

### 4. Should fix: the window's close while :s asks leaves the question open on another buffer

`keys_feed()` handles `KEY_CLOSE` before anything else, and `sub_asking` with its line number and
line copies stays set. **measured** (`build/asking a.txt b.txt c`, ASan build, 1 run): two
windows on two files, `:%s/o/XY/gc`, `y`, the window's close (`KEY_CLOSE`), `y`: the second `y`
writes a.txt's line 1 (`XYne twXY`) over line 1 of b.txt, and the message line still asks. The
same happens when another file comes into the window from outside the keys (`core_edit_file`,
case `b`). Wanted: the question ends (as Esc) before a `KEY_CLOSE` is acted on, and `loop()`
refuses to go on when the buffer is not the one it asked in; a test case and plant.

### 5. Small: where ours follows Neovim's backtracking engine, not its default

The README says ours follows the NFA engine. In my random cases the only differences from default
Neovim that are not listed gaps were these, and in each ours equals the other engine (**measured**:
30 cases of 2,100 against `ex_oracle_bt.lua`; the ones below also by hand with `\%#=1`, `one.sh`):

- `\@>`: `:%s/\(.\)\@>[^o ]\@<!/X/g`, `:%s/\v @>foo//` (Neovim's default misses `  foo.bar`),
  `/\v\n@>/+1`, `/z\@>\n\w\{-1,}` (default: E486, the other engine and ours find it).
- `\_[..]` in `:s` with `g`: `:1s/\_[^z]//g` on `ab`, `cd`, `zz` leaves an empty first line in
  default Neovim (its NFA program does not say it can match a line break, so do_sub() stops at
  the line's end) and joins the lines in ours and with `\%#=1`.

Neither needs code. The README's oddities list should name both, and regex.c's opening comment
("both give the same matches") is not true as written. `\%#=` itself is E476/E383 in ours and is
not in the README's "not built" list.

### 6. Small: the check's cost

`test_keys_ex` adds 3 min 45 s to `make test` here (**measured**, 1 run, 4 cores: 12,000 Neovim
processes), and 64 of the PR's plants run it whole: a plant caught in the first of its four
phases still runs the other three, because `main()` adds up `bad` and checks at the end. About
4 hours of plant time in all, an hour more per CI shard of four, whose limit on main is 75
minutes. `CHECK(!check(...))` per phase costs nothing when green and stops a caught plant at the
phase that caught it.

### 7. Nits (shorter code, Davy's rule)

- regex.c: the digit-count expression `d == 'x' ? 2 : d == 'u' ? 4 : d == 'U' ? 8 : ...` with its
  base stands three times (lines 196 to 198, 210, 285), and the `\_[` and `[` branches of
  `atom()` are the same ten lines twice: one helper each.
- tests/test_keys_ex.c types a string with the same `for (const char *s = ...; *s; s++)
  keys_feed(...)` line five times; test_keys_flash.c and test_keys_map.c each have a `feed()`.
- include/keys.h says of `keys_hl` that after the compile "only the keys' line copies grow"; the
  repeat's position stack (`push()`) and `growth()` also grow in the redraw path, to the longest
  repeat. True to CLAUDE.md's rule (grow to the largest, then stay), but the sentence is thread
  0's to correct when the header is next touched.
