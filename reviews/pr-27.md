## What was verified

- **The mapping against an identity oracle** (**measured**, `map.c`). Every byte carries an id; a range is the id of its first and of its last byte; an edit that deletes the first hands the start to the byte after the deletion, one that deletes the last hands the end to the byte before it (lsp.h's rule), and nothing in the oracle computes with offsets. Edits are inserts, deletes, replaces, joins (a newline and the blanks after it become one blank), up to 4 edits per command, and undo of the last command, over 1- to 4-byte characters. Publications are for the current version, for a version the editor has left, with unsent edits pending, incremental, and split across reads. 5 seeds of 300 trials: 240,558 publications (70,504 for a left version or with edits pending), 601,042 ranges, checked after every edit and every publication: 0 differ. A burst mode (thousands of commands between publications) fills the log: 3 seeds, 79 publications, 3 dropped by the full log, 0 wrong.
- **Real Lean 4.35** (**measured**, `live.c` with the real loop, `leanraw.py` for what Lean sends): 3 files, each diagnostic on the bytes Lean meant, including `𝔹` after `𝔸` (UTF-16 columns 11 to 13, bytes 89 to 93) and Lean's end-of-file error, which is a point.
- **Real clangd 18** (**measured**, `live.c`): 2 files, 5 diagnostics, each on the right bytes, including one after an astral character in a string and a point at the end of the file.
- **The gate** (**measured**, the PR's `src/lsp/bench/stale.c`, 5 runs at 250 ms per key for 30 s on a stand-in file, see finding 5). "simple": max hidden 6.5, 4.0, 3.2, 7.2 and 9.0 s, median 6.5; 5 of 5 fail the 2 s limit. "ok" on the same logs: 0 ms in 5 of 5. Live, about 2.6 million shown `sorry` warnings were checked against the text; all were where Lean meant (the 305 the bench counted as "elsewhere" are explained in finding 5).
- **What a server may send** (**measured**, `fuzz_handle.c`, libFuzzer with ASan and UBSan on `out` and `handle` with a document open, edits logged and requests pending): 1,433,261 runs in 121 s, no crash, no range outside the text.
- **The test's oracle is independent of the code under test** (read, and its result agrees with `map.c`'s).
- **The process model**: the server is a child of the loop (`proc_spawn`), nothing in `src/lsp/` blocks or starts a thread.
- Not verified: rust-analyzer (not installed here); Davy's own longest Lean file (the PR says so too).

## Findings

### 1. A file with one byte that is not UTF-8 gets no diagnostics, and takes Lean's server down (asked for before the merge)

`str_putq` writes bytes of 0x80 and above as they are, so the didOpen (and every didChange) of such a file is not valid JSON. lsp.h says an invalid byte counts as U+FFFD, and the UTF-16 kernel counts it so, but the writer does not send it so.

- clangd: `JSON parse error: Invalid UTF-8 sequence`; the didOpen is dropped and the file never gets a diagnostic. `live cases/latin1.c 10 clangd` shows 0 diagnostics where the same file with `e` for the `é` byte (`cases/ascii.c`) shows 1 (**measured**, 2 runs each).
- Lean: `Watchdog error: Cannot read LSP message: invalid UTF-8`, and the server exits with code 1 (**measured**, `rawbytes.py`, 1 run). One server serves a whole project, so every open file of that project loses its diagnostics until `\r`.

Neovim converts such a file on load and sends valid UTF-8, so there it works. Asked for: the writer sends U+FFFD for what the kernel counts as an invalid byte, so text and columns agree, with a test (a Latin-1 line through the fake server, which today assumes valid UTF-8) and a plant.

### 2. The full edit log is never reached by any check (asked for before the merge)

The log holds 4,096 edits; when full, the older half goes and `floor` rises. That branch is the part of "ok" that LspSync.tla does not have, and no test runs it: two plants there pass `make test TESTS=lsp` (`extra-plants.sh`, **measured**, 1 run):

- the branch removed (`if (0)`), which writes past the log: not caught, so the test never has 4,096 edits between two publications;
- `floor` not raised after the drop: not caught.

`map.c`'s burst mode catches both (`oracle-plants.sh`: a heap overflow under ASan, and a wrong range), and passes on the PR's code, so the branch is right today. Asked for: the test reaches it (a burst of commands with the server silent), and the two plants join `tests/plants/lsp.txt`.

### 3. Five more plants no check catches (does not block)

`extra-plants.sh`, 13 plants, **measured**, 1 run: 6 caught, 7 not. Besides the two above:

- a dead server's diagnostics stay on the screen (`forget` not called in `dead`);
- a reply is shown while an edit is not yet sent (`!d->chg.n` dropped from `current`);
- incremental diagnostics for a new version keep the old version's (`ver != v->ver` dropped);
- diagnostics without a version are ignored (the `v < 0 ? d->ver : v` rule, taken from Neovim);
- the URI is not percent-encoded; the project root is never searched for (the test's path has neither a blank nor a root file).

Each is a line of behaviour lsp.h or the PR text promises. A check for each, with its plant, is cheap.

### 4. Columns past the end of a line (does not block)

LSP says a column greater than the line's length means the line's end. `edge.c` (**measured**, 1 run):

- case 1: a range that lies wholly past the end of its line, or past the last line, is dropped ("all of it deleted since"), though nothing was edited. lsp.h says an empty range stays, as a point; Neovim clamps and shows it.
- cases 2 and 3: the range `2..99` on `abcde`, then `XY` typed at the line's end. Published before the edit, it is shown as `[2,5)`; arriving after it, as `[2,7)`. The same diagnostic lands differently by arrival time, because the column is cut to the line only after the mapping.

Lean and clangd sent no such column in my runs (**hypothesis**: rare). The first is a one-line fix (decide "point" after the conversion); the second needs the old line's length, which the client no longer has, so a sentence in lsp.h is enough.

### 5. The bench's input is not in the repo, and its check counts by a loose match (does not block)

- DESIGN.md's numbers come from "a 3,200-line generated file", but no generator is committed, so they cannot be re-run as recorded. I used a stand-in (`gen_lean.py`: 800 theorems, every fourth with `sorry`; 7.5 s to elaborate). The result has the same shape (see above), not the same numbers.
- `check_sorry` takes any message containing "sorry". On my file it reported 38, 57, 65, 92 and 53 warnings "elsewhere" in 5 runs. All are Lean's parse error `unexpected token 'sorry'; expected command`, and each sits exactly on the token `sorry` as it moves (bytes 42169 to 42175 while the line above is typed). So they are right, and the PR's "0 elsewhere" depends on its file having no such error. Matching "declaration uses" would say what is meant.

Asked for: commit the generator next to the bench.

### 6. What LspSync.tla does not cover of the code (does not block)

DESIGN.md already states that the model has points, not ranges, and no restart. Three more differences came with "ok" as built, and belong in that paragraph:

- the log is bounded, and a publication older than `floor` is dropped (finding 2);
- file progress and diagnostics share one log, so a progress message for version 6 makes a diagnostic for version 5 that arrives after it drop. Lean sends them in order; the test's fake server is written to expect the drop;
- a version is several edits, and edits wait unsent until the command ends; a publication can arrive in between. `map.c` covers this (70,504 such publications).

None of these shows a wrong position; each can only hide a stale publication, which is "simple"'s behaviour.

### 7. How long one publication holds the loop (does not block; a number for package 4)

`handle` runs inside the loop. `perf.c`, 20,000 lines, 5 runs each, median (range), **measured**:

| Diagnostics in one publication | Edits in the log | For | Time |
|---|---|---|---|
| 100 | 2 | the version before them | 0.15 ms (0.14 to 0.21) |
| 1,000 | 50 | the current version | 2.97 ms (2.93 to 3.17) |
| 1,000 | 50 | the version before them | 3.20 ms (3.14 to 3.50) |
| 800 | 4,000 | the version before them | 10.8 ms (10.6 to 17.5) |
| 5,000 | 4,000 | the version before them | 114 ms (109 to 118) |

About 3 µs per diagnostic plus a walk of the whole log per position. Lean's incremental batches in the bench were small, so this is far from the frame budget in Davy's use; a server that sends 1,000 at once costs more than a 2 ms frame.
