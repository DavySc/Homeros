## Required

### 1. Footnote references on one long line are searched from the line's start each (measured)

`fn_span()` asks `holds(l, eol(l), p, link_re)` and `holds(l, e, x - 1,
macro_re)` for every reference on a line, and each search starts at the
line's start and runs to its end when it finds nothing. So a line of k
references costs k scans of the line.

`tests/test_org.c` has a gate for this: one 64 KB line, coloured in 256-byte
pieces and then shown, limit 100 ms under the sanitizers. Its units have no
link and no footnote. `longgate.c` is that gate with them (3 runs, beside
other work):

| unit | ms |
|---|---|
| `word ` | 19, 19, 20 |
| `a[fn:1] ` | **5760, 5979, 6025** |
| `a [fn::b c] ` | **3688, 3508, 3442** |
| `a [fn:: (` | **15716, 16693, 16997** |
| `[[a][b]] ` | 57, 58, 64 |
| `http://b.c ` | 55, 56, 76 |
| `<http:b c> ` | 49, 50, 66 |
| `[[a][b ` | 23, 24, 34 |
| `<http:b ` | 26, 26, 39 |

At -O2 (`longline.c`, 1 run each): 1,000 references on an 8 KB line take
26 ms, 4,000 on 32 KB take 365 ms, 16,000 on 128 KB take 5.5 s; main takes
2.7 ms for the 32 KB line. A paragraph typed as one line with a few
footnotes is fine; this is the worst case the long-line gate exists for
(PR 83's review, item 1).

Wanted: the three footnote units and the link units in the long-line gate,
passing. A reference's link and macro need not be looked for from the line's
start again: the references come in order, so the last match found (or the
place the last search stopped) can be kept for the line.

Smaller, same gate: links are quadratic on a long line too, with a small
constant. `link_next()` asks `eol(q)` twice for every match (`separate(q, z <
eol(q) ? z : eol(q))`), each a scan to the line's end: `a [[b][c]] ` 11.6 ms
at 44 KB and 183 ms at 176 KB (-O2, 1 run each; 4.6 ms on main at 44 KB).
It passes the 64 KB gate (57 ms of 100). A newline before `z` can be looked
for in `[q, z)` alone.

### 2. An inline footnote that never closes is scanned to the end of the text, every time it is asked (measured)

`sexp()` (Org's `scan-sexps`) runs from the reference's `[` until the
brackets balance. When they never do, it runs to the end of the text, one
code point at a time with two table searches each. Nothing remembers the
answer: the line's footnotes are asked by `meta()`, by `fontify()` and by
`orgfx_conceal()`.

**While typing one.** Typing `x [fn::a` is this text until the `]` is typed.
`perf2.c`: 100,000 lines of `a *b* x^{2}`, line 10 replaced, the first 50
lines shown and then coloured, 5 alternating runs each:

| line 10 | sanitizers | -O2 |
|---|---|---|
| `a *b* x^{2}` | 0.3 to 0.6 ms, median 0.4 | 0.1 (all 5) |
| `x [fn::a` | **126.6 to 202.7, median 146.7** | **53.6 to 56.4, median 54.8** |

That is 1.2 MB after the opener, so about 45 ms per MB per frame at -O2: the
2 ms frame budget is passed when more than about 45 KB of text follows the
footnote being typed. A headline does not stop it (the scan is not bounded
by the walk).

**A paragraph of them.** The early review wrote that an inline footnote
whose parentheses never close "does not do this", from `[fn:: (` at the
line's start. A footnote at a line's start is not a reference (`p > l`), so
that text never reached `sexp()`. With a character before it
(`perf.c`, last 50 lines shown then coloured, 1 run each):

| lines | `x [fn::a`, sanitizers | `x [fn::a`, -O2 | `x [fn:: ( [fn:1]`, -O2 |
|---|---|---|---|
| 1,000 | 269 ms | 128 ms | 288 ms |
| 2,000 | 902 ms | 675 ms | 914 ms |
| 4,000 | 3.5 s | 2.2 s | 4.2 s |
| 20,000 | | 28.6 s | 48.9 s |

It quadruples per doubling, as the link searches did before their fix. The
same text at a line's start (`[fn:: (`, 20,000 lines) takes 10.5 ms.

Wanted: gate entries in `test_org` for one opener that never closes at the
top of the 100,000 plain lines, and for 20,000 lines of `x [fn::a`, within
the plain-line limit. What I would try, the author's choice: skip the bytes
that cannot matter in `sexp()` without `uni_cp` and the two table searches
(ASCII other than `"` and the brackets), keep the last `sexp()` asked and its
answer in the `OrgFx` until the next update (three asks a frame become one),
and when a scan failed, fail at once for any later opener after the last
closer or quote that scan saw. The third text (`x [fn:: ( [fn:1]`, a closed
reference after each open one) is not covered by that last rule; say what
you measure for it.

### 3. Ten Org differences the generator never makes (planted, reproduced against Org)

Each line is one of my plants. `make org-conform ORG_N=2000 SEED=1 test
TESTS=org` passes with it in place. The directed text makes the planted
driver differ from Org (`tri.py`, `tri.log`), and the real driver agrees
with Org on all 42 texts.

| Plant | Text that shows it |
|---|---|
| `separate()`: a keyword's `]:` past a blank not looked for (the second loop) | `kw2.org` `<id:x\n#+ab[ c]:>` |
| `verb_re()`: verbatim may be empty (`fits(m, m + 1, ...)`) | `ve9.org` `[fn:1] a\n== [[fn:1]] b`, `ve10.org` |
| `verb_re()`: the match ends at its closer (`*z = c + 1`) | `ve8.org` `[fn:1] a\n=c= =d\n[fn:1] y= z` |
| `hidel()`: a hidden part not cut at the line's end | `ml1.org` `[[a\nb][c]] x`, `ml2.org` (`-s`) |
| `hidel()`: a hidden part not cut at the line's start | the same two |
| `frag()`: no `$$` fragment at a line's start | `dd4.org` `[fn:1] a\n$$x$$ [[fn:1]]`, `dd5.org` |
| `frag()`: a `$` fragment may start before `;` | `sc3.org` `[fn:1] a\n$;x$ [[fn:1]]`, `sc4.org` |
| `valid()`: a fixed-width line is a valid context | `fw1.org` `[fn:1] a\n: [[fn:1]]`, `fw2.org` |
| `macro_re()`: a macro's `*` not taken | `st1.org` `[fn:1] a\nx \cite*{[fn:1]}`, `st2.org` |
| `fin()`: a form feed ends a plain link | `ff1.org` `x http://ab\f y`, `ff2.org` |

Most of these are `valid()`'s path, which only a reference that is no
reference reaches (one in a link or a macro, under a definition): the
generator rarely puts `[[fn:1]]` or `\cite{[fn:1]}` on a line that starts
with something `valid()` cares about. A link whose target spans lines
(`[[a\nb][c]]`) is not in `LINKS` at all, so nothing tests a hidden part
that crosses a line. Add the shapes to the generator, and these as plants.

Two of these first looked caught: the timed gate at `tests/test_org.c:1263`
failed while my other plants ran (low priority, 3 jobs on 4 cores). Run
again, `org-conform` and `test_org` passed with the plant in. The gate is
still easy to trip under load, as the early review said.

## Code that changes nothing (could be shorter)

Five more plants pass every check, and I found no text that shows them:
the real and the planted driver give the same answer on 60,000 random texts
each (`redundant.py`, `redundant.log`, -O2, three modes). Delete each, or
show the text that needs it and test it.

- `link_next()`: `e = lim + 11 < N ? lim + 11 : N`. Every caller's `lim` is
  a line's start, and a type holds no newline, so a match that starts before
  `lim` has its `:` before `lim`. `e = lim` gives the same answers.
- `fn_line()`: `&& a >= l` in `if (z > c->fz && a >= l) c->fz = z;`. A span
  with `a < l` is a definition's, and its `z` is on the line `l`, so it
  never carries to the next line anyway.
- `separate()`: `&& !o` and `&& r - 1 > o`. Any `[` of the run does (`o` is
  used as a flag only), and `S[r - 1] == ']'` is never the `[`.
- `uri()`: the `inside()` stop in the URI loop (`if (S[i] == '\n' &&
  inside(i + 1)) return 0;`), which the early review asked a gate for. No
  gate covers it, and without it 8,000 lines of `[[a` are no slower (0.6 ms
  against 1.0, 1 run each): the loop stops at the next bracket anyway.
- `holds()`: `z >= pos` against `z > pos`. My text for a macro that ends
  just before the reference's `]` (`ho6.org`) agrees with Org either way.
  This one may only need a better text.
