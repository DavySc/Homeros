## Findings to fix before merge

**1. A prompt answered after the repository changed acts on what was never shown (Git.tla ActsOnSeen; loses work).** measured, 1 run each.
The version a write carries is read when the write is queued (`wsend`: `r->shown`), which for `x` is after the `y`. Between the question and the answer inotify can refresh the buffer.
- `f1.sh`: cursor on a.txt's first hunk, `x` asks "Discard hunk?"; outside, that hunk is reverted; the refresh moves the cursor to the second hunk; `y` discards the second hunk (`discard_hunk` looks up the section at the cursor again). The ELEVEN edit is gone; nobody was asked about it.
- `f1b.sh`: `x` on a.txt asks "Discard unstaged changes in "a.txt"?"; outside, a line is appended; `y` runs `checkout -- a.txt` and the new line is lost. The stale check passes because the version was taken after the refresh.
The model tags the write in `Ask`, when the user chooses. The code should take the version (and for a hunk, the patch) when the question is put, and drop the write if it moved. A plant for it then belongs in `tests/plants/git.txt`.

**2. `SPC h r` resets every change within three lines of the next, not the one under the cursor (loses work, no question asked).** measured, 1 run (`f9.sh`).
Four changed lines (2, 5, 8, 11) show four sign blocks; `SPC h r` on line 2 reverts all four, because the hunk comes from the status diff with 3 lines of context, where they are one hunk. gitsigns (the reference for `SPC h`, FEATURES.md) works on hunks without context: one block. `SPC h s` has the same grain (stages all four). Either build the patch for the block under the cursor, or state the difference and its evidence; as it is, the signs promise one thing and the key does another.

**3. Deleting the commit message buffer leaves `git commit` waiting for ever and the repository's buffers frozen.** measured, 1 run, on the stand-in (PR 29 + PR 20, `README.md` f6).
After `c c`, deleting the message buffer other than by `ZZ`/`ZQ` leaves `busy` at write: a file staged outside stays under "Unstaged changes" after `g r`, `u` and `c c` do nothing and say nothing, and the `git commit` process stays. with-editor cancels when its buffer is killed, and it remaps `:wq`, `:x` to finish and `:q` to cancel (`with-editor-mode-map`); here only `ZZ` and `ZQ` end it. At least: a message buffer that is gone cancels the commit.

**4. `ref/git.c` is not deleted.** The rule agreed with thread 0: when `src/X` lands, the PR deletes `ref/X`. The Makefile no longer builds it.

**5. A fifth of the package is run by no check, and none of it has a plant.** measured (gcov above; extra plants).
`git_sign`, `SPC h s/r/S/u/p`, `SPC g l/L/d/b/B`, Enter on a commit or stash, amend, reword, pull, stash pop are never executed by `make check`. My plants "gutter signs all say added", "SPC h s stages every hunk of the file", "SPC g B opens the line above" and others pass the whole check (list below). CLAUDE.md: a check never seen to fail proves nothing; FEATURES.md names the signs and these keys as part of the feature. `git_sign` and `git_leader` run on ref/core.c's one buffer (`signs.c` does it), so tests need no new core. Finding 2 sat in this untested part.
Also unrun: everything behind `!git_headless` (`git_fill` into a core buffer, the split for diffs, `q`). That waits for package 4; say so in the PR and in project memory, with a test owed when PR 20 lands.

## Smaller findings

**6. Buried log and diff buffers are read again after every write.** measured, 1 run (`f2.sh`). `l l`, `q`, then `s` on a file: after `git add` the shim shows the status's 4 reads plus `log --graph -n256`. `q` never drops the `Aux`, so each write costs up to 2 extra git processes for buffers nobody sees, for the rest of the session. The "at most 5" holds for the status; a write's refresh can run 7.

**7. Opening the log (or a commit) again before the loop has read the first git's output shows both outputs joined.** measured, 1 run (`f3.sh`): 4 lines for 2 commits. `aux_open` kills the old process and resets `out`, but the old process's pipe is still delivered to the same `Aux`. Needs type-ahead or a slow loop turn; a generation number on the run, or waiting for the old exit, closes it.

**8. A full process table gives a false clean status without a message.** measured, 1 run each (`f4.sh`). With 30 other children, "Staged changes" is missing; with 31, both diff sections are. `start_reads` ignores `git_spawn`'s result. If all three fail, `done(r, -1)` returns early (`left` is -1) and `busy` stays set for ever (read from the code: hypothesis, not run). Unlikely with MAXP 32, but the answer to a failed read should be the "git: cannot run git" message, not a clean tree.

**9. Untracked files on another filesystem than the trash can never be discarded.** measured, 1 run. Repository on /dev/shm, trash under /tmp: `x y` says "git: cannot move c.txt to the trash". Emacs's `move-file-to-trash` copies and deletes across filesystems. The file is kept, so nothing is lost; but on a separate /home or data partition `x` on untracked files never works.

**10. Linked work trees: no Tag header and no Stashes section.** measured, 1 run (`f5.sh`). `has_tags`, `stashes`, `branch_of` and `prev_branch` read `refs/`, `packed-refs` and `logs/` under the work tree's own git directory; in a linked work tree they live in the common directory. Same class, not run: a repository with the reftable backend has none of these files (hypothesis).

**11. `git_free` kills a process that is not git's, and leaves callbacks into freed memory.** measured, 1 run each (`f7.sh`). With git busy (a commit waiting), `git_free` calls `proc_kill(r->pid[s])` for all six slots; unused slots hold 0, so the child in loop slot 0 (here a `sleep`, in the editor the language server or a tool) gets SIGTERM. And a loop turn after `git_free` while git's child still runs is a heap use after free in `on_proc` (ASan). Both only at exit today (main.c runs no loop turn after it).

**12. Dead and surplus code (the top rule).** `log_count` (sec.c, sec.h) is never called. `QMAX 8`: a second queued write is dropped as stale once the first finishes (its end moves the version), measured with `s` typed twice and with ten times; Git.tla's queue is 2 long.

**13. Liveness by address (hypothesis, not reproduced in 3 tries: glibc 2.39 twice, 2.44 once).** `git_buf_alive` and `of()` decide by the `Buf`'s address. A buffer deleted and another allocated at the same address would be taken for the status buffer (and overwritten by the next refresh) or for the old file (`SPC h S` would `git add` the old path). `ofs` also never forgets a buffer. Buffer numbers (`nr`) do not repeat.
