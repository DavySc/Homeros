## Findings

**1. Two of the four lam+alef pairs are untested (apply before merge).** Dropping U+0623 or U+0625 from the Arabic rule in both `uni.h` and `uni.c` passes Frama-C (227/227), test_uni, test_uni_nvim and fuzz_uni. The random lines draw from `special[]`, which has U+0622 and U+0627 only; the other two alefs come up only by chance from a bucket of thousands. Reproduce: `reviews/pr-12-repro/spec-plants.sh` (first two lines "NOT CAUGHT"). Fix: add 0x623 and 0x625 to `special[]` in `tests/test_uni_nvim.c`. The contract is right today (Neovim's `arabic_maxcombine` has these four; `l` agrees on my lines); the gap is that nothing would notice if it were not.

**2. `g == 8` in `uni_width` is dead (apply before merge).** All 26 regional indicators are already wide in the table (0 of 26 have cells code 0, counted from gen.py's output), so "a regional indicator that is narrow alone" never exists. Replacing `8` by `99` in the contract and the code passes every check, the exhaustive width comparison included. By the top rule the condition goes, from `uni.c:132` and from the `uni_width` contract in `uni.h` (header: through thread 0). If it is kept for a future Unicode version, that is speculative generality; the exhaustive test would catch the day it matters.

**3. The deviations are not in DESIGN.md (thread 0, need not block).** DESIGN.md still says "Unicode 16" in three places (the behaviour table's cluster row, the Positions/Cursor motion row, package 3's acceptance) and names "Neovim and Helix" for cluster motion without saying that stepping back follows Helix alone. The record today is `uni.h`'s comment, the PR text and project memory. DESIGN.md is where "behave like X" is named per behaviour, so it should carry: Unicode 18 (the tools' Neovim), step back = Helix, and that 5- and 6-byte forms are invalid here but one character in Neovim (measured: `\xf8\x88\x80\x80\x80x` is 2 stops for Neovim's `l`, 6 here; inherited from thread 0's `uni_len`).

**4. `uni_gprev` costs time in proportion to the distance back to the nearest ASCII byte (record, no change asked).** One step back from the end of a line with no ASCII byte: 300 bytes 2 µs, 3 KB 20 µs (14 to 26), 100 KB 0.57 ms (0.49 to 0.62), 1 MB 5.7 ms (5.2 to 6.1); 200 steps back on the 1 MB line 1.1 s. Neovim's and Helix's steps are bounded. Lines of Lean, SQL, org or prose in any script with spaces or ASCII punctuation never get near this. It is the residual risk of the chosen rule and should be written next to it (finding 3).

## The two intended deviations

**Unicode 18.** Sound. The oracle is the tools' Neovim, and the tables equal it on all 2^21 code points (the PR's test, re-run in `make check`) and regenerate from the published data. The version is one argument.

**Step back copies Helix.** Sound, and it is a copy of a reference editor, not a new mechanism, so the "New approaches" table does not apply. Evidence: Neovim's `h` does land inside clusters that its `l` treats as one (about 4% of my Indic-heavy lines), which no design would choose on purpose; Helix lands on the start (run here). The contract proves the result is a start reachable by forward steps and that the cluster there holds byte i-1. One limit to state plainly: `bound` takes "every ASCII byte is a start" as a case of its definition. That it equals "starts made from byte 0" is true by `more`'s first test and is checked by fuzz_uni and test_uni_nvim (measured), not proved as a lemma. Consequences for package 5: `h`, `X` and backspace will differ from Neovim on conjuncts and on emoji+ZWJ+stray byte; its conformance needs that exclusion written down.

## Notes for other packages (not defects here)

A. **Neovim's `virtcol()` disagrees with Neovim's screen next to invalid bytes.** `<84>` + virama + `X`: the screen puts X in column 6, `virtcol` says 5 (its getvcol joins the invalid byte with what follows; likewise an invalid byte after a Prepend). `uni_width` agrees with the screen and with `utf_ptr2cells`. About 29% of my lines (which are dense in invalid bytes) show it. Packages 4 and 5: a conformance test that compares virtual columns will see this on invalid UTF-8.

B. `ref/core.c` still steps by code point and now adds `uni_width` per code point, so e + combining accent counts 2 cells until package 4 steps by `uni_glen`.

C. The PR's speed benchmark source is not in the repo; `speed.c` here reproduces its conclusion.
