## Findings

Every finding was reproduced by running it; the output is in
`reviews/pr-175-repro/p175.out`.

### 1. Esc leaves the F5 armed: a later `:Declare` runs other text (blocking)

The PR lists "Esc on the prompt leaves the F5 waiting: a later `:Declare` by
hand runs it" as a known gap. What waits is a byte range (`pa`, `pz`), and
it is run on the buffer as it is when `:Declare` comes, however much later.

`p175 esc` (**measured**, 2 runs, the same both times): a temp table with 3
rows; `delete from #t where x = @a` selected; F5; Esc on the prompt. The
WHERE then moves to its own line under a comment line. `:Declare @a int = 2`
typed by hand, to set the value for later. Without F5, the editor runs the
old byte range, which now holds `delete from #t` and half of the comment:
`(3 rows affected)`, all rows gone.

Wanted: a run starts only from F5 or from the Enter that answers that F5's
own prompt. Any way out of the prompt (Esc, Ctrl-C, backspace on the empty
line, another command typed there) forgets the waiting F5. `sql_key` sees
every typed key when no map is pending, so a key that arrives outside the
command line while a session waits can clear it; the author picks the
mechanism. A test and a plant for it. My plant s2 (below) shows the same
state is untested from the other side: with `s->asked = 0` removed from
`run`, every later `:Declare` runs the last asked F5 again, and all tests
pass.

### 2. A default with a non-ASCII character arrives broken and is used (blocking)

`params` feeds the default to `keys_feed` one byte at a time. `p175 utf8`
(**measured**, 2 runs): the file has `declare @n nvarchar(20) = N'café €'`;
F5 on `select @n as n, len(@n) as l` shows the command line
`:Declare @n nvarchar(20) = N'cafÃ© â¬'`, and Enter runs it: the result is
that text with `l` 9, not 6. The value is kept, so every later run uses it.

Wanted: the default fed as code points (uni.h decodes), and a test with one.

### 3. CASE in a DECLARE list: the file cannot be run with F5 (blocking)

`else` and `end` are in `sql_vars`'s list of statement words, so a CASE
expression at depth 0 ends the DECLARE for it.

- `vars`: `declare @x int = case when 1=1 then 1 else 2 end, @y int` followed
  by `select @y`: `sql_vars` lists `@y`; SQL Server lacks nothing.
- `p175 case` (**measured**, 2 runs): F5 on that whole file asks for `@y`.
  With an answer the server refuses the batch (`Msg 134 ... '@y' has already
  been declared`); with Esc nothing runs. Before this PR the file ran.
- The same file's `@x`, used from another batch, gets the default
  `int = case when 1 = 1 then 1` (cut at `else`): `Incorrect syntax near ';'`.

My oracle (`ora.py`, 80 statement forms, the server under SET NOEXEC ON as
in the PR's): 3,821 batches kept on seeds 11 and 12, 75 differ, **all 75**
of this class (**measured**, 1 run each). The PR's own generator on a fresh
seed (4242): 517 kept, 0 differ (**measured**), so its claim holds for the
forms it draws; it draws no CASE.

Wanted: CASE ... END not ending a DECLARE (its words counted as a depth, for
one), the form added to `tests/test_sql_vars.py` and the recording.

### 4. A `--` comment inside a DECLARE item swallows the batch's first line

`p175 comment` (**measured**, 2 runs): `declare @a int -- the id` / `= 4` /
`select @a as a`, line 3 selected. The prompt shows
`:Declare @a int -- the id  = 4`; Enter sends
`DECLARE @a int -- the id  = 4; select @a as a`, all of it a comment after
`--`: nothing runs and nothing says so. `item` copies the bytes between the
item's first and last token, comments included. Not blocking (rare); the
fix for 3 touches the same lines.

### 5. A default over 255 bytes is cut

`e->cmd` is 256 bytes. `p175 long` (**measured**, 2 runs): a table variable
with 40 columns gives a prompt cut in the middle of column 15; Enter keeps
the cut text and the server answers `Msg 173`. Each later run fails the
same way until `:Declare @t` forgets it. Not blocking.

### 6. A kept value wins over the file's DECLARE after it changes (Davy's call)

`p175 stale` (**measured**, 2 runs): `declare @a int = 3`, line 2 selected,
F5, Enter: `a` is 3. The file's line changed to `= 7`; F5 on line 2 again:
`a` is 3, with no prompt, and nothing in the results says which value ran.
This is "keeps it per file" as built, but with Davy's files (the DECLARE at
the top is what he edits) an INSERT can run for the old value unseen. Put
to Davy on a decision card; not blocking.

### 7. Smaller

- Each `DECLARE @a int = 3; ` put before a batch adds a `(1 row affected)`
  line to the results (`p175 davy`: `(1 row affected)` then
  `(2 rows affected)` for an INSERT of 2 rows). The client prints that line
  for a file's own `declare @a int = 5` too (`p175 n2`), so it is older than
  this PR; with the PR it shows on every run with a parameter.
  **Hypothesis**: SSMS does not print it; to be compared with sqlcmd.
- Enter on a prompt with no value forgets nothing, runs nothing and leaves
  the F5 waiting (`p175 two`), and the selection is gone (`gv` brings it
  back). With finding 1 fixed the waiting part goes away.
- `run.c` has no fuzzer (`tests/fuzz_sql_*` cover tds and pg). `soup.py`:
  90,000 random token batches through `sql_vars` under ASan and UBSan, no
  report (**measured**, 3 seeds).
- With the file's first batch a CREATE PROCEDURE, the whole-file scan for
  defaults stops there (`break`), so later DECLAREs give no default
  (read from the code, **hypothesis**, not run).

## Method

Tools as CI installs them; SQL Server 2022 and PostgreSQL 17 in containers,
a second pair without ports for the plants so `make check` keeps its own.
`mk.sh TREE probe.c OUT` builds a probe against the tree with the test
flags (objects cached). `p175 SCENARIO` drives the editor through
`keys_input`, as main.c does, against the servers. `vars` prints
`sql_vars`'s answer for stdin. `prun.py TREE plants.txt` applies each plant
line in a second worktree, builds its one test and runs it.
