## Blocking

### B1. The 1,001st undo writes to freed memory

The new cap on undo-mark entries (`UMARKS_MAX` 1,000, `umarks_put()`) is one short of what the undo tree keeps. With a mark set, after more than 1,000 groups the oldest group's entry is dropped. Undoing that far, `core_undo()` makes a new entry for that group, which sorts last in the list; the counting loop then finds it is entry 1,001, frees it, and the `memcpy` below writes into it.

**measured** (`marks_cap.c`, 2 runs with ASan, 1 without): 1,100 one-character groups with mark a moved before each, then undo as far as it goes. ASan stops at undo 1,001 with heap-use-after-free in `umarks_put` called from `core_undo`. Without ASan the run goes on, 1,001 groups are undone and 1 mark comes back wrong. A second scenario (600 groups, 500 undone, 600 on a new branch, all undone) is clean: 0 marks wrong.

So the comment's hypothesis ("groups the tree has freed, as long as it frees the oldest numbers first") is off by one against `UNDO_LEVELS`: the tree undoes 1,001 groups. Never free the entry just made, and take the cap from the undo package's own number. `fuzz_core` cannot find this, since it never makes 1,000 groups; a test with a lowered cap or 1,100 groups can (`marks_cap.c` runs in 0.1 s).

Smaller, same code: every new entry walks the whole list, all buffers' entries included, to count. **measured** (`marks_perf`, 5 alternating runs, microseconds per edit, median and range, machine busy): 5,000 groups 1.36 (1.01 to 1.96) without a mark, 4.01 (3.81 to 4.55) with; 20,000 groups 1.28 (1.03 to 1.43) against 3.76 (3.64 to 4.91); 40,000 groups 1.07 (1.03 to 1.35) against 3.76 (3.63 to 4.12). ### 2. Shrinking the window area does not reset the wanted column

When CTRL-W `-` or `_` makes the command line taller (the current window is the last full-width one, for instance the only window), Neovim sets 'cmdheight', and setting that option sets `w_set_curswant`, the same rule `core_set_wrap` already copies. The core's `top_new_height()` changes the height without it.

**measured**: `mini.py 12 30 'abcdefghij\nab\nabcdefghij\nab\nabcdefghij\nab\n' k:5l k:j w:- k:k`: Neovim's cursor ends on line 1 column 2, the core's on column 6 (also with `w2:_`; with `$` first both agree, as curswant is then "end of line"). Recomputing the wanted column there (`experiments.diff`, second hunk) makes the three reduced cases and their three originals match, with the 300 recorded cases still matching.

### 3. The `<<<` marker is cut short on lines numbered 10 and up

`put_number()` writes `<<<` into the number column's own buffer, so after a two-digit number only `<<` fits and after three digits only `<`. Neovim always draws three, over the first text cells.

**measured** (`mini.py 6 20 @cases/f12.txt wrap k:10G 'k:A<90 y><Esc>'`, and lines 99 and 100 of a 120-line file): Neovim `10<<<yyyy`, core `10<<yyyyy`; Neovim `100<<<yyy`, core `100<yyyyy`. Line 9 matches. Any long wrapped line past line 9 in a short window shows it.

### 4. `:set wrap` is not kept for the next buffer in that window

Neovim keeps a window's `:set` value for buffers it has not shown before (`w_allbuf_opt`). The core takes "the window keeps its own" to mean the current value, which `:bp` has by then replaced with the other window's.

**measured** (`mini.py 10 20 '<long line>\nx\ny\n,<long line>\n2\n3\n' new wrap bp e:f1`): Neovim shows f1 wrapped in that window, the core unwrapped.

### 5. A non-current window's skipcol after a resize counts bytes where Neovim counts characters

`plines_col()` walks to byte `col`; Neovim's `plines_win_col()` counts `col` characters (its loop decrements the byte column once per character), so with multi-byte characters before the cursor it sees a later column. **measured**: `cases/r7_5.txt` (`'\tა x'`, CTRL-W K) differs; the same case with `a` for `ა` matches (1 run each). The mechanism is a **hypothesis** from Neovim's source as I remember it; the dependence on the character's byte length is measured. It only shows in a window that is not current, one row high, on a wrapped line: small, but it is not timing. Copy it or record it as a known difference.

### 6. Entering a window does not look at its view again

Neovim's `win_enter_ext()` calls `changed_line_abv_curs()`, so `update_topline()` runs for the entered window with its real `w_botline`. The core's `win_enter()` leaves `topvalid` set, and the view `scroll_to_fraction()` chose at the split stays, with fewer than 'scrolloff' lines below the cursor.

**measured** (`scan_split.py`: an N-line file, `LG`, `CTRL-W s`, `CTRL-W p`, over 5 screen heights, 8 file lengths and up to 16 cursor lines): 39 of 425 combinations differ, among them 24 rows, any file of 20 lines or more, line 15: Neovim shows lines 11 to 20, the core 9 to 18. Clearing `topvalid` in `win_enter()` (`experiments.diff`, first hunk) makes that case match, and the 300 recorded cases and fresh seeds 2 to 5 give the same result as before (1 run each). With both experiments, my wider generator (`gen2.py 400 1`: the PR's tokens plus `NG` jumps and more window switches) goes from 5 differing cases of 400 to 2; those two are point 10 and the note for package 5 below.

The PR's generator misses this because its only long jumps are `G` and `gg`: the cursor is rarely low in a tall window when it is split. Please add `NG` (or any jump to a random line) to `gen_tokens`.

### 7. An undo group's "join" flag outlives its buffer

`edit_file()` reuses an empty unnamed buffer by copying it to a local `Buf old` and calling `buf_unload(&old)`; `umarks_drop()` compares the buffer's address, so it drops nothing, and the entries of the old undo history stay under the reused `Buf`. The new file's undo starts at group 1 again and inherits group 1's `join` flag.

**measured** (`stalejoin.c`, 1 run): `tests/test_core_undo.c`'s "same bytes as dd" case gives line 1 after undo and redo in a fresh editor, and line 2 when an unnamed buffer first had a line opened and joined back in one group, undone, and was then reused by `:e file`.

### 8. An edit gets slower with every undo group while a mark is set

With any of a-z, `<` or `>` set, every undo group keeps an entry in the `umarks` list, and every new group walks the whole list (`umarks_find` finds nothing). **measured** (`marks_perf.c`): five alternating runs per side, mean of the last 1,000 one-character edits in microseconds, median (range): after 5,000 groups 0.60 (0.57 to 0.73) with no mark against 16.2 (12.2 to 22.9) with mark a set; after 20,000 groups 0.59 (0.58 to 0.70) against 270 (251 to 291); after 40,000 groups 0.59 (0.56 to 0.70) against 690 (627 to 701). 0.69 ms per edit is a third of the 2 ms frame budget. The undo tree keeps 1,000 levels (`UNDO_LEVELS`), so the list also holds entries for groups that no longer exist. Neovim keeps the marks in the undo header, which costs nothing to find. An entry per group in the undo tree would need `undo.h` (thread 0); within the core, a new group cannot have an entry, so the search can be skipped for it.
