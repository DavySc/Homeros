# Review of PR 51: SQL colours (nvim-treesitter's grammar and queries)

Reviewed head 4a64ff1 on base 8243cdb (main at the time of review), 2026-11-18.
Repro files: `reviews/pr-51-repro/`. Machine: 4 cores, Xeon 2.3 GHz, cloud container.

## Verdict

**Changes requested**, for one small thing: `make fuzz` runs no SQL
(finding 1). Everything else holds. The colours are Neovim's on every byte I
compared (9,760 random cases, 238 whole files, 3 directed texts: 0 differ),
the scanner patch is correct and the test's Neovim parses with the same
patched C, all 23 syntax plants are caught, and `planted.sh` now reports a
real reason for each.

Separately, SQL costs more than the three languages before it (section 5:
55 ms in one stretch at the first SQL file, 28 MB of resident memory, an
editor of 13.9 MB instead of about 2, and 27 to 84 ms of parsing per key on
two large files). Those are the grammar's costs and Neovim pays the same
ones, so they do not block this PR, but the PR's "Cost" section names none
of them, `syntax.h` now states a number SQL exceeds, and Davy should see
them.

## Blocking

### 1. `make fuzz` runs none of the SQL grammar (measured)

`tests/fuzz_syntax.c` is unchanged: `byte() % 3` picks among `f.c`, `f.lua`
and `f.md`. So the fuzzer, the check that stops and resumes parses at
arbitrary points and reads faces from stale trees, never enters the code this
PR adds. That code is the package's first scanner that keeps heap state
between calls (`start_tag`, serialized into the tree), written by hand, and
already needed one memory patch. The random test does run SQL under ASan, but
its 16 SQL snippets contain no `$`, so a dollar tag is only ever edited by
chance, when a window of the corpus holds one.

Asked for: SQL as a fourth language in `fuzz_syntax.c`, with `$$`, a tagged
`$a$` and a lone `$` among its tokens (and its header comment, which names
three languages); and a `$$` among `test_syntax.c`'s SQL snippets.
`reviews/pr-51-repro/fuzz_sql.c` is that fuzzer narrowed to SQL: 137,038
runs in 60 s found nothing, so I expect the change to pass as it is.

## What holds

### 2. The colours (measured)

Both sides colour SQL, and identically: table above. On `select.sql` 6,781
of 8,142 bytes are coloured on each side; on `plpgsql.sql` 77,393 of
123,117. The queries compiled into the binary are byte for byte the files
the test's Neovim reads (`build/syntax/queries.c` entries 8 and 9 decoded
against `queries/sql` and `nvim/queries/sql`: 8,123 and 144 bytes, equal;
both links resolve to one store path). Neovim finds `parser/sql.so` and
`queries/sql` only under `build/syntax/src/nvim`. `injections.scm` names the
language `comment`, which neither side has (Neovim: "No parser for language
comment"), so both leave comments without injected colours.

The grammar is revision 174cebb of derekstride/tree-sitter-sql, the revision
nvim-treesitter's own `parsers.lua` names (nvim-treesitter
0.10.0-unstable-2026-11-07 in this nixpkgs). `parser.c` in the build equals
the fetched one; `scanner.c` differs by the patch's one line.

### 3. The scanner patch (measured, and read)

Reproduced without the editor (`leak.c`: tree-sitter, the grammar and
LeakSanitizer): the scanner as fetched leaks 1,024 bytes on
`CREATE FUNCTION f() RETURNS int AS $$ SELECT $$;`, the patched one nothing.
No whole corpus file leaks on a fresh parse even unpatched, which is why it
took edits to find.

I read every path of `scanner.c` that allocates. `scan_dollar_string_tag`
frees its size cell on all three returns and the tag on the failing one. Of
the scan function's three branches, the first stores the tag in the state,
the second frees the end tag on both returns, and the third had four exits:
tag missing (nothing to free), tag equal to the open one (the leak), end of
text, and match (both free). With the patch all are balanced, and the freed
pointer is not used again; a second `free` there is caught by ASan (my
plant). The patch uses `--replace-fail`, so a changed upstream line fails
the build instead of silently dropping the fix.

The test's Neovim loads the parser built by the same derivation, after the
same `postPatch`. Measured rather than read: that `.so` leaves one block
fewer than nixpkgs' unpatched one on `body.sql` (`dl.sh`).

### 4. Allocation in the redraw path (measured)

`syntax_faces`, the part of this package inside a frame, allocates nothing
after first use in any of the four languages: 0 allocations in 200 frames on
each of 7 files (`alloc.sh`).

The SQL scanner does allocate, in `syntax_update` (the deferred parse): 8
bytes on every call where a dollar string may start, and 1,024 more per `$`
it meets. Per key: 138 on `select.sql`, 22,119 on `plpgsql.sql`, against 0
for C, 1 for Lua and 3 for Markdown. That is small next to tree-sitter's own
allocations in the same update (356 per key on `test_syntax.c`, 2,476 on
`select.sql`, 79,448 on `plpgsql.sql`), so it adds to what the parse already
does and does not move allocation into the frame.

### The PR 48 follow-ups (measured)

Hex printing does what it says: with the priority-tie bug planted,
`planted.sh` reports `tests/test_syntax.c:656: CHECK(...) failed`, and all
110 printed cases decode to their files. No reason line of the 23 plants is
case text any more. The test changes weaken nothing: the three older
languages keep 40 cases each by default, case 2 is still the Markdown block
quote, and the Markdown-only allowance still tests `c % NL == 2`.

## 5. What SQL costs (measured; for Davy and thread 0, not blocking)

**First use.** `first.sh`, a two-byte file per language, 5 alternating runs,
median and range:

| | first `syntax_update`, one stretch without asking `stop` | resident memory after |
|---|---|---|
| C | 14.4 ms (14.4 to 22.4) | 4.1 MB |
| Lua | 3.2 ms (3.1 to 3.3) | 2.6 MB |
| Markdown | 8.6 ms (8.5 to 13.6) | 3.7 MB |
| SQL | 54.6 ms (50.7 to 57.8) | 29.5 MB |

`include/syntax.h` says the first update "compiles its queries, 9 to 23 ms
without asking". SQL takes more than twice the top of that range, so the
header needs thread 0. Neovim 0.12.6 loads the same query in 38.1 ms (37.3
to 42.2; C: 15.9), so this is the grammar's size, not our code.

Of SQL's 27.7 MB, 11.7 MB are pages of the parser's tables and 16.0 MB is
heap, of which 178 KB is still in use: the query compile's working memory,
which glibc keeps. `malloc_trim(0)` after it brings 29.7 MB to 14.1 MB (1
run). DESIGN.md's target is 15 MB at start with no file.

**Size.** `sql/parser.o` holds 11.70 MB of the editor's 13.74 MB of text
(`size build/gcc/homeros`); C's parser is 0.60 MB. `parser.c` is 43 MB and
compiles in 4.8 s (C's: 0.4 s), once per build and once per plant.

**Per key.** `alloc.sh`, 200 keys typed in one place, time of the update
that follows each (it asks `stop`; the longest stretch without asking has a
median under 1 ms on every file):

| file | update per key, median |
|---|---|
| `tests/test_syntax.c`, 24 KB | 0.19 ms (0.19 to 0.21, 5 runs) |
| 3,000 one-line SELECTs, 170 KB, no syntax error | 1.13 ms (1.05 to 1.18, 5 runs) |
| PostgreSQL's `plpgsql.sql`, 123 KB | 26.8 ms (25.8 to 27.5, 5 runs); Neovim 39.7 (38.6 to 41.8) |
| `tsql.sql` 100 times over, 143 KB | 84.1 ms and 81.7 ms (1 run at each of two lines); Neovim 92.8 |

On the last two the grammar reuses almost nothing of the old tree: the cost
is the same at line 100 and line 1,500 (79,448 and 79,491 allocations per
key). An error elsewhere is not the cause (the clean file with a bad line
at either end stays at 1.2 ms). **Hypothesis:** Davy's real T-SQL files of
that size behave like the last row, since the grammar reports a syntax error
on ordinary T-SQL (`DECLARE @id INT = 42;`); I have none of his files to
measure. Typing is not held up (the update stops for input), but colours
then trail the text by several frames and each key costs that much
processor time, as in Neovim with this grammar.
