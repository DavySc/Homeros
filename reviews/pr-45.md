# Review of PR 45: org incremental reparse (`org_edit`), head ae7aa25

Independent review against the contract in `include/org.h` ("updates `*e` and `*count` to what `org_parse(s, n)` gives, reparsing only the top-level subtrees the edit touched; 0 ok; -1 out of memory, `*e` then freed and NULL"). Everything below was run by the reviewer on one machine (4 cores, gcc 13.3, clang 18.1, the tools of `tools.nix`). The drivers are the reviewer's own, in `reviews/pr-45-repro/` (its README says how to rerun). Tags as CLAUDE.md asks.

**Verdict: changes requested, one finding.** The result is right everywhere I looked: 198 million enumerated edits and 5.2 million chained random edits all equal a whole parse, and no edit of an ordinary typing run fell back to a whole parse. But one typable edit costs hundreds to thousands of whole parses (finding 1: 80 ms on an 81 KB file, 12.5 s on 974 KB). The fix removes the loop, is 2 lines shorter and is tested below. Nothing here needs Davy.

Two things the table shows:

## 4. Findings

1. **Fix before merge: a new shallower headline above many deeper ones costs one whole parse per headline it takes in.** When the span's last top-level node ends past the span, the loop (`src/org/org.c:775`) adds one old top-level node and parses again. But the headline's end is scanned to the end of the text, and its children are parsed to that end, whatever the span's limit: every round is a parse of the whole subtree, and there are as many rounds as old top-level nodes swallowed. Typing `* n` on a new first line of a file whose headlines all start at level 2 (or promoting its first headline):

   | Text | PR | One parse (below) | `org_parse` | Tag |
   |---|---|---|---|---|
   | synthetic agenda, every headline one level deeper, 81 KB, 210 top-level nodes | 80.0 ms (79.7 to 84.7), 449,323 nodes parsed | 0.41 ms (0.40 to 0.56), 4,218 nodes | 0.36 ms | measured, 5 alternating runs |
   | the same 12 times, 974 KB, 2,520 top-level nodes | 12.5 s, 63.8 million nodes parsed | 5.1 ms (5.0 to 5.3) | 4.4 ms | measured; PR 1 run, variant 5 |

   The first parse already holds everything: `f` runs to the new headline's true end, and that end is where an old top-level node began (a headline nested in an old top-level node is deeper than it, so the first headline at the new one's level or above is top-level). So the loop can go: take `R` from `f` and splice (`reviews/pr-45-repro/one-parse.diff`, 2 lines shorter, with the plant moved to the new line). Tried by the reviewer: `enum 4` 192,748,996 edits 0 differ; 189,000 chained edits and 18,900 under ASan+UBSan 0 differ; both compilers; `fuzz_org` 896,609 runs in 60 s; both `org_edit` plants caught; typing times unchanged (table of section 3: every median and p99 inside the PR's range or below it). All measured, 1 run each.
2. **Record: the top-level subtree is the unit.** One top-level headline over the whole file means a whole parse per key (5.2 ms at 974 KB, 100% of the nodes, measured). Fine at Davy's 81 KB (0.5 ms, measured); the design's "only the heading subtree an edit touches" would need the innermost subtree. For the PR's known limits.
3. Small: after a failed whole reparse `*count` keeps its old value (`*e` is NULL as the contract says); the `fail:` path sets it to 0.

What was looked for and not found: any edit whose list differs from a whole parse, any sanitizer report, any leak or wrong return on a failed allocation, any whole reparse while typing, any real planted bug passing the fuzzer.
