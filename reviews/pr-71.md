# Review of PR 71: package 12, JSON colours and T-SQL operators in one colour

Reviewer: separate Fable 5.2 thread, 2026-11-19. Contract: CLAUDE.md,
`include/tsql.h`, Davy's asks (JSON as nvim-treesitter colours it, fast on
big files; T-SQL operators in one colour like SSMS, not the comments' grey).
Head 25fe47e, whose base is main 240a897.

## Verdict

**Changes requested at 25fe47e.** The T-SQL colour change and the PR 64
report are fine. JSON's colours match Neovim on everything valid I tried
but two things, and one of them breaks "fast on big files": a long string
is read from its start for every 256 bytes drawn.

## Findings

### 1. Blocking: one long string costs 59 ms a frame per MB (measured, 5 runs each)

`json_paint` looks for escapes from the string's first byte to its last on
every call (`for (size_t i = p + 1; i + 1 < e; i++)`), and the core calls it
once per 256 bytes drawn (`draw_line`), so a frame costs about 50 reads of
the whole string. A base64 value is the usual case.

`reviews/pr-71-repro/longstr.c N MODE`, the core's reads for one frame (the
PR's own `bench_json.c` frame), index filled, median (range) in ms:

| Text | 100 KB | 1 MB | 5 MB |
|---|---|---|---|
| T-SQL `SELECT '<N bytes>'`, frame at top | 0.037 (0.037-0.046) | 0.455 (0.447-0.467) | 2.02 (2.00-2.08) |
| JSON `{"data": "<N bytes>"}`, frame at top | 5.72 (5.65-5.75) | 59.1 (58.5-62.5) | 299 (248-327) |
| the same, frame in the middle of the string | 5.54 (5.50-5.71) | 56.5 (52.5-60.0) | 317 (260-330) |

T-SQL's frame in the middle of its string is 0.004 ms.

A scan that starts at the window (and steps back over the run of
backslashes it lands in, to know which one escapes) is 4 lines more:
`reviews/pr-71-repro/suggested-fix.diff`. With it (measured, 5 runs): 0.166
ms, 1.48 ms and 13.2 ms at the top (one lex of the string, as T-SQL's), 0.03
ms in the middle; `test_json` and `test_tsql` pass, and my 94 documents get
the same faces as before (one run each). The author may know a shorter way.
Whatever the fix, the test needs a string longer than 256 bytes with escapes
(the random documents' strings hold at most 5 pieces) and a plant.

### 2. To fix: a valid number with `e+` is drawn in three pieces (measured)

`1e+5` and `1.5E+10` are valid JSON (RFC 8259). tree-sitter-json 0.24.8
takes no plus in an exponent and reports a syntax error, so Neovim draws
`1`, plain `e+`, `5`; json.c copies that (`{"a": 1e+5, "b": 2}`: Neovim
`!RPPPD.N..ND.PPPD.NR`, ours the same faces). The random documents never
hold `e+` (`num()`'s exponents are `e1 E7 e-3 E-10`), so "valid documents"
in the PR's text leaves these out. This is the grammar's bug, not a
behaviour to copy: the two existing departures already take the better
colour over Neovim's. Taking the sign as `tsql_token` does (`+` or `-`) also
makes the number's tail the same code as tsql.c's lines 103 to 111, which
can then be one function (finding 4). Add the case to the directed lines.

### 3. To settle: `include/tsql.h` changes without thread 0

CLAUDE.md: headers in `include/` change only through thread 0. The PR adds
`json_token`, `json_paint` and a parameter to `tsql_new` there. The change
itself is the smallest that does it (a private header would be one more
file), so this only needs thread 0's yes, recorded on the PR.

### 4. Shorter (no-duplication rule; `tools/dupes.py` from PR 66, run on this head)

At the gate's 50 tokens: no copy in `src/syntax` (measured, 1 run; the tree
fails only on other packages' lines, which PR 66's list and this main
disagree on). Below the gate, between json.c and tsql.c:

- `is_digit` and the token function's head (json.c:10, tsql.c:56), 40 tokens.
- The number's fraction and exponent (json.c:43, tsql.c:104), 40 tokens;
  gone with finding 2.
- The space test is written twice in `json_token` and is tsql.c's
  `is_space`; `is_digit` is tsql.c's too. One of each, shared, is shorter.
- The fill loop (json.c:81, tsql.c:218), 30 tokens: `json_paint` could
  return the face and leave the fill to `paint`'s loop, with the escapes as
  the only extra.

### 5. Notes, not blocking

- A third departure, not in the PR's list (measured): a string with a raw
  newline that closes on a later line (`["abc⏎", "d"]`) is one string in
  tree-sitter-json, without a syntax error; json.c ends it at the line's
  end, so the rest of that document is coloured shifted by one quote. Only
  invalid JSON does this, and ending at the line is the right choice while
  typing; but json.c's header comment ("a string ends at its line's end, as
  tree-sitter-json's string does") is true only for the unclosed one.
- A key far from its colon, or a string before a long comment, costs a read
  of the gap in every frame that shows it: 2.5 ms per MB of blank lines, 2.3
  ms per MB of comment (measured, 5 runs, `longstr` modes 2 and 3). Same
  class as the known open-comment cost; no real file looks like this.
- JSON's brackets, commas and colons are Catppuccin's overlay2, the
  comments' grey, as in Neovim. Davy's "not the comments' grey" was about
  T-SQL; if he wants it for JSON too, that is his call (hypothesis that he
  will notice).

## What holds

- **T-SQL operators (938dba3).** Three face names, one test mapping, the
  plant turned round. Sky (137,220,235) is used by no other T-SQL category
  (keyword mauve, string green, number and system function peach, sp_
  procedures blue, comments overlay2 italic), so the SSMS operator group
  reads as one colour and is far from the comments in hue and brightness.
  Nothing shorter does it.
- **JSON against Neovim, my own documents** (`reviews/pr-71-repro/cmp.sh`,
  measured, 1 run): 94 documents, 74 the same byte for byte, among them a
  2.5 MB pretty-printed one, a minified one, a 120 KB string of escapes,
  CRLF, UTF-8 keys, 200 nested arrays, comments between key and colon. The
  20 that differ: 12 are the listed top-level string, 1 is the raw newline
  above, 7 are documents tree-sitter-json finds a syntax error in.
- **The cache of a kind instead of a face** (tsql.c): T-SQL's faces are
  worked out per read now; the PR's before and after timing shows no
  difference, and finding 1's T-SQL row is the same path.
- **Plants** (measured, 1 run, `tools/planted.sh` on a tree holding only
  these files): json.txt 20, tsql.txt 51, syntax.txt 21, all 92 caught. My
  10 extras (`extra-plants.txt`, `plants.log`): 7 caught. Not caught: an
  escape scan that stops one byte earlier (an equivalent change: a closed
  string's last byte cannot be a backslash that escapes); `*/*` not closing
  a comment (no document has a comment right after another); an exponent
  without digits (`1e`, invalid JSON, no reference for it).
- **PR 64's report**: the cherry-pick is `reviews/` only and is what that
  review wrote.
