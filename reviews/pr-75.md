### 2. The comment on `full` says ":w to a new name" sets it; in Neovim that is true only for a buffer without a name

### 3. `full` has no stated value when `file_full()` fails, and that state is reachable

`file_full()` needs the directory to exist (include/file.h:67). The comment gives NULL only for
"without a name".

- **measured** (`pctF.sh`, 3 runs): `nvim nodir/new.txt` in a directory without `nodir` names the
  buffer `<cwd>/nodir/new.txt` and %F shows `~/proj/nodir/new.txt`; `file_full("nodir/new.txt")`
  returns -1 (ENOENT).
- **measured** (`missing_dir.c`, 3 runs, identical): `core_open("nodir/new.txt")` returns 0, the
  buffer's `path` is `nodir/new.txt` (message: E303, no journal), and `file_full()` on it returns -1.
  So a named buffer whose `full` cannot be computed exists today.
- **hypothesis** (not run): a path of PATH_MAX bytes or more fails the same way.

Neovim's fallback is the cwd, a `/`, and the name as typed. The header should say which Homeros
takes (that, or `path` as typed), or the bar shows "[No Name]" for a file that has a name.

HOME is T/home/u unless said):

### 4. The comment names `home_replace()`, which Homeros does not have; three of its rules are easy to miss

`make index | grep -c home_replace` prints 0: the name is Neovim's (`os/env.c`), and the comment
does not say so (include/file.h says "Neovim's ... (fix_fname())" for the same kind of reference).
What a first version written as `strncmp(path, getenv("HOME"), n)` gets wrong, each **measured**
above in live Neovim:

- A match counts only when the next byte is a separator or the end: T/home/u2/... keeps its
  path, HOME=/ replaces nothing, HOME itself is `~`.
- Neovim tries two homes: `$HOME` as set, and the directory it resolves to (`init_homedir()`
  changes into it and asks for the cwd, which also drops a trailing slash). `file_full()` resolves
  directories, so with HOME a symlink (or with `/home` a symlink, as on Fedora's image-based
  systems) only the resolved one ever matches. Resolving HOME is a syscall, so it is one more reason
  to cache.
- `build_stl_str_hl()` asks `buf_spname()` first and runs `trans_characters()` after: no name
  shows `[No Name]`, a control byte in a name shows as `^A`. Both happen at draw time, so NULL for
  "no name" is right; a buffer with `buftype=nofile`, a help buffer, a terminal and the quickfix
  list show other names (outputs in `pctF.out`), which matters for Homeros's scratch and terminal
  buffers when package 4 draws their bars.

Windows, **hypothesis** (read in Neovim's source, not run: no Windows Neovim here): `home_replace`
takes `$HOME`, else `%USERPROFILE%`; `path_fnamencmp` ignores case and treats `/` and `\` as equal;
the result keeps the path's own separators, so `file_full()`'s `C:\Users\davy\x` shows as `~\x`.
The comment's "(~/...)" is the POSIX spelling only.

Suggested comment, same two lines:
`/* %F before buf_spname() and trans_characters(): file_full() of path, then Neovim's
home_replace() (~ for $HOME or the directory it resolves to); set and freed with path; path
as typed if file_full() fails; NULL without a name */`

### 5. Low: the grid.h comment puts ^X under NonText; Neovim draws it with SpecialKey

**measured** (`nontext.lua`, 3 runs): `^A`, `<80>`, `<9f>` are SpecialKey. Catppuccin links
SpecialKey to NonText, so one face is enough and the pixels are right. The comment should say
"NonText ('@@@', the '<' and '>' fillers) and SpecialKey (^X), which catppuccin links to it", so
nobody later splits them or looks for ^X in Neovim's NonText code.

### 6. Low: is `full` better stored without the `~`?

Not blocking; for thread 0 to decide before package 4 codes against it.

- **measured**: `src/shada/shada.c:131` and `:140` already call `file_full(buf->path)` for every
  window's buffer at exit; Neovim keeps the unshortened `b_ffname` and shortens into a stack buffer
  when it draws. A `full` that holds `file_full()`'s result would serve both and remove those calls;
  the `~` then costs one compare per bar per frame (no syscall, no allocation, if the resolved home
  is computed once).
- As the PR has it, `full` has one reader, and shada keeps resolving a relative `path`.
- `src/tools/pick.c:79` `full()` and `src/git/keys.c:1275` are not the same rule (one does not
  resolve, one resolves the file too), so they would stay.

A cached field itself is right, **measured**: `file_full()` at draw time costs 1 `getcwd` for a bare
name and 6 `readlink` calls for a six-part absolute path (`strace`, 1 run each), 0.36 us (range
0.32 to 0.46) and 2.2 us (2.16 to 2.35) per call (5 runs of 100,000 calls each), per window per
frame; and Neovim's name does not follow a directory renamed after open, which a value computed per
frame would.

### 7. Low: three rows of `faces[]` are now the same bytes

**measured** (read in `ref/theme.c`): NonText equals "which-key separator" and "kitten dim"
({108,112,134}, `FACE_FG`); PmenuSbar equals PmenuSel without bold, and a scrollbar cell is a blank,
on which bold shows nothing. The table already keeps one row per Neovim group in places (LineNr and
EndOfBuffer are equal) and shares a row in others ("normal float: NormalFloat, WhichKey"). The new
rows follow the first habit; nothing to change unless thread 0 wants the second, in which case
PmenuSbar is the one row that could go.

### 8. Low: mini.statusline shows %F only in a wide window

**measured** (mini.nvim's `lua/mini/statusline.lua` on its main branch today, not Davy's pinned
revision): `section_filename` returns `%F%m%r` when the window is at least 140 columns, `%f%m%r`
below that, `%t` in a terminal. %f is the name as typed (`pctF.out` has it for every case), which is
`path` and needs no new field. Not this PR's to fix; package 4 should know `full` is half of it.
