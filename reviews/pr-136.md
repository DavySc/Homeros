## Findings that block

### B1. A Zig buffer whose first token is `?` crashes the editor (**measured**)

`src/syntax/zig.zig:302` reads `a.tokenTag(k - 1)` for a `?` token without asking `k > 0`. With `k = 0` the index wraps (ReleaseFast has no check) and the read lands 4 GB past the tags.

- `repro/q.c` linked with the PR's libraries: `./q '?u8'`, `'?'`, `' ?'` and a comment line followed by `?` all end in SIGSEGV; gdb: `zig.Ast.tokenTag` from `zig.colour` at `zig.zig:302`.
- In the editor (`repro/editor.py`, a pty, `build/gcc/homeros -t`): open an empty `a.zig`, type `i?`: `the editor died, status -11 (SIGSEGV)`. Unsaved text in other buffers goes with it.
- `repro/fuzz_zigrev.c` (B3) finds it after 177 runs.

Fix: `tg == .question_mark and k > 0 and ...` (with it, `q` passes and the fuzzer runs clean). The fix needs a test line and a plant.

The PR's evidence "153k parses, 0 panics" under ReleaseSafe did not reach this: its edits never made `?` the first token (**hypothesis** about why; the miss itself is measured).

### B2. `:w` formats with another release's formatter when the zig on PATH has no library of its own, and that breaks code (**measured**)

`zig_release()` falls back to the nearest or newest parser, which is fine for colours, but `keys_write_pre` then formats on every `:w` with it. zig fmt is not only layout: 0.17's rewrites builtins.

`repro/pick.py` and `repro/editor.py`, in the editor, one run each (deterministic):

| zig on PATH | formatter used on `:w` |
|---|---|
| none | 0.17's |
| 0.14.1 | 0.15's |
| 0.15.0, 0.16.0, 0.17.1 | its own (right) |
| 0.18.0 | 0.17's |
| a `zig` that answers after 2 s (a version manager's wrapper, a cold disk) | 0.17's, after the editor waited 1 s |

With no zig on PATH, `:w` of a Zig 0.16 file holding `_ = @intFromEnum(E.a);` leaves `_ = @backingInt(E.a);` on disk, and Zig 0.16 then answers `error: invalid builtin function: '@backingInt'` (the file passed `zig test` before). Over a whole std (`repro/fmt.out`, last 6 lines): 0.17's formatter changes 136 of the 472 files of 0.16's std it accepts, and 110 of 452 of 0.15's; 0.15's changes 2 of 0.16's and 2 of 0.17's, 0.16's changes 5 of 0.15's and none of 0.17's.

"No zig on PATH" is an ordinary case here: Homeros started from the desktop file does not have a project's nix shell on PATH (**hypothesis** for Davy's setup; the Windows work laptop without zig is the same case).

`research/zig.md` already says what to do ("If a project's version has no shim, spawn its `zig fmt` and colour with the nearest shim, saying so"). The smallest change: `syntax_zig_fmt` formats only when the release on PATH has its own library, and answers otherwise so `:Format` can say why; the DESIGN.md row's residual risk names what is left. Tests and plants for: no zig, an older zig, a newer zig.

### B3. The Zig path has no fuzzer in the repository (CLAUDE.md: a package adds its fuzzers; every merge runs them)

`tests/fuzz_syntax.c` picks among 7 languages, none of them Zig, so `make fuzz` never enters `zig.zig`, `syntax_edit`'s face shifting, `fold_zig` or `syntax_zig_fmt`. The PR's fuzzing was done outside the repo and is not repeatable from it. B1 is what that costs.

`repro/fuzz_zigrev.c` is `fuzz_syntax.c` with an eighth language (`f.zig`, 16 Zig tokens including `?`) and `syntax_zig_fmt` called at any moment. Runs (**measured**, 1 each, `-max_len=256`):

- PR's libraries: SEGV at `zig.zig:302` after 177 runs.
- B1 fixed locally, PR's build (ReleaseFast, ASan on the C side): 1,446,586 runs in 301 s, clean.
- B1 fixed, the libraries built ReleaseSafe (Zig's own checks on): 0.17's 1,311,048 runs in 301 s; 0.15's 954,835 and 0.16's 940,453 in 151 s each (a fake `zig` on PATH picks them; `pick.py` shows the pick works). All clean.

Asked: Zig as a language of `fuzz_syntax.c` (or a `fuzz_syntax_zig.c`), with a plant. Since the editor's build cannot stop on a null in a broken tree (the DESIGN row's own residual risk), fuzzing the ReleaseSafe build in `make fuzz` would be the check that sees it; at least record how to do it.

### B4. The speed numbers in DESIGN.md and `syntax.c` are the prototype's parse alone, not what the editor does per edit (evidence rule)

The DESIGN row and `zig_parse`'s comment say "full reparse median 0.054 ms, p99 1.3 ms an edit against tree-sitter's incremental 0.079 / 5.8 ms". That was `Ast.parse` alone. An edit in the editor is `syntax_edit` + `syntax_update`: copy the text, parse, colours, fold spans, face mapping, every row's fold level.

`repro/bench.c` (the PR's `syntax.c`, `-O2`, 80 one-byte inserts at random places in each of Zig 0.17's 563 std files, 45,040 edits, 5 runs, **measured**; `repro/bench.out`):

| | median (range over 5 runs) |
|---|---|
| one edit, median | 0.195 ms (0.191 to 0.198) |
| one edit, p99 | 6.63 ms (6.06 to 6.75) |
| one edit, max | 26.1 ms (22.5 to 33.8) |
| largest file (`Io/Threaded.zig`, 829 KB), median edit | 15.5 ms (15.1 to 16.2) |
| open, median / largest | 0.29 ms / 23.2 ms |
| zig fmt, median / largest | 0.16 ms / 10.5 ms |

`repro/parts.c` on the largest file (best of 20, 3 runs): parse alone 4.4 to 4.5 ms, parse with colours and fold spans 17.4 to 17.6 ms. So colours and folds cost about three times the parse, and the mechanism as shipped is 3.6 times the quoted median and 5 times the quoted p99; on the row's own comparison it is behind tree-sitter's incremental parse numbers (which leave out tree-sitter's queries, so the comparison was never like for like).

`syntax_update` never asks `stop` for Zig, so in the largest file each key is followed by about 15 ms in which the next key waits; `syntax.h`'s contract for `syntax_update` ("in slices ... returns nonzero when input is waiting") does not say Zig is the exception, and package 12's gate is "frame budget held".

Asked: the row and the comment state the measured cost of the shipped path (with run counts), and `syntax.h` gets its sentence through thread 0. Not asked for this PR, but the obvious next step under Davy's top rule: most of the 13 ms is not the parse (`tokenSlice` lexes each token again, twice per token in `colour`, and once more in the comment scan); **hypothesis**, not profiled.

## zig fmt equivalence (**measured**)

`repro/fmtcmp.c` links the PR's three libraries and compares `zigNN_fmt` with `zig fmt --stdin` of the same release (nixpkgs' 0.15.2, 0.16.0, 0.17.1) on that release's whole std (540, 550, 563 files), as is and changed six ways so the formatter has work: no indent, a quarter of the newlines joined, no comma before a newline, doubled spaces with tab indents, CR LF, one byte in 2,000 deleted. `repro/fmt.out`:

- 21 runs over 11,571 texts: **0 differ, 0 where only one side refuses**; both refuse 2,983 (broken by the change), identical 8,588, of which the formatter changed 5,894.
- The PR's own test only checks that std comes back from itself without indents, for the one release on PATH.

So "in-process zig fmt is `zig fmt`" holds for the matching release. (B2 is about the non-matching one.)

## One mechanism, duplication, the keys change

- `fold_count` is shared by `fold_tree` and `fold_zig`; the prefix/suffix trim is one piece for verible and zig fmt; `zig version` goes through `proc_spawn`/`proc_wait` as verible does. `make dupes` passes. No second way to do an existing thing found.
- `buf_format`'s callers all ask `fmt_kind()` first, so the new `else` branch is never reached with kind 0 (read, and `test_keys_gq` passes).
- Each library: 6 exported functions, only libc names undefined (`nm`, **measured**); 2.6 to 2.8 MB each.
- `zig_release()` blocks the open of the first `.zig` file on `zig version`: 7 ms here (**measured**, 1 run), up to the 1 s limit with a slow wrapper (B2's table).
