## Findings

1. **`make check` red: `z` and a key above U+00FF** (measured, fuzzer plus typed cases). `nv_zet()` looks the key up with `strchr("ocaRM", c)`, which takes `c` as a `char`. `z` + U+0100 gives the terminator, `i` = 5, and `op[5]` is read: UBSan "index 5 out of bounds" at `src/keys/normal.c:1321` (fuzz_keys_all input `04 ae 61 01`, saved as `pr-147-repro/fuzz_keys_all-crash`; typed `zĀ` aborts the same way). `z` + U+016F (`ů`, low byte `o`) acts as `zo`: `jzczůj` ends on line 3 with the fold open, Neovim on line 8 with it closed. The `c &&` guard only covers 0.
2. **`>>`, `<<` and Visual `>` on a closed fold do not open it** (measured, static foldexpr and `vim.treesitter.foldexpr`). Neovim's `op_shift()` ends with `foldOpenCursor()`. `j zc >> j` on `t.h`: Neovim opens 2/8 and lands on line 3; Homeros keeps it closed and lands on 9.
3. **`p` / `P` on a closed fold, then `u`: the cursor differs** (measured, both oracles). `yy j zc p u`: Neovim line 2, Homeros 8. `yy 3G zc P u`: Neovim 3, Homeros 2. `do_put()` here moves `W->line` to the fold's edge before `u_save()`; Neovim's comment there is "Don't move the cursor yet, u_save() uses it". Moving the line after `u_save()` alone did not make the cases agree (tried, 1 run), so the core's cursor rule for undo is involved too.
4. **`fold_open_cursor()` tests the wrong thing** (measured by the core thread, files in project files `reviews/pr-147-undo-folds/`; I reran only `j zc k dd u`, which agrees). Neovim's `foldOpenCursor()` tests `hasAnyFolding()` and then opens what holds the cursor, including a closed fold of one line that `checkSmall()` shows open. Homeros tests `has_folding(cursor line)`. `jzc 9G zc k dd u`: after the parse Homeros closes 2/8 and 9/10 again, Neovim leaves them open. Their suggested line: `if (W->fold) core_fold(E, FOLD_VIEW, W->line, 0);`.

## On the test

The fold phase compares cursor, error and text; whether a fold is open shows only through a later move. Comparing `foldclosed()` of each line costs one line in the oracle and one loop in the test, and found nothing on the PR's key set (4,500 cases), so the keys there are right; it would make the 'foldopen' plants direct.

Its foldexpr is a list of levels by line number. That is valid only while the text is unchanged, which is why edits come last. Findings 2 to 4 all need an edit followed by a key. For those the right oracle is tree-sitter folds on both sides with the parse run between keys, as the core thread's driver does (`pr-147-repro/ts-folds.lua`, `reviews/pr-147-undo-folds/test_zz_undo.c`).

## Withdrawn

Two things I first reported do not hold and are recorded so nobody repeats them:

- "`o` on a closed fold leaves it closed where Neovim opens it." True against a static foldexpr (`jzco`: Neovim joins the line to the fold and `edit()` opens it). With `vim.treesitter.foldexpr`, Davy's configuration, Neovim leaves 2/8 closed and `j zc ox<Esc> k` is identical in both (measured, 1 run).
- "`core_undo()` does not shift folds when lines come back." The core's adjust is Neovim's `foldMarkAdjust()` (core thread, measured with `foldmethod=manual`); the static expr hid that by re-evaluating synchronously. `j zc k dd u` agrees with tree-sitter folds (measured, 1 run).

A static foldexpr is re-evaluated inside `changed_lines()`; tree-sitter folds, like Homeros's, update after the parse. Any fold case with an edit in it must be checked against the second.

Also seen, not this PR's: `j=5j` differs from Neovim without any fold (text differs), in the content-based probe.
