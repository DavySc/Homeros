# Review of PR 172: snip: columns from the buffer's database connection (package 19)

Reviewed head f17fa01d286d544ff2ace028035ecada7b05b8db, on main eafbdd33 (no merge needed).
Reviewer thread "Review SQL live completion PR 172", 2026-11-27. Everything below is
**measured** unless tagged; probes and plants are in `reviews/pr-172-repro/`.

## Verdict: changes requested

The feature works: `d.` after `join dom d` lists the live columns on SQL Server and
PostgreSQL, completion never dials, and the fallback without a connection is main's
behaviour at main's speed. But the catalog is kept per buffer and searched linearly,
and that costs time in the key path that grows with the database: A and B below break
DESIGN.md's gate (frame ready under 2 ms p99 after a key), and C shows another
database's columns.

Setup: SQL Server 2022 and PostgreSQL 17 in Docker on 127.0.0.1; databases `big`
(2,000 tables of 50 columns, 100,004 columns) on both, `big200`/`big500`/`big1000`
(10,004 / 25,004 / 50,004 columns) on PostgreSQL, `cs` (Latin1_General_CS_AS, tables
`Dom` and `dom`) on SQL Server. Timings: `p172.c` built -O2 without sanitizers
(`mko2.sh`) against the PR head and against main, pinned to one core while `make
check` ran on the other three; 300 keys per run; main and PR alternating.

## Findings

### A (blocking): every buffer switch reads the whole catalog again

`scan()` reads the catalog when `I.catb != e->buf`. Two SQL buffers on one connection
(the usual case: a folder's default connection) therefore re-read, re-intern and
re-sort all of it at every switch, in the loop turn after the first key, or in that
key if it starts a word. `p172 switch CONN 40` (a.sql and c.sql in one folder, 40
switches per run):

| catalog | loop turn after a switch, median per run | a word typed at once after a switch |
|---|---|---|
| main, 100,004 columns (3 runs) | 0.025 to 0.031 ms | 0.30 to 0.42 ms |
| PR, 10,004 (3 runs) | 5.3 to 6.3 ms | 5.0 to 6.6 ms |
| PR, 50,004 (3 runs) | 33.3 to 34.9 ms | 26.2 to 36.8 ms |
| PR, 100,004 (5 runs) | median 64.9 ms (61.0 to 67.2), worst turn 116 ms | median 60.3 ms (59.3 to 64.7) |

The PR's description measured this (32 to 47 ms at 50,002 columns) and accepted it.
With frames on three monitors a switch is one key. Also once per login: the first word
start after the catalog arrives walks it twice in the key (`collect()` calls
`sql_catalog(..., column, ...)` as its question, which already builds every fact, then
`scan()` throws that away and reads again): 84.1 ms median (83.5 to 113.2, 5 runs) at
100,004 columns, 38 ms at 50,004, 7 to 9 ms at 10,004 (3 runs each); main 0.04 ms.

Wanted: the catalog's facts built once per catalog (per connection and read), off the
key, and kept across buffers. Package 19 cannot tell today whether two buffers share a
catalog or whether it changed; that probably needs something from `sql_catalog` (thread
0 and package 22), for example a value that changes when the connection's catalog does.

### B (blocking): a dot walks every fact of the catalog

`collect()`'s merge loop tests each of the index's facts with `is_of()`; with the
catalog in the index that is every column of the database at every word start after a
dot (`p172 time CONN 300`, key `.` after the alias `d`):

| catalog | `.` median per run | p99 per run |
|---|---|---|
| main, any (5 runs) | 0.005 to 0.009 ms | 0.022 to 0.062 ms |
| PR, no login (6 runs) | 0.005 to 0.016 ms | 0.026 to 0.135 ms |
| PR, 10,004 (3 runs) | 0.36 to 0.46 ms | 0.61 to 0.77 ms |
| PR, 25,004 (3 runs) | 0.90 to 1.54 ms | 1.66 to 2.13 ms |
| PR, 50,004 (3 runs) | 1.74 to 1.81 ms | 2.84 to 4.19 ms |
| PR, 100,004, SQL Server (5 runs) | median 3.88 ms (3.71 to 5.57) | 5.9 to 10.6 ms |
| PR, 100,004, PostgreSQL (3 runs) | 3.52 to 3.68 ms | 6.2 to 6.6 ms |

About 0.036 ms per 1,000 columns; over the 2 ms gate from about 25,000 to 50,000
columns. A plain word start grows less: 0.317 ms median on main (0.29 to 0.38) against
0.638 ms (0.625 to 0.667) at 100,004 columns, 5 runs each. Keys inside a word are
unchanged (0.01 ms). `sql_catalog` hands the columns over grouped by table, so the
columns of one table can be found without a walk (hypothesis: a binary search over the
catalog's own order).

### C (blocking with A): after `:Connect` the popup shows the old database's columns

`p172 conn pg cs`, 3 of 3 runs: F5 on `pg`, `d.` lists `id kind Name status`;
`:Connect cs`, F5 (its catalog arrives: 4 rows), wait 1.5 s, `d.` still lists
`id kind Name status`; only after another buffer was visited `Id Kind kind2
lower_only`. The PR lists this under Residual. Columns of the wrong database are worse
than none, and the fix for A (know which catalog the facts are from) fixes it too.

### D (not blocking): tests miss most of the new code's rules

`review-plants.txt`, each against test_snip_sql alone (`prun.py`): 1 of 6 caught.
Not caught: the first buffer's catalog kept for every buffer; the catalog read at
every index build (the cost the PR says it avoids); the index made again at every
word start once the catalog is in; the catalog's tables never offered (after FROM);
the catalog's spelling of a name winning over the file's. Caught: columns filed under
their schema. The first three need a second buffer or a count of reads in the test.

### E (not blocking, notes)

- Case-sensitive database (`cs`): the columns come (`Id Kind kind2 lower_only` after
  `d.` for `join dom d`), so PR 168's finding B stays fixed through the popup. Names
  that differ only in case are one name to the index (`by_fact` and `is_of` use
  strcasecmp): `Dom` and `dom` are two tables there and `d.` lists the columns of
  both; `from d` offers `dom` once. Rare; SSMS keeps them apart.
- A table that exists in two schemas has its columns merged the same way (read from
  the code, not run: hypothesis).
- Without a connection every word start and every index build calls `sql_catalog`,
  which looks for the connections file again (`lookup`): `.` 0.013 to 0.016 ms
  against 0.009 to 0.010 ms on main with no connections file (3 runs each), about
  5 microseconds a word start.
- F5 itself still blocks for the name lookup when the name server is silent (10.0 s,
  3 of 3; main's behaviour, package 22's, not this PR's).

## What holds

- Davy's case, live: `select * from app a join dom d on d.` in a file that names no
  column offers nothing before a login and `id kind Name status` after F5 in another
  buffer of the folder, on SQL Server (54 and 100,004 columns) and PostgreSQL (6 and
  100,004); `where k` in a one-table statement ranks the live column `kind` first.
- No freeze when the server is away: with a name server that never answers, `.`
  before any F5 takes 0.12 to 0.57 ms (3 runs) and nothing is dialled; while F5's
  login is tried, 2,700 dots per run take 0.02 ms median, 0.4 ms at most, longest
  loop turn 5.8 ms (3 runs). Same against a refused port.
- No connection: main's popup (the file's own columns, PR 167), main's speed.
- `make test TESTS="snip snip_sql"` passes at the head (1 run; test_snip_sql: the
  columns after 16 loop turns).
- PR 167's follow-ups are in: OFFSET and MATCHED no columns, the two tests, the
  report merged.
