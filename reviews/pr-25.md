## The MoveFileExW choice

- **measured** (`replace.c` under `strace`, 1 run each): Wine performs `ReplaceFileW` as three Linux calls, `rename(file, rfXXXX.tmp)`, `unlink(rfXXXX.tmp)`, `rename(temp, file)`, and `MoveFileExW` as one `rename(temp, file)`. So the PR's 26 to 38 of 200 against 0 of 200 compares Wine's own three-step sequence with Linux's atomic rename. It is a true measurement of Wine and says nothing about NTFS in either direction.
- What does hold for real Windows is Microsoft's page for ReplaceFileW (read 2026-11-17), error 1176 ERROR_UNABLE_TO_MOVE_REPLACEMENT: "If lpBackupFileName was specified, the replaced and replacement files retain their original file names. Otherwise, the replaced file no longer exists and the replacement file exists under its original name." Without a backup name the call has a documented state with no file at the path. That is enough to drop it as DESIGN.md wrote it.
- The alternative the PR does not compare is ReplaceFileW *with* a backup name, which keeps the attributes and, by the same page, both files on that failure. It is still several steps, and neither page says what a kill between them leaves, so it is not better on evidence; it should be in the comparison.
- What the rename gives up, from the same page's list of what ReplaceFile preserves: creation time, short file name, object identifier, DACL, security resource attributes, encryption, compression, named streams. **measured** under Wine (`probe.c` step 1): a hidden or system file comes out with neither attribute. The PR names the ACL and the hidden and system attributes; an individually encrypted (EFS) file coming out as plain text is the one worth adding.
- Microsoft's MoveFileExW page does not state atomicity. Git for Windows, libuv, Go and Rust all replace files this way, which is the practice the PR copies. Real NTFS (a kill during the rename, both calls) stays a phase 1 measurement on Davy's machine; until then the row is a hypothesis, as the old one was.

## Findings to fix before merge

### 1. The identity kept after a save is read from a handle that is still open for writing

`file_save` takes `mine` with `ident(h, &mine)` and only then closes `h`. Microsoft's "File Times" page (read 2026-11-17): "When writing to a file, the last write time is not fully updated until all handles that are used for writing are closed", and "The only guarantee about a file time stamp is that the file time is correctly reflected when the handle that makes the change is closed." If NTFS moves the time at the close, the FileId the editor keeps differs from the file's: the watch then reads a change (W11 at the next edit) and the next plain `:w` is refused with E13, after every save. **hypothesis** from the documentation: Wine keeps Linux's mtime, so `test_file_win`'s "one identity across saves" passes here and would be the check that fails on Windows. The fix costs nothing and is right on both: close the temp, then take its identity by its own name before the rename (the name is ours, and the rename changes none of volume, index, size or time).

### 2. The journal's lock is its share mode, so any reader of a leftover journal looks like a second editor

`state_open` opens the journal with `FILE_SHARE_DELETE` only. **measured** under Wine (`probe.c` step 3, 1 run): a child journals an unsaved change and is killed; while another process holds the 169-byte journal open for reading with full sharing (what a virus scanner, a backup or an indexer does), `journal_open` returns -1 with EWOULDBLOCK, which the core reports as E303 "another editor has it open" and opens the file's text without the recovery; once the reader closes, the same call recovers. A scanner looking at a file just left by a crash is the likely moment on Windows. An exclusive `LockFileEx` (fail immediately) on a byte past the data, on a handle opened with full sharing, keeps a second editor out, goes with a crashed process, and lets readers be.

### 3. The comment and the PR text state Wine's behaviour as Windows'

`win.c`'s head comment and the PR say ReplaceFileW "removes the file and then moves the temp in". That is Wine's implementation (the trace above). Please say what was measured where (under Wine, of Wine), cite Microsoft's error 1176 for Windows, add ReplaceFileW with a backup name to the comparison, and list what the rename gives up, encryption included. The plant "ReplaceFileW, which is not crash-safe" is caught under Wine for the same reason; say in its name or the test that on Windows it may not be.

## Smaller, to record

### 4. A file another program holds open cannot be saved, and neither can a read-only one, even with `:w!`

**measured** under Wine (`probe.c` steps 1 and 2): with a reader holding the file open without delete sharing (most Windows programs), `file_save` returns SAVE_ERR (EACCES), forced too; the file and directory are left clean. The same for a file with the read-only attribute. Windows' sharing rules give the first on NTFS as well (hypothesis). Git for Windows, whose way of saving this copies, retries the rename for a short while because scanners hold files briefly; Vim's `:w!` clears the read-only attribute. Add both to "Not done" so phase 1 measures how often a save fails on Davy's machine with the Lean server and OneDrive running.

### 5. Hidden and system attributes could be kept

One `GetFileAttributesW` on the file and `SetFileAttributesW` on the temp before the rename keeps them. Optional; the PR records the loss as a hypothesis about Davy's files.
