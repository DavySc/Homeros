# Review of PR 148: Lean colours from the server (semantic tokens) and LSP on Windows

Package 13 (`src/lsp/`), with thread 0's hooks in `include/` and `src/core/`. Reviewed at
`c090f77` (code as `eb0ab40b`; the commit on top changes only `.github/workflows/check.yml`),
which holds main `5e38c687`. Reviewer: a separate Fable 5.2 thread, 2026-11-24.

**Verdict: changes requested.** The mechanism is the right one and it is small: one token
set per file that reuses the diagnostics' `Set` and `shift_set`, one hook the core draws
through, tokens laid over the grammar. It works end to end against the real Lean server and
it combines with PR 144's Lean grammar with no extra code. Five things stop the merge:

1. On a long Lean file the server's colours stop part of the way down and stay that way.
2. One token answer holds the event loop for over 2 ms on the project's own stand-in file,
   and for over a second on one long line.
3. An older plant no longer applies, so the train's plant run would be red.
4. The new tests miss most of what the new code does: 14 of my 18 plants pass.
5. The CI job the last commit adds fails, and the Windows job is skipped behind it.

Every claim below is tagged **measured** (with the run count), **read** (source read, not
run) or **hypothesis**. Repro files are in `reviews/pr-148-repro/`.

## What holds

## Findings

### 1. On a long Lean file the colours stop part of the way down (blocking)

Lean does not hold a `semanticTokens/full` answer until the file is elaborated. After about
3 s it answers with the tokens of what it has elaborated so far, and later asks the client
to ask again with `workspace/semanticTokens/refresh`. The PR answers that request with
`null` like every other server request and does not offer `refreshSupport`, so the first,
partial answer is all the editor ever shows until the next edit.

- **Measured, 4 runs** (`e2e long/Long.lean 30`, the 3,219-line file of
  `src/lsp/bench/gen_lean.py`, real `lake serve`, nothing typed): the last coloured byte was
  on line 976, 692, 994 and 735 of 3,219, still so after 30 to 40 s. With a space typed at
  line 1,100 after 12 s (1 run): colours to line 2,026 of 3,219, 28 s later.
- **Measured, 1 run** (`leanpartial.py`): the answer to the request at open came at 3.6 s
  with 2,970 tokens ending on line 1,034; Lean sent `workspace/semanticTokens/refresh` at
  5.7 and 7.6 s; a request after elaboration (7.9 s) got 9,240 tokens to line 3,219.
- **The reference, measured, 1 run** (`nvimtok.lua`, Neovim 0.12.6, same file and server):
  4 token requests, 1 refresh from Lean, 9,240 tokens held, the last on line 3,219.

The machine was running `make check` beside these, so Lean was slower than on Davy's
laptop and the cut would come later there. The mechanism does not depend on that: any file
Lean needs more than about 3 s for is cut (hypothesis for the exact limit; I did not find
it in Lean's source).

What I would do: what Neovim does. Offer `workspace.semanticTokens.refreshSupport` and, on
that request, call `tokens()` for the server's files (Neovim debounces these, "some LSPs
send rapid fire refresh notifications"; here each request cancels the last, which may do). It is a few lines in the branch of
`handle()` that already answers server requests. The test needs a fake that answers
partly, then asks for a refresh.

This also changes what the debounce measurement shows. `bench/tokens.py` stops at the first
answer for the final text, and that answer is the partial one: with the count printed
(`tokens-count.py`, **measured**, 4 of 4 runs) it ended on line 1,937, 2,552, 2,391 and
1,862 of 3,219. So "3285 ms against 3283 ms" compares Lean's own timer on both sides, not
the debounce. The CPU numbers (16.7 s against 16.9 s) still stand. Please measure again to
the whole file's tokens once refresh works, since the refresh adds requests.

### 2. One answer holds the loop over 2 ms; one long line holds it over a second (blocking for the long line)

`hold.c` runs the editor's modules against `fake.py`, a server that answers with a token on
every word, and times each `loop_once(0)`. **Measured**, 6 answers each unless said, `-O2`, the check
running beside it:

| File | Tokens | Longest loop turn per answer |
|---|---|---|
| 3,219 lines, 3 tokens a line (the stand-in's size: Lean sends 9,240 for it, 142 KB) | 9,657 | 2.1 to 3.4 ms (12 answers, 2 runs) |
| 1,500 lines, 3 a line | 4,500 | 1.0 to 1.4 ms (5 answers) |
| 10,000 lines, 5 a line | 50,000 | 12 to 21 ms |
| one line of 10 KB | 5,000 | 65 to 107 ms |
| one line of 40 KB | 20,000 | 1.1 to 1.6 s |

`json_parse` alone is 0.93 ms of the first row and 5.1 ms of the second (`jp.c`, best of
20). The rest is `decode()`. Its long-line cost is quadratic: `lsp_u16_byte(b, n, c)` walks
from the start of the line for each token, twice. Walking on from the last token's column
makes it linear and should take most of the first row's `decode()` share too.

The long line must be fixed: typing stops for a second per answer. The 3 ms on the
stand-in I leave to the author with a number to beat: it is one loop turn per answer, not
per frame, and PR 27's review accepted about 3 ms for 1,000 diagnostics. But with finding 1
fixed the whole file's answer comes after every pause in typing, so please measure it on
the real path and say where it lands against the 2 ms gate.

### 5. The PR's new CI job fails, and takes the Windows job with it (blocking)

See "The check": `winexe` fails on a fresh tree because `winlink` needs tree-sitter's
sources fetched first, and `windows` is skipped behind it. Either `winlink` makes
`build/syntax/src` itself or the job runs `make wincc` first (thread 0's files).

### 6. Smaller points (not blocking)

- **An error answer clears the colours (measured, `hold 50 5 3`, 1 run).** When the server
  answers the latest request with an error, `decode()` runs with no array and empties the
  set: colours shown go away and nothing asks again. Neovim logs the error and leaves the
  highlights alone (read, `semantic_tokens.lua` line 355 of 0.12.6). Real Lean never did this to the latest request in my runs.
- **Two colours differ from the themes the editor copies (read, not run in either editor).**
  `ref/theme.c` copies catppuccin/nvim, whose `semantic_tokens.lua` sets
  `@lsp.type.variable = {}` (the grammar's colour stays) and `@lsp.type.enumMember` to
  teal; the PR paints `variable` with the text colour and `enumMember` peach. For Lean
  under VS Code, which PR 144 follows, Catppuccin's theme has no rule for `property`, so
  fields keep the text colour there, while the PR draws them lavender (as Neovim does).
  Keyword and variable come out the same as VS Code. Worth one decision and a comment:
  which editor the token colours follow for Lean.
- **`src/lsp/check.sh` and `src/tools/check.sh`** are now the same 15 lines but for the
  test's name and the Wine prefix. One function in `tools/winpass.sh` beside `winlink`
  would leave each a line.
- **`lsp_open` no longer gives a file in a directory that does not exist a server**
  (`file_full` needs the directory; `absolute()` fell back to the working directory), and a
  symlinked file keeps the link's name in its URI, as Neovim's. Both look right; neither
  has a test.
- The log file of `test_lsp` is now `/tmp/homeros-lsp-<pid>` made with `fopen`, where it
  was `mkstemp`. Tests only.
