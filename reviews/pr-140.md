**Verdict: changes requested.** The design is right and the speed claim is better than the PR
says: on Windows itself a scroll is 19 times faster than GDI's and a whole redraw 5.6 times,
for 14 microseconds more per typed character. One mechanism holds (no GDI text is left, the
owners check catches a second path, Wayland and Windows run the same painter). Five things stand
in the way: a font-numbering bug in `dwrite.c` that costs a 0.46 s freeze and half the font
table for one emoji-style character (1); a one-line change that makes the typing frame's drawing
4 times faster on Linux and takes back part of the Windows cost (2); drawn glyphs whose tests let
four of five planted bugs through (3); `test_win_font` fails on Windows itself (4); and the
wallpaper half now in the PR is PR 135 at a head that has changes requested (5).

## Speed

### Frames on Windows itself (measured)

`src/win/probe/frames.c` (the PR's) linked with main's backend (GDI), the PR's, and the PR's
with `span0.diff` (finding 2); `winprobe.sh` builds FreeType and HarfBuzz with zig as
`windows.nix` does. 5 alternating runs of 200 frames, a 34 by 102 window; the range of the 5
medians:

| | main (GDI) | PR | PR with `span0.diff` |
|---|---|---|---|
| whole screen | 12.60 to 12.73 ms | 2.24 to 2.29 ms | 2.22 to 2.31 ms |
| one changed character | 44 to 46 us | 58 to 59 us | 52 to 54 us |
| text moved up a row | 13.20 to 13.42 ms | 0.66 to 0.72 ms | 0.64 to 0.70 ms |

The same under Wine 11 here (39 by 128, 5 alternating runs, the machine also running the check):
whole screen 4.86 to 5.00 ms against 3.32 to 3.46; one character 27 to 28 us against 44 to 45
(one run 79); a row up 3.38 to 3.44 ms against 0.63 to 0.71. So the PR's Wine numbers reproduce
(typing 1.6 times GDI's, the PR says 31 against 19), and Wine understated the gain: on Windows a
scroll is 19 times faster, not 3.7, because GDI's text is much slower there than under Wine. The
runner has no monitor, so what `BitBlt` to a visible window costs on Davy's laptop is still a
**hypothesis**; README and DESIGN.md should carry these numbers in place of "under Wine only".

The typing frame is the one thing slower: 14 us more, 0.2% of a 144 Hz frame. The second run
(on `101bba2d`, no wallpaper set) agrees: 12.62 to 13.35 ms, 44 to 45 us and 13.24 to 16.88 ms
for GDI; 2.24 to 2.33 ms, 57 to 58 us and 0.64 to 0.70 ms for the PR.

### Over a wallpaper, Windows itself (measured, `101bba2d`, a 1920 by 1080 picture)

Same probe and runs, `XDG_CONFIG_HOME` pointing at the picture:

| | PR, no wallpaper | PR, wallpaper | with `span0.diff`, wallpaper |
|---|---|---|---|
| whole screen at a new size (`make_dib` runs) | 2.24 to 2.33 ms | 17.97 to 18.23 ms | 17.86 to 18.50 ms |
| one changed character | 57 to 58 us | 47 to 49 us | 41 to 42 us |
| text moved up a row | 0.64 to 0.70 ms | 1.72 to 1.81 ms | 1.73 to 1.80 ms |

- A scroll over a wallpaper redraws its rows instead of copying them: 2.6 times the cost
  without one, and still 7 times faster than main's GDI scroll with no wallpaper (13.3 ms). PR
  135's own Windows drawing would be GDI's time and half again. So the per-cell cost that
  PR 135's review found is gone here.
- A new size costs 16 ms more with a wallpaper: the HALFTONE `StretchBlt`, as PR 135's review
  measured. Inherited (finding 5).
- Typing is faster over a wallpaper than without one, because the scroll search and its
  memcmp of every row are skipped there: that pass costs about 10 us on Windows. With
  `span0.diff` typing over a wallpaper is 41 to 42 us, under GDI's 44. Without a wallpaper
  `span0.diff` as written compares the rows twice (the gate, then `paint_span`); one pass
  shared by both would bring the usual typing frame to about GDI's time. The author's to shape.

### Fonts on Windows itself (measured, 1 run of `fontprobe.c`, 3 processes for `font_open`)

- **Start-up**: `font_open` takes 1.7 to 2.9 ms the first time in a process (3 processes), 0.3
  to 0.7 ms again. No font is scanned at start-up; Linux's is 3.2 ms (README). Under Wine the
  first call takes 235 to 269 ms, which is Wine's DirectWrite, not Windows'.
- **A character's first look** (once per `font_open`, inside the frame that first shows it):
  ✦ 29 ms (the first fallback of the process, Segoe UI Symbol), ↻ 3.8 ms, ⏵ 5.3 ms, 𝓝 6.7 ms,
  ❤️ 8.2 ms, a ZWJ family 13.8 ms, 😀 93 ms (Segoe UI Emoji's first load), 中 219 ms (Yu
  Gothic's first load). Again: 2 to 44 us. Linux's worst first load is 3.9 to 17.4 ms (README).
  WezTerm resolves fallback off its drawing thread; Homeros has one thread, so these are frames
  that long. The file is not the cost (`blobprobe.c`, 1 run, files not read before in the
  process): HarfBuzz's blob of a 9 to 18 MB CJK file takes 0.1 to 0.4 ms (it is mapped, not
  read), FreeType's face 6.7 ms for Yu Gothic (17 to 30 ms for MS Gothic, SimSun, Malgun), its
  first glyph 0.8 ms (13 ms for MS Gothic and SimSun, 138 ms for Malgun Gothic). So most of the
  219 ms is DirectWrite's side (`MapCharacters` for a new script, `CreateFontFace`): a
  **hypothesis** until the author times the calls.
- **A character no font has**: 70 to 87 us each (the scan of every family is cheap on Windows);
  remembered, 0.1 to 0.2 us each. After 768 answers the table is emptied and the first 30 cost
  2.4 ms again, as built.
- **Colour**: Segoe UI Emoji draws in colour through FreeType without PNG (😀: 225 pixels with
  unequal channels; ❤️ and the ZWJ family too). The PR's hypothesis is now measured.

### Fallback answers, Linux (measured, the PR's `bench/fallback.c`, 5 alternating runs)

No font: 391 to 453 us a row on main, 8.7 to 9.4 on the PR. ✦: 44.6 to 48.4 against 33.6 to
37.2 (faster, the PR says no difference). ─: 6.3 to 6.6 against 5.5 to 6.1. The claim holds.

## Findings

1. **`dwrite.c` numbers every font it looks at while it hunts for a colour font; one
   emoji-style character costs 0.46 s and 33 of the 64 font numbers** (measured on Windows
   itself, `fill.c`). A cluster with U+FE0F whose character plain fonts have (©️ ™️ ⚠️ ✔️ ▶️)
   asks for colour fonts only. `MapCharacters` is asked without the U+FE0F (font.c drops
   ignorables), answers a plain font, and the scan then walks every family; `take()` calls
   `add()` first, which gives a number to each family that has the character, and only then
   refuses it for not being a colour font. Windows runner, 2 runs on 2 machines: the first ©️ took
   459,610 and 268,466 us and the table went from 1 to 34 fonts; the next clusters 3.3 to 11 ms
   each. Wine with CI's fonts: 37
   to 56 ms, 2 to 48 fonts; with 100 more font files: 2 to 63, and 64 (full) two clusters later.
   At 64, `add()` answers -1 for every new font, so from then on a character draws only if one
   of the 64 has it (by reading; not reproduced, since under Wine unifont is among the 64 and
   has everything). Davy's laptops have more families than the runner. `number.diff` (shorter
   than the code it replaces: `take()` goes) asks the colour before numbering; with it the same
   run numbers 2 to 3 fonts under Wine and `test_win_font` passes; on Windows itself 1 to 2
   fonts, and the first ©️ took 799 us. That last number is not a fair before and after: the
   patched program ran right after the unpatched one, with Windows' font cache warm, so how much
   of the 0.27 to 0.46 s the patch removes is a **hypothesis**. If the scan stays slow when
   cold, giving `MapCharacters` the U+FE0F or asking Segoe UI Emoji's family first would skip
   it; the author's to choose and measure on Windows (`winprobe.sh` is there).
2. **The painter compares every cell of every row on every frame; one `memcmp` a row first makes
   the typing frame's drawing 4.3 times faster on Linux** (measured above: 24.7 to 5.7 us) and
   takes 6 of the 14 us back on Windows (58 to 52). `span0.diff` is one line in `paint_span`
   (a row without the cursor in either grid that compares equal has no span), so Wayland's
   second compare against its other buffer gets it too. Davy's rule is that no cycle is wasted,
   and this is the frame he feels most.
3. **Four of five bugs planted in the drawn glyphs pass the tests.** 164 characters are drawn;
   `test_font.c` checks that each has ink and the cell's size, and the shape of 11. Not caught:
   heavy lines drawn light, every lower block (▁ to ▇) drawn full, Powerline's separators
   mirrored, dashes drawn solid. Davy's report was a block bug. Each class needs a check and a
   plant: eighths that grow by row, ━ thicker than ─, E0B0 against E0B2, the dashes' run counts.
4. **`test_win_font` fails on Windows itself** (measured, 1 run): line 35 looks for
   "JetBrainsMono" in the font's path, and DirectWrite gives
   `C:\WINDOWS\FONTS\JETBRAINSMONO-REGULAR.TTF`. Its header says it runs on Windows. Compare
   without case. The larger gap is thread 0's: nothing in CI runs `dwrite.c` on Windows (the
   `windows` job has no fonts' library); `winprobe.sh` shows the zig build takes 4 minutes there.
5. **The wallpaper half is PR 135 at `4764a988`, which has changes requested and has moved on**
   (its review: `reviews/pr-135.md`). What this PR does with its Windows findings: the per-cell
   cost (a `BitBlt` and a transparent `ExtTextOutW` per cell, 47% more) is gone by design, the
   painter copies the cell's ground from the wallpaper's pixels in memory; in exchange a scroll
   over a wallpaper copies no rows on Windows and redraws them (1.7 to 1.8 ms, above). The
   per-size cost is inherited unchanged: `make_dib` still scales with HALFTONE at every
   `WM_SIZE` (16 ms more a size here; 12 to 81 ms in that review). PR 135's two broken plants are
   repaired. So this PR needs PR 135's outcome for the size cost before either lands, and a
   look at the merged head after it.

## Smaller things

- **Half blocks and quadrants round differently** (measured, `sp.c`): at a cell 17
  wide (12 points at 175%) ▌ is 9 pixels and ▘ ▖ are 8, and ▌ and ▐ both own column 8.
  `mx = (w + 1) / 2` would make them agree.
- **The cell is one pixel taller than GDI's** (22 against 21 at 96 DPI): 34 rows where the old
  build had 35 (runner), 39 against 41 (Wine). It is Linux's cell, so this is parity, but Davy
  will see it. Line numbers are also Linux's surface1 now, darker than GDI's overlay0.
- `include/font.h` still says fontconfig finds the fonts (thread 0).
- README says "no measurable difference" for ✦; it is faster (above).
- PR 128 (title bar) needs `BASE` and `TEXT` again from `PAINT_BASE`; whoever merges second.

**Finding 1, fixed.** `add()` refuses a font that is not a colour font before it takes a
number, and an emoji-style cluster asks `MapCharacters` with Segoe UI Emoji as the base family.
Measured on Windows itself (1 run): the copyright sign with U+FE0F takes 10 ms and numbers 1
font (was 459 ms and 33 of 64); 6 emoji-style clusters draw in colour (3.9 to 10 ms the first

once and about 0.1 us from then on.
