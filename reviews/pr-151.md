# Review of PR 151: which-key's `<c-d>` and `<c-u>` scroll a cut panel

Head reviewed: `dc3d5c20` (its base is main `5e38c68`, the current main, so there is nothing to merge). Reviewer: a separate Fable 5.2 thread, briefed with the diff and `include/keys.h`, not the author's conclusions. 2026-11-24.

**Verdict: changes requested, a small round.** The scrolling works and the layout is which-key's (measured below). Two cases differ from which-key (1, 2), one line is not needed (3), and the test lets 7 of my 9 planted bugs pass (4). Finding 5 is older than this PR and is for package 5 to fix, here or next.

Everything tagged **measured** was run here; the count is given. What I only read is tagged **hypothesis**.

## Findings

### 1. `<c-u>` on a panel of odd height scrolls one line too far (measured)

which-key's `Win:scroll()` (win.lua, v3.17.0) moves by `math.ceil((up and -1 or 1) * height / 2)`: down by ceil(H/2), up by floor(H/2). The PR moves by `(wh + 1) / 2` both ways.

- **measured, 1 run:** the body of `Win:scroll()`, copied into `reviews/pr-151-repro/wkscroll.lua` and run on a float in nvim 0.12 `--clean --headless`: height 5 over 14 lines, `<c-d>` then `<c-u>` shows from line 3, then line 1 (counted from 0). Height 4: 2, 3, 1, 0 (the PR's test case, where both agree).
- **measured, 1 run:** the editor in a pty, 24x40, an 18-line file, `G`, Space, `<c-d>`, `<c-u>` (`odd-height.txt`): the panel is 5 rows; after `<c-u>` it is back at line 0, which-key would be at line 1.
- **measured, 1 run each:** `test_wkscroll.c` draws 273,210 panels (both levels, 21 widths from 20 to 200, heights 4 to 40, every cursor row, 8 random scroll keys) and compares each row with the uncut panel's lines. Against the PR's own rule: 0 differ, the help is right in all. Against which-key's rule: 873 differ, all on odd heights after `<c-u>`.

At 80 columns and wider the SPC list is at most 7 lines, so today this shows only in a narrow window; it shows everywhere once a group grows. The fix is one expression, for example `(k == 4 ? wh + 1 : -wh) / 2` (my plant k: the test passes with it too, see 4).

### 2. Scroll keys that arrive between two frames are clamped once, not per key (measured, 2 runs)

`map()` adds to `wtop` and only `keys_draw` clamps it. `main.c` handles up to BATCH keys before it draws, so the same keys give different screens depending on when frames come. which-key clamps in `scroll()` on every key.

Pty, 24x50, a 100-line file, `G`, Space, then `<c-d><c-d><c-d><c-u>` (`burst.txt`):

| how the keys arrive | first list row shown |
|---|---|
| in one write | `c ➜ +compile` (line 3 of 7) |
| 0.2 s apart | `e ➜ File Explorer` (line 1) |

`test_wkscroll pr burst` (1 to 3 keys between draws): 12,925 of 273,210 draws differ from the per-key rule. A user meets it with key repeat on a slow frame or a slow connection. Clamping where the key is handled needs the last draw's limit (`h + 3 - H`) kept next to `wh`.

### 3. `core_changed = 1` in the scroll branch does nothing (measured, 1 run)

`main.c` sets `dirty` after every key (the `for` over the queue), and `<BS>` in the same panel redraws without it. With the line removed the test passes (my plant e) and the editor in a pty still shows the scrolled panel after `<c-d>`. By the top rule the line goes.

### 4. Seven of nine review plants pass `test_keys_map` (measured, 1 run each)

`reviews/pr-151-repro/review-plants.txt`, run with `plant.sh` (the test built against the plant, under ASan and UBSan):

| plant | result |
|---|---|
| a: step `wh / 2` instead of `(wh + 1) / 2` | not caught |
| b: the cut panel's help centred as the short one (`hw = 22`) | not caught |
| c: step from the list's height (`wh = h`) | not caught |
| d: `r < top` dropped, scrolled-off rows drawn above the panel, over the text | not caught |
| e: no `core_changed` | not caught (finding 3) |
| g: `hint &&` dropped, so `<c-d>`/`<c-u>` are swallowed after any half-typed map | not caught by `test_keys_map` (not run against the whole `make test`) |
| i: scroll stops one line early | caught |
| j: the help offers scroll on a panel that fits (`H <= h + 3`) | not caught |
| k: finding 1's fix | passes, as it should; no case tells the two rules apart |

The tests scroll only a panel of height 4 with 7 lines at 24x80. Wanted: an odd height with more than 2 lines to scroll (a and k, c), a check that the rows above a scrolled panel keep the text and their background (d), the help's column when cut (b), no `scroll` in the help of a panel that fits (j), `<c-d>` after Space typed fast or after Org's `c` still Vim's (g), each with its plant.

### 5. Older than this PR: a NUL key after `SPC g` reads past a map's name (measured, 2 runs: main `5e38c68` and this head)

`typed()` compares `m[j] == lead[j]` without stopping at the end of `m`. Space, `g`, Ctrl-Space (the terminal sends 0): for the group `" g"` the 0 matches the string's end, `typed()` returns 3 and `map()` reads `m[3]`.

```
ERROR: AddressSanitizer: global-buffer-overflow
#0 map src/keys/keys.c:295        (main: keys.c:275)
#1 keys_input src/keys/keys.c:343
```

`reviews/pr-151-repro/nul.py BINARY FILE` shows it on both. In a release build the byte after the string decides: if it is not 0 the map "may still complete", `nlead` stays 3 and the next key writes `lead[3]`, past the array (**hypothesis**, read, not run). Not caused by this PR; it should be fixed in package 5 with a plant, in this round or the next keys PR.

## What holds

- **measured, 1 run:** the editor in a pty at 24x50, 100-line file, `G`, Space: the panel is 4 rows at the bottom, shows 2 list rows and `<c-d>/<c-u> scroll`; `<c-d>`, `<c-d>`, `<c-u>` show lines 2, 3 and 1 on; nothing is drawn under the footer. This closes point B of PR 129's review.
- **measured (273,210 draws, above):** no row differs from the uncut panel's lines under the PR's rule, no write outside the grid (ASan, UBSan), the help offers scroll exactly when the panel is cut.
- **hypothesis (read in which-key v3.17.0, view.lua, state.lua, win.lua; only `scroll()` was run):** the buffer is the list with a blank line above and below plus one line the footer float covers (`text:nl()`), so h + 3 lines; the help adds scroll when `opts.height < text:height()`; scrolling returns the same node and keeps the view; any other node calls `show()`, which starts from line 1; the keys scroll only while the view is valid, so typed fast `<c-d>` stays Vim's. The PR matches each. When the help does not fit centred it starts right after the trail (`SPC<esc> close`), as which-key's `string.rep(" ", n <= 0)` does.
- `4` and `21` as literals are package 5's way (normal.c, edit.c). No new mechanism, no copy: `make dupes` is in the check below.
- The diff is `src/keys/keys.c`, its test, its plants and PR 129's report: package 5 and `reviews/` only.
