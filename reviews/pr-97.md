## Notes (non-blocking)

1. **`syntax_update`'s result for a .org file is not tested. Measured.** Planted `return orgfx_update(s->org, stop), 0;`: `test_syntax_org` passes. `src/main.c` draws again after deferred work only when the result is 1, so with that bug a typed headline would keep its old colours until the next key. The four plants the PR adds cover the other four call sites. Ask (package 12's next PR): `CHECK(syntax_update(s, t, NULL) == 1)` after an edit in `tests/test_syntax_org.c`, and this plant.
2. **A comment quotes a measurement the record does not hold. Measured again here.** ab23ec9's comment on `inject()` says its worst case "costs about 50 ms a key; Neovim 0.12.6 takes 834 ms (measured, 5 runs each; PR 91's review)". PR 91's report has 41.4 ms for ours and no Neovim figure. Run again (`lualong250.nix` from `reviews/pr-91-repro/gen.py`, a key at line 125 with lines 100 to 150 visible, 5 alternating runs, per-run medians; Neovim's side is `reviews/pr-97-repro/nvtime.lua`, one `parser:parse({100, 150})` after each key): ours 39.8 ms (31.9 to 43.7), Neovim 0.12.6 561.8 ms (540.5 to 572.2). So the comment's point stands (Neovim is slower by an order of magnitude on this file) and its numbers are near; the source it names should be this report or the author's own record. The other claim there, that a halted injection scan "starts again and never ends while keys come (measured: sliced parses looped)", I did not reproduce: **author's measurement, not checked.**

For package 16, not this PR (it wires `orgfx_update` as org.h describes it): **one update is one step, and `stop` is never asked. Measured, 3 runs each, same bench.** On the manual that step is 0.2 ms. It grows with the subtree an edit sits in: the manual with every headline's stars removed (one 900 KB section) 2.8 to 3.8 ms per key (worst 7.5); a 30,000-item list 5.0 to 6.4 ms (worst 10.9); a 30,000-row table 1.4 to 1.5 ms (worst 2.9); the manual ten times over (9 MB) 0.86 to 0.96 ms per key and 39 to 59 ms for the first parse. The step runs after the frame, so it delays the next key only if that key arrives inside it. No file of Davy's is known to have these shapes; `syntax.h`'s sentence that `stop` "is asked now and then" does not hold for .org (nor does it say so for T-SQL).
