## Findings

1. **The two new loops were longer than needed** (99c2791; fixed in 6b4395b).
   With `level()` returning the level, the skip in `recurse` is one `for` and
   the backing-up in `update` is `while (level(f, &l) < 0) l.lnum--;`; the
   doubled `/* foldlevelExpr() */` comment goes. `shorter.diff`, 535 to 531
   lines, checked with gcc and clang on every trace above before it was sent.
   The author applied it unchanged and retargeted the two plants that named
   the old lines.

## Notes (no change asked)

2. Read beside Neovim 0.12's `foldlevelExpr()`, `foldUpdateIEMS()` and
   `foldUpdateIEMSRecurse()`: the first-line rule uses the buffer line
   (`lnum + off`), the skip keeps `lnum` at the line after the last defined
   one and `lnum_save` at the line whose level was used, `if (fp == NULL)
   return bot;` is back. `lvl_next` stays unported: with "n", ">n" and "-1"
   only it is an input to `getlevel` that those forms never read
   (**hypothesis** from reading; every measurement above agrees).
3. The premise holds: Neovim's `_fold.lua` stores -1 for rows an edit adds
   (`FoldInfo:add_range`), and its `on_bytes` inserts them after the edit's
   last old row, as the INC oracle's `T` does.
4. Trailing "-1" rows: they join the fold around them, and a fold whose
   only defined line is the last one before them is not made ("3" then "-1"
   reads 2 2; `* y y` reads 1 1 1). That is Neovim's answer (`exh.txt`).
   `fold.h`'s comment says "the level of the next defined line" and does not
   say what happens with none; thread 0 may add it.
5. `fold_adjust`'s new early return (`line2 < line1 && !after`) is
   `mark_adjust_buf()`'s first line. Three planted variants (`line2 < line1`
   alone, `<=`, `!after` alone) fail the replay.
6. `tests/test_fold.txt` is now 2.1 MB (605 scenarios, 24,805 steps); the
   replay takes under a second.
7. PR 107's second-pass report (e204b83) is in; that debt is paid. Its notes
   5 to 11 stand.
