## Findings

### 1. After CTRL-V `$`, a sideways move leaves the block drawn to the line ends (the keys', one line)

**Measured** in tmux, real Neovim against `build/gcc/homeros`, 3 key sequences, 1 run each, text `bar_1 more / ab cd / xyz long line here`:

| Keys | Neovim | Homeros |
|---|---|---|
| `l CTRL-V $ j w` | columns 1 to 2 on three lines | every line to its end |
| `l CTRL-V $ j b` | columns 2 to 4 | to the end |
| `lll CTRL-V j $ 0` | columns 1 to 4 | to the end |

After a `j` or `k` both agree again.

Cause: `visual()` reads `Win.want`, as Neovim's `win_update()` reads `w_curswant`. The keys set it lazily (`set_curswant` in `src/keys/buf.c`). Neovim's `update_screen()` calls `update_curswant()` before it draws a Visual area ("Update w_curswant so that the end of Visual selection is correct", drawscreen.c). Homeros has no such call. `nvim --headless` with `redraw!` does not make it either, which is why the oracle and the recorder cannot see this.

A fix, **measured**: `keys-curswant.diff`, one line in `keys_feed` (`if (VIsual_active) update_curswant();`). With it the three sequences draw as Neovim, and `test_core_visual`, `test_core_screens` and the 1,176 recorded sequences still pass (1 run). It is package 5's file, so it is theirs to take.

### 2. Code that can go: the cursor's second cell, and the blank written on the end cell

- `visual()` returns `xt` so that both cells of a double-width character under the cursor stay out of the area. `put_cell()` returns before it sets anything on a second cell (`else if (j) return;`), so `xt` changes nothing there. The one other place a second cell is painted is the `<` filler, which the current window never shows under its cursor.
- `if (!full) wput(..." "...)` writes a blank where `grid_clear()` left one.

**Measured**: `shorter.diff` removes both (one parameter, the `core_line`/`uni_width` test, the `wput`). The results are the same on all 4,515 cases: the 503 recorded, the 4,000 fresh ones above (the same 11 differ), the 12 of finding 3, plus `core_contract`, `core_screens`, `core_markdown` and the recorded sequences. Plants x4, x13 and x14 on the PR's code are not caught, for the same reason.

### 4. A key costs more with wrap on

`core_update` now runs `comp_botline()` after every key. **Measured**, `bench.c` (33 motion keys through `keys_feed`, 1,500 rounds, a 2,000-line file with lines up to 300 words, window 50x120), 5 alternating runs, plants running beside both sides:

| | main 240a897 | PR | |
|---|---|---|---|
| wrap | 3.41 s (3.20 to 3.46) | 5.61 s (5.55 to 5.75) | 69 to 113 µs a key, 1.65 times |
| nowrap | 0.035 s (0.034 to 0.035) | 0.038 s (0.038 to 0.041) | 0.71 to 0.77 µs a key, 1.09 times |

One key at a time this cannot be seen. A macro or a paste in Normal mode on long wrapped lines takes two thirds longer. `core_draw` then runs it a second time for the current window (`core_update`, then `win_drawn`).

A frame, **measured**, `drawbench.c` (50x120, nowrap, 20,000 frames, 5 alternating runs under the same load): main 216 µs (211 to 223); PR without a Visual area 231 µs (229 to 238); `v` 245 µs (234 to 277); block 287 µs (283 to 297). In block mode `visual()` walks both end lines again for every row.

### 5. The test driver reads past a narrow grid

`tests/test_core_visual.c:88` reads the mode text's cells without looking at the grid's width: a recorded case of 12 columns reads past the grid (**measured**: ASan heap-buffer-overflow, 1 run). The PR's generator has no width under 20.
