## First pass (73ddea3): eight findings, all answered in 832682b

1. **Underlines cost every diagnostic before the line, for each line drawn.**
   `draw_line` walked `dv[0..]` up to the line's end and called `diag_span`
   (six rope look-ups) for each. One diagnostic per line, a 40x120 window at
   the end of the file, `core_draw` in ms, 5 runs (`bench.log`):

   | diagnostics | 73ddea3 | with `if (dv[k].z < ls) continue;` |
   |---|---|---|
   | 50 | 0.155 to 0.267 | |
   | 200 | 1.28 to 2.55 | 0.04 to 0.07 |
   | 500 | 5.54 to 5.98 | 0.05 to 0.10 |
   | 1,000 | 12.7 to 19.4 | 0.07 to 0.14 |
   | 20,000 | 280 (1 run) | 0.47 to 0.53 |

   The same window at the top: 0.11 ms. (The machine was also running
   `make check`; the gap is far outside that noise.) Over the 2 ms gate
   from a few hundred diagnostics. **Fixed** by that line, with a frame-time
   case in test_core_diag and its plant.
2. **main.c still watched the start file**, though the body said the line
   was gone: `core_watch` ran twice per outside write (3 of 3 runs), once
   with main.c's two lines deleted, and core.c's `on_watch` was a copy of
   main.c's. **Fixed**: main.c's two lines are deleted (thread 0's, agreed,
   as the author reports).
3. **Insert mode**: after `i<Down>` Neovim leaves the message on line 1
   (current_line hooks CursorMoved only), the core moves it to line 2.
   **Listed** as a known difference in test_core_diag.py.
4. **Server order**: sign and message take the last diagnostic by position;
   Neovim takes the last one the server sent (given col 4 warn, then col 0
   error: Neovim `E int x = 1;     ■■ first-col`, the core `W ... ■■
   second-col`). lsp.h sorts by start, so the order is lost before the core
   sees it, and lsp.c's `qsort` is not stable for two with one start (glibc
   kept them in order here; Windows' may not). The generator makes neither.
   **Listed**; the change is package 13's and thread 0's (follow-up 1).
5. **`us[64]`**: 100 one-character diagnostics side by side underline 100
   cells in Neovim, 64 in the core. **Listed**. My plant "only the last 8
   are kept" is caught, so the array's shift is tested; its boundary at 64
   is not (no case has more than 17 diagnostics).
6. **A stale plant broke the build**: core.txt's "the '>' of a double-width
   character ..." called `put_cell` one argument short. **Fixed**.
7. **The watch.py plant was not caught** (3 of 3 runs): main.c's line kept
   the first case alive. With finding 2 fixed it is caught (author; my
   re-run below).
8. **watch.py's second case proved nothing**: the first case's editor is
   killed after its `x`, its crash journal for a.txt stayed in the shared
   state directory, and the second editor's recovery printed W11 with no
   outside write at all (`watch_case2.py`: PR head, no write: `W11: Warning:
   File "a.txt"`; and with no loop watch anywhere the case still "warned").
   On a clean state the feature is right: W11 only after the write.
   **Answered** with a file and state directory per case, but see B.

     cursor line in both).

   Each needs a case and its plant. Surviving too, and fine to carry in the
