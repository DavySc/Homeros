## Blocking

**A. Typing in a buffer with no file name is undefined behaviour.**
`is_sql()` (snip.c:83) computes `b->path + n - 4` before testing `n > 4`.
With no name (`homeros` started with no file, `:enew`) that is NULL - 4;
with a name shorter than 4 bytes it points before the string. snip_key
calls it on every Insert-mode key in every buffer. Measured (1 run, ASan+UBSan
build, `noname.c`): `src/snip/snip.c:83:14: runtime error: applying
non-zero offset 18446744073709551612 to null pointer`, and the process stops.
The sanitised editor stops the same way on the first key typed in an unnamed
buffer. No test covers it, because every case in test_snip opens a named file.
Fix with D below.

**B. The cursor ends up in the wrong place, past the end of the line, after a mirror is rewritten.**
In `sync()` the cursor moves only when `at >= z`. A cursor *inside* the
mirror being rewritten (after Right into it and a key typed there) stays at
its old byte, past the new text. Measured against nvim (prefix.py, each
prefix compared):

    body '${2:a b}a${2:a b}', keys x <Right> <S-Tab>
      nvim i 1 3 xax      ours i 1 4 xax      (col 4 on a 3-byte line)
    body '${1:ab}-${1:ab}--', keys x <Right> <Right> z z <BS>
      nvim i 1 2 x-x--    ours i 1 3 x-x--

Fresh seeds found this: `snip.py 500 102` had 1 difference, and seed 106 had
1, the same cause. Neovim's rule, fitted to the 3 measured cases
(**hypothesis** for other cases: nvim_buf_set_text's fix_cursor_cols) is to move a
cursor after the range by the change and to clamp a cursor inside it to the
end of the new text:

    if (at > z) set_cursor(e, at - (z - a) + n);
    else if (at > a + n) set_cursor(e, a + n);

With that change (measured): test_snip still matches 0 of 1,983 recorded
cases. All 3 repros match nvim. Seeds 102 to 106 (500 each) and catalogue
seeds 201, 203 and 204 (300 each) leave only the C-w class listed in
snip.py's docstring. Please add a plant for it.

**C. An extra empty undo step when the first stop has mirrors.**
After an expansion whose first stop has mirrors, `u` changes nothing the first
time. Neovim undoes the expansion with that `u`. Measured:

    body '${1:ab}-${1:ab}' after 'x ', keys <Esc> u u
      nvim: u -> 'x '            ours: u -> 'x ab-ab' (no change), 2nd u -> 'x '

On Davy's catalogue, comparing every snippet against nvim (batch.py, 59
compared, 2 refused by Neovim): `<Esc> u` differs on 19 of 59, `q <Esc> u u`
on 19, and `q <Tab> w <Esc> u u` on 26. So about a third of his snippets
need an extra `u`. Cause (**hypothesis**): the mirror write in the
expansion's `after(e, 0)` comes after select_stop's Esc has closed the
undo group, so it opens a new group. In Neovim that set_text joins the
expansion's undo step, because there is no u_sync before the TextChanged
that select_tabstop's typeahead causes. I tried skipping a mirror whose
text is already equal. It fixes all 59 cases, but 10 of the 1,983 recorded
cases then differ (the identical set_text also moves the extmarks), so that
is not the fix. The write must join the expansion's group. snip.py never
draws `u` or `<C-r>`, and test_snip has no `<C-r>`. Please add both, after
an `<Esc>` only: a typed `u` in Insert mode opens the popup on the test
catalogue's `pure`, which makes false differences.

**D. A third copy of the `.sql` test, which also behaves differently.** `is_sql` exists in
`src/keys/ops.c:1699` (case-sensitive, NULL-safe) and in
`src/syntax/syntax.c:333` (case-sensitive), and now in snip.c
(case-insensitive, not NULL-safe). A file named `X.SQL` gets snippets but no
colours, no gq and no format on save. Davy's rule ("as little code
duplication as possible") puts this in one function behind a header (thread
0), called from all three. The case question is Davy's. Neovim's filetype
detection matches `*.sql` case-sensitively on Linux, so keep the
case-sensitive test unless he says otherwise.

## Non-blocking

- **E.** `select_stop()`'s loop backing over UTF-8 continuation bytes repeats `uni_prev` (uni.h).
- **F.** `tests/test_snip.c`'s `key()` decodes UTF-8 by hand, which `uni_cp`/`uni_len` already do. Its key-name table repeats `tests/test_git.c`'s `keyof()`. Copies in tests/ count under CLAUDE.md. One shared key-name parser for the tests would also make <C-r> (C) available to both.
- **G.** If one of the three mallocs in `load()` fails, it returns with the others leaked and `sn` NULL. That is harmless because `nsn` stays 0, but `cat` and the other arrays leak. One allocation, or freeing on failure, would fix it.
- **H.** The catalogue is read once per session, so an edit to `snippets/sql.md` needs a restart. That is fine for step 1. Say so in snip.h, or reload when the file's FileId changes (file_watch exists).
- **I.** snip.py's docstring says the C-w class "stops ... one character later". Seed 103 case 336 and seed 201 case 262 show C-w deleting far more (`    a@          é` vs ours `    a é`), with no stop in the body (the snippet ends at once). The cause may still be the same undo sync. Please widen the wording, or check whether it is a keys difference on its own.
- **J.** `is_sql`'s `(x[1] | 32)` is a bit trick. That is allowed outside proved code, but it goes away with D.

**K (new, non-blocking): text typed at a final stop on another line undoes with the last fill.**
Body `${1:a}\nx`, keys `q <Tab> e <Esc> u`: nvim gives `a\nxe` (the `u`
takes back `q` and keeps `e`). Ours gives `a\nx`. On Davy's catalogue,
`q <Tab> w <Tab> e <Esc> u u u <C-r>` differs on 12 of 59 (measured),
every one a snippet whose `$0` is on another line than its last stop.
It is not snippet code. Plain Neovim does the same with no snippet:
`cmd-undo.lua` (`iq<Cmd>call cursor(2,2)<CR>e<Esc>u`) prints `{ "a", "xe" }`.
It is Vim's Insert-mode undo after a cursor move that is not an arrow key
(no start_arrow, so no u_sync). This is **hypothesis**: the same
Insstart/ins_need_undo family as the C-w class. Ours is the plainer result,
and no text is lost. Please list it with the C-w class in snip.py's
docstring, with this reduced case. Package 4's undo can copy it later if
Davy wants. `run.sh` repeats it.
