## Findings

### 1. Blocker (fixed in 1002918): file_save read a struct stat it no longer filled

222ee23 replaced file_save's `if (!stat(real, &st)) ident(&st, &now)` by `file_id(real, &now)`,
but file_save still read `st.st_nlink`, `st.st_mode`, `st.st_uid` and `st.st_gid`.

- **measured**: `make check` on 222ee23 stops at `tests/test_file.c:106` (mode kept), 3 of 3 runs
  of the test; `tests/test_file_eol.c:130` (a hard link) fails too. With the stat put back as on
  main, test_file passes 3 of 3.
- **measured** (`savemode.c`, 6 of 6 runs, ASan build and -O2): a 0600 file saved through
  `core_write` has mode 0000 afterwards.
- The PR's two `file_id` plants run `test TESTS="file file_save image"`, so on 222ee23 they
  were caught by this failure, not by their own bug.

### 2. Changes requested (fixed in 92bd2ea): image_latex failed for a relative dir

`proc_spawn` runs the tools in `dir`; latex got the base name, dvipng got `dir/ltximg-...`
again, which inside `dir` names `dir/dir/...`. Org's own `ltximg/` is relative to the note.

- **measured** (`reldir.c`, real latex and dvipng of TeX Live 2023): `reldir ltx` fails 3 of 3,
  `reldir $PWD/ltx` gives the PNG 3 of 3 (158 to 182 ms under load).

### 3. Changes requested (fixed in fe5a038): failed renders never settle past 64 fragments

`failed[]` is a ring of 64. With more failing fragments on a screen (latex not installed, and
notes dense with inline formulas), each frame asks for all of them, those the ring forgot start
again, and their failure sets `core_changed`, which asks for the next frame: the editor redraws
and spawns forever.

- **measured** (`failring.c`, PATH without latex, 300 frames, each followed by the loop):
  60 and 64 fragments: 0 of the last 100 frames ask for another; 65 and 100 fragments: 100 of
  100.

The memory of failures must cover every fragment a screen can hold, or a missing tool must be
remembered once instead of per fragment. Wants a test and a plant.

**Fixed in fe5a038**: every failure is kept for the session (a list that grows). **Measured**
(`failring.c` on fe5a038, 1 run each): 64, 65, 100 and 500 fragments: 0 of the last 100 frames
ask for another. Plant "only the last 64 failures remembered". The lookup walks the list for
each fragment in each frame; with a session's failures in the hundreds that is microseconds.

### 4. Fix or record (fixed in fe5a038): a fragment TeX never finishes

- **measured** (`spin.c`, 1 run): `\loop\iftrue\repeat` holds its job for good, and latex is
  still running at 99% CPU after the editor's process has exited; its .tex, .aux and .log stay.
  Eight such fragments and no formula renders again in that session. `loop_timer` with
  `proc_kill` would bound it; otherwise it belongs under the README's residual risk.

**Fixed in fe5a038**: each tool is killed after 10 s. **Measured** (`spin.c DIR 15000`, 3 of 3
runs): the job ends after 10.007 to 10.009 s, no latex process is left, nothing is left in the
directory. A tool still running when the editor exits runs on; the README records it.

## Notes (no change needed for approval)

- **First load of a scaled image, measured** (`split.c`, 5 runs each, 4 cores busy with the
  check): a 3840x2160 screenshot PNG into a 1280x720 box: decode 127-153 ms, then
  stb_image_resize's sRGB scale 166-177 ms; a noisy 3840x2160 PNG 514-550 + 168-176 ms; a
  4000x3000 JPEG 116-125 + 231-236 ms. The README names 55 ms for a decode and does not
  measure the scale. The box is part of the cache's key, so every new box (each step of a
  window resize, if the core derives the box from the window) decodes and scales again:
  the core should pass a box that does not follow the window where it can, and the README
  should record the numbers. The plain (not sRGB) resize is no way out: 121-123 ms.
- **image.h** does not say that a number is only good for the frame it was asked in (its slot
  may be reused; `image_put` takes the slot's current generation), nor that `dir` may be
  relative. One line each, through thread 0.
- **image_draw trusts the slot's cell size**, not the caller's: a cell made for a larger cell
  than the buffer now has would be copied past its cell. Safe as main.c is (it draws the grid
  right before every present, and a new cell size is a new slot); **hypothesis**, not run.
- **The backends fill a tile's background and image_draw then overwrites the whole cell**
  (tiles are padded to whole cells); the fill only shows when image_draw refuses a stale cell.
  **Measured** (`jump.c`, 5 alternating runs of 300 frames): a whole 53x18-cell image appearing
  in one frame costs 0.171 ms (0.163-0.183) against 0.156 ms (0.150-0.163) for text in the
  same cells. Small; thread 0's lines.
- **Duplicates the check cannot see**: a fourth FNV-1a (journal.c, grid.c, wl.c at 32 bits, now
  latex.c at 64), and image.c's blend `(c * a + bg * (255 - a) + 127) / 255` is wl.c's `mix()`
  again (the same result for every input: 255 is odd, so no half to round). For thread 0 or the
  cleanup thread to give one home. test_image.c's `ms()` is `loop_now()`.
- **Windows**: latex.c's fopen, rename and remove take the UTF-8 path as it is; a notes folder
  with letters outside the code page would fail there (**hypothesis**, not run; file.c has the
  wide-path helpers).
- **The tests' fixture is grey**, so red and blue swapped in a backend would pass them.
  **Measured**, 1 run each: a (255,32,0) PNG shows as (255,32,0) in the Wayland window (grim
  under headless sway, `colour.c`) and in the Win32 window under Wine (test_win with that PNG).
