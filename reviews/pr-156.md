# Review of PR 156: one editor per Windows session

Head f8ff0b14 (one commit, stacked on PR 150 at 5264d8c; PR 150's head is now 68c289b4, main 76b9001).
Reviewed 2026-11-24. **Verdict: changes requested**, three small ones, all in the tests; the
mechanism held in everything run here.

## What it does

`homeros.exe FILE` started while an editor runs in the same Windows session hands the file's
full name to that editor and exits; the editor opens it in a new frame and raises it. A named
mutex guards "find the editor's message-only window, else create it"; the file travels by a
sent WM_COPYDATA (Notepad++'s single instance, Emacs's `emacsclient -c` for the behaviour).

## Blocking

1. **The check is red and the main-loop test never passed** (measured: CI run 45381709874,
   and 1 local run). `tests/test_frames_main.c:38: CHECK(t_nraise < NW)`: the test's log of
   raises holds 8 and the two new hand-overs make 10. With the log at 64 the test passes
   (2 runs) and the four `src/main.c` plants are caught for their own reasons (1 run each);
   without the fix all four would count as caught by this unrelated failure. `make test` stops
   there, so CI never reached `make win`.
2. **It no longer builds on PR 150's head** (measured, 1 run). Merging f8ff0b14 with 68c289b4
   and main is textually clean, but PR 150's round 2 added its own `case 11` to
   test_frames_main: "duplicate case value". Renumbered to 13 and 14 (and the log at 64) the
   test passes on that merge (1 run): `reviews/pr-156-repro/frames_main-on-150.diff`.
3. **The "noturn" plant is not caught under Wine** (measured: caught 3 of 20 runs by hand,
   and NOT CAUGHT in the one `planted.sh` run). The eight racing launches rarely overlap
   between FindWindowEx and CreateWindowEx there; the author's 10 of 10 was on Windows 11.
   The train runs plants under Wine, so its shard would be red most times. A test that does
   not race: the test takes the mutex itself, starts a launch, and checks that after a wait
   the launch has neither exited nor handed anything over; then releases it.

## Not blocking

- My plants the tests let through (`plants-mine.txt`, 1 run each): `remote_stop` moved after
  `b->close` (the spec's "late" variant has no test in main.c; the stub could record the
  order); `dirty = 1` dropped from the hand-over loop (either untested or not needed);
  `!lost &&` dropped; `!tty &&` dropped; the second FindWindowEx dropped (a refused launch
  makes a second remote window); `!cd->cbData` dropped; files handed out newest first;
  AllowSetForegroundWindow dropped.
- **Hypothesis, for Davy to try once on his machine:** that the new frame really comes to
  the front when the launch came from another program. Wine does not enforce Windows'
  foreground rules (the frame came forward with and without AllowSetForegroundWindow, 3 of 3
  each) and on GitHub's runner my stand-in for "the program in front" could not take the
  foreground at all (`raise.c`, 10 rounds, no result).
- Past 32 frames a launch is told "taken" and nothing opens (measured under Wine, `e2e3.sh`:
  36 launches, 32 frames, the 37th exits 0). The PR lists it; it is the one case where the
  stated NoLoss does not hold in the code. Selecting 40 files in Explorer reaches it.
- A program that waits for the editor to exit (git's `core.editor`, for one) gets an instant
  exit. Homeros's own git panel does not start homeros.exe (checked by grep), so only an
  outside git is affected. The PR lists it.
- `include/remote.h` and `src/main.c` are thread 0's by CLAUDE.md; this PR is Davy's own.
- The PR text says the base is PR 150's branch "so this diff shows only this change": true
  on GitHub, but the branch sits on 5264d8c, two review rounds behind.
