# Review of PR 177: one token request per burst of Lean refreshes

Reviewed head 88700674, which sits directly on main db4233ef (train 34), so there is no merge to redo. Package 13 (`src/lsp/`). Repro files: `reviews/pr-177-repro/`.

**Verdict: changes requested.** One defect (finding 1), which main does not have. The fix I tried is shorter than the PR's code and also closes findings 2 and 3.

## Findings

### 1. With 16 or more files on one server, a refresh loses requests and fills the loop's timer table (measured)

The PR arms one timer per file (`loop_timer(retoken, d, 200)`). The loop has 16 timer slots in all (`src/loop/timer.c`, `MAXT`), shared with the key hints, the yank flash, the SQL index, the dashboard, LaTeX and the infoview's keep-alive. `loop_timer` answers -1 when the table is full, and the PR does not look at the answer. The request in flight has already been cancelled by then, so that file keeps the colours of Lean's partial first answer until its next edit.

`many.c` opens N files on one fake server (`many.py`). Each first answer colours one word; then the server sends one refresh, and later answers colour two words.

| Files | Show the refreshed answer | Another `loop_timer` just after the refresh |
|---|---|---|
| 8 | 8 | 0 (ok) |
| 15 | 15 | 0 (ok) |
| 16 | 16 | -1 (table full) |
| 17 | 16 | -1 |
| 20 | 16 (5 of 5 runs) | -1 (5 of 5 runs) |
| 40 | 16 | -1 |

So for 200 ms after every refresh (Lean sends one about every 2 s while it elaborates, PR 148's review) any other timer is refused: a yank flash that never ends, a key hint that never shows. With fewer files the same happens once other timers hold slots. On main every file is asked on a refresh, so this is new.

Neovim arms a timer per buffer too, but its timers are not a fixed table.

**Fix tried (`fix-short.diff`, 10 changed lines, lsp.c ends 2 lines shorter than the PR's):** one timer per server. `retoken(void *s)` asks every file of `s`; the refresh arms it with `loop_timer(retoken, s, 200)`; the answer to `initialize` calls `retoken(s)` in place of its own copy of the same loop; `dead()` drops the timer in place of `forget()`. Measured on that tree: 17 and 40 files all show the refreshed answer and the other timer is accepted; `test_lsp` passed 3 of 3. The author's plant "a refresh's wait outlives its buffer" needs a new target there (the line moves to `dead()`).

### 2. The `cancel` in the refresh handler is untested (measured: my plant 2 passes the test)

Plant: `cancel(d, &d->tokid), loop_timer(...)` becomes `loop_timer(...)`. `make test TESTS=lsp` passed. This is the kind of line the PR sets out to test or delete. `tokens()` cancels the request in flight itself when the timer fires, so the line only matters for those 200 ms: without it an answer that arrives meanwhile is shown, then replaced. Delete it (as `fix-short.diff` does; `test_lsp` 3 of 3) or test it (the fake parks a request, sends a refresh, and wants the cancel before the next request). `fix.diff` is the variant that keeps it.

### 3. A refresh with more than one file is untested (measured: my plant 4 passes the test)

Plant: the refresh handles only `s->docs`, the first file. The test passed: the fake only sends a refresh while one file is open. With `retoken(s)` shared between the refresh and the `initialize` answer, the existing plant "only the first file asked once the server is ready" covers both, and no new test is needed.

### 4. Nits

- `decode()`'s comment still says "No array (an error): the tokens shown stay". Now only a missing `data` keeps them; a `data` that is not an array clears them (measured below). Say "No data".
- An edit inside the 200 ms sends its own request, and the timer then cancels that one and asks again: one request more than Neovim, which sends edits through the same timer. Harmless (hypothesis: rare, a refresh comes about 2 s after an answer); no change asked.
