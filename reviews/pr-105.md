## Findings

### 1. Verible's error stream is not tested to stay out of the buffer (blocking, small)

`on_verible` keeps stdout only (`stream == 1`). With that line changed to `if (stream && b)`, so that stderr is appended to the output too, `make test TESTS=keys_gq` passes (**measured**, 1 run): the fake formatter never writes to stderr. The real one does while exiting 0: in lines mode on `ibex_cs_registers.sv` it wrote 90,655 bytes to stderr with exit status 0, so with that bug a gq would paste Verible's complaint into the file. Ask: the fake writes a line to stderr in its "ok" mode, and a plant for the line.

### 2. proc_wait follows the slot, not the child (blocking, small)

loop.h: "until it is reported". `proc_wait` loops on `proc(id)`, and a slot is free from the report on. A child whose `fn` starts another child when it is told of the exit gets the same id back for the new child, and the wait goes on for it, then kills it at the timeout and returns -1. `reuse.c` (**measured**, 1 run): `true` reported at once, its report starts `sleep 3` in slot 0, `proc_wait(id, 1000)` returns -1 after 1,002 ms having killed the sleep. The Verilog formatter's `fn` starts nothing, so the editor cannot reach this today; a later caller (a language server restarted from its exit report is the pattern lsp.c already has) would lose a child it never waited on. Ask: either end the wait at the report (for example the report clears `only`, and the loop runs while `only == id`), with a test and a plant, on both systems; or thread 0 writes the restriction into loop.h. The first is the one that keeps the header's sentence true.

### 3. PR 101 moved (blocking, mechanical)

PR 101's head is now aad695a ("fuzz_infoview_call: from_child takes str_lines' ctx"). It merges into e95199a with no conflict. Without it `make fuzz` does not build: `tests/fuzz_infoview_call.c:45: error: too few arguments to function call, expected 3, have 2` (**measured**, 1 run, on e95199a); with it the fuzzers pass.

### 4. The flake says "its tag"; the commit is 38 past it (not blocking)

`git describe` on 4349e86 gives `v0.3.1-38-g4349e86`, and the binary says "0.3.1+". The comment "built from its tag" and `version = "0.3.1"` (and the PR text's "tag 0.3.1") name something else than what is built. Either pin v0.3.1 (2ad996f) or say what it is (nixpkgs writes `0.3.1-unstable-2026-11-xx`).

### 5. Short copies (not blocking; CLAUDE.md asks a review to flag them)

- `src/lsp/bench/sv.c` copies `edit` (5 lines) and `cmpl` (1 line) from `src/lsp/bench/stale.c` (`tools/dupes.py 30` names both).
- `proc_wait` in `loop.c` and `win.c` share their first lines (30 tokens, under the check's 50), as the two files' other twins do. They differ in the kill deadline and the wake-up, so I see no shorter form without a new shared header.
- "E342: Out of memory!" is now written in both `verible` and `buf_format`.

### 6. Messages (not blocking)

A timeout, a Ctrl-C and a non-zero exit all say "verible-verilog-format failed". Verible's own first stderr line (it names the line and token of a syntax error) is dropped; with `--failsafe_success` on by default a syntax error says nothing at all. slang-server reports the same error, so nothing is lost once diagnostics are drawn (note 7).

### 7. The editor does not draw diagnostics yet (not this PR's; for Davy and the coordinator)

The gate is measured at the client: "shown" in the bench and the PR text means `lsp_diags` holds the error. Nothing but the Lean infoview reads `lsp_diags`: `src/core/draw.c` says "Diagnostics and the LSP status are not drawn yet". **Measured**, 2 runs, `e2e_sv.py`: the real editor in the Ibex project starts slang-server (it is the editor's child), a typed `@@@` is saved, and the screen shows the typed text and nothing about an error. So after this PR Davy gets formatting, and a server that knows the errors, but sees no error until core draws diagnostics (the faces are in grid.h already). The PR text should say "held by the client", and the plan's "errors as you type" needs that core work scheduled.

### 8. What the bench's ":w" time covers (not blocking)

`until` starts its clock after `save` has written the file and sent didSave, and the didChange went out before the write, so the figure is the time from didSave to the first publication with an error, whichever notification caused it. In a 5-line project it reads 0.0 ms. On Ibex the figure is 20 to 57 ms either way, an order below the gate, so the verdict does not depend on it; the bench's comment could say where the clock starts.
