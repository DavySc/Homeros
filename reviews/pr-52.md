# Review of PR 52 (package 4: marks under a delete from mid-line, and the marks an undo group saves)

**Verdict: CHANGES REQUESTED.**

Head `ec4a167`, base `8243cdb`. Reviewer: a separate Fable 5.2 agent, briefed with the diff and the contract (`include/core.h`, DESIGN.md, Neovim 0.12.6), not with the author's conclusions. Every finding below was reproduced by running it. The repro sources are in `reviews/pr-52-repro/`.

The rule itself is right. Driven through package 5's keys (PR 26), the PR's core gives Neovim's `'<`, `'>`, cursor and text in all 7,920 cases of a systematic grid (main: 2,960 differ) and brings 39 random differences to 0 (**measured**, below). The change list, the jump list and marks a b c also match Neovim on the one case I traced by hand (**measured**, 1 case). What has to change is around the rule: one regression that the core API reaches, tests that let six real bugs through, and two lines that are not needed.

## Findings

### 1. A group left open in one buffer loses its saved marks when another buffer is edited (regression from main; core API only)

`snap_buf` and `snap_seq` are one pair for all buffers. Buffer A has an open group, buffer B is edited, then A is edited again in the same group: `snap_buf != b`, so the core takes A's group for a new one and overwrites its saved marks with the marks as they are by then. Undo then restores the wrong marks.

```
bash reviews/pr-52-repro/keys-tree.sh ec4a167 /tmp/k52      # PR head
bash reviews/pr-52-repro/keys-tree.sh 8243cdb /tmp/kmain    # base
/tmp/kmain/build/san/twobuf   ->  lines 3, mark a on line 2 (2 is right)   exit 0
/tmp/k52/build/san/twobuf     ->  lines 3, mark a on line 3 (2 is right)   exit 1
```

**measured**, 1 run each side (deterministic). `twobuf.c` uses only `core.h` and `undo.h`. Package 5's keys close the group at every Normal mode key (`src/keys/keys.c:113`), so I found no key sequence that reaches it (**hypothesis**: none exists; Insert mode CTRL-O was tried and splits the group as Neovim does). Other callers of `core_edit` (LSP edits, tools) are bound only by the header, which does not say "close the group before you switch buffer". Either keep the saved group per buffer, or state the rule in `core.h` through thread 0.

### 2. The new tests let six planted bugs through (CLAUDE.md, "A check you have never seen fail proves nothing")

The three plants the PR adds are caught. I planted eight more against the same lines (`own-plants.txt`, run by `own-plants.sh` through `tools/planted.sh`, against `make test TESTS="core_undo core_contract core_screens"`):

| Plant | Result | A real bug? |
|---|---|---|
| a joined mark keeps its column (`m->col += col - col`) | caught (`test_core_undo.c:145`) | |
| `'>` on a deleted middle line is not joined | **not caught** | yes: the test sets `'>` but checks only `'<` |
| the change list is not joined | **not caught** | yes: Neovim gives `(1,8)`, see `lists.lua` and `lists.c` |
| the jump list is not joined | **not caught** | yes: same case |
| every `core_mark_join()` of an edit saves the marks again (`join_snapped != b` removed) | **not caught** | yes: `ab\ncd\nef\ngh\n`, `G k v k Esc gg 3J u` gives `'<` 1,4 where Neovim gives 2,1; 120 of 7,920 grid cases differ |
| the marks saved before a join are never dropped (`join_snapped = NULL` removed) | **not caught** | yes: 234 of 7,920 grid cases differ |
| every edit of a group saves the marks again (`snap_seq = ...` removed) | **not caught** | yes: 318 of 7,920 grid cases differ |
| an unloaded buffer keeps `snap_buf` | **not caught** | not shown: I did not find a sequence that reaches it |

**measured**: 1 run of each plant; the grid counts are 1 run each of `marks.py --grid` on a driver built with that plant. So four of the PR's new statements (`'>`, change list, jump list, and the guard that keeps the first snapshot of several joins) and two of its resets have no check that fails without them. Each needs a case in `tests/test_core_undo.c` and a plant in `tests/plants/core.txt`: check `'>`, one `change[]` entry and one `jump[]` entry in the existing d5w case; a join of three lines (two `core_mark_join()` calls, one edit) then undo; a second group after a join; two edits in one group that the keys opened.

### 3. One clause and one variable are not needed (Davy's top rule)

In `edit()`, `undo_seq(b->undo) != seq ||` adds nothing: a group that the edit opens gets a number above every number saved before, so `snap_seq != undo_seq(b->undo)` is already true. With the clause gone, the local `seq` goes too (`simpler.diff`, 1 line added, 2 removed).

**measured**: with `abort()` planted where the two conditions disagree, `make test TESTS="core_undo core_contract core_screens file_core"` passes and `fuzz_core` (78,024 runs, 61 s) and `fuzz_keys` (72,437 runs, 61 s) never reach it; a driver built from `simpler.diff` gives the same counts as the PR on the grid (0 of 7,920), focus seed 1 (0 of 1,800) and wide seed 2 (6 of 3,000, the same six). The PR's third plant names the clause's text, so it changes with it.

### 4. A group that the keys open and never edit still saves no marks (not a regression; the PR's rule does not cover it)

The PR saves the marks of a group opened by `undo_record()` alone "at its first edit". Neovim saves them in `u_save_cursor()` itself, so a group with no edit has them too. `d{` on line 1 column 0 is such a group (`op_delete()` with `oap->empty`).

```
python3 reviews/pr-52-repro/marks.py /tmp/k52/build/san/marks_drv --case $'bar\nab,\n' v '<Esc>' d '{' v j '<Esc>' u
  nvim '> = 1,1    ours '> = 2,1     (mark line)
... --case $'bar\nab,\n' v '<Esc>' d '{' v j '<Esc>' u gv d
  nvim and ours differ in the text
```

**measured**, 1 run each on the PR and on main (both differ the same way). The core cannot see `undo_record()`, so it cannot fix this alone. If the keys opened their group through the core (one function in `core.h` that records and saves the marks), the marks would be saved where Neovim saves them, the empty group would be covered, and `snap_buf`, `snap_seq` and, for joins that follow `u_save_cursor()`, `join_snap` would have no work left (**hypothesis**: not built or measured). That is a header change, so thread 0's call. Until then this belongs in `src/core/known/README.md` or `tests/conform-known.json`.

## What I checked and found right

- **The rule** (`nodel_join()`): Neovim's `op_delete()` runs `del_lines()` on the lines between (ONE_ADJUST_NODEL marks go to the first deleted line, which is then the old end line) and `do_join(2)` (`mark_col_adjust()` adds `start.col`). The PR's "line = L, col += col" is that. Deletes that start at column 0, end at the end of a line, include the line break (`v…$d`), `d` and `c`, counts, `J` and `gJ` with counts and from Visual mode, marks on the start line, on deleted lines, on the end line and after it, then `u`, `u CTRL-R`, `u CTRL-R u`: `marks.py --grid`, 7,920 cases, 0 differ on the PR, 2,960 on main (**measured**, 1 run each; again 0 with PR 26's newer head `cc5d0cb`).
- **Random sequences** (`marks.py`, each sequence also with `gv Esc` and `gv o Esc` appended, which show both ends as the cursor): focus seed 1, 1,800 cases: PR 0, main 39. Wide seed 2, 3,000 cases: PR 6, main 75. Wide seed 3, 3,000: PR 3. Focus seed 5, 3,000: PR 3. All 12 that remain on the PR reduce to finding 4 or the three rows above, and each differs on main too (**measured**, 1 run per seed).
- **Change list, jump list, a b c** (`lists.lua` in Neovim, `lists.c` in the core): after the delete Neovim has `(1,8) (1,6) (2,1)`, `'a` unset, `'b` 1,6, `'c` 2,1; after undo `'a` 2,4, `'b` 3,2, `'c` 4,1, `'<` 3,2; after redo as after the delete. The PR gives the same in all three states. Main leaves `(2,4)` and loses `'a` and `'b` on undo (**measured**, 1 case).
- **Nothing else added**: the three plants and the `#include "undo.h"` are used. Apart from finding 3, I found no line to remove.
