## Findings

### 1. `test_core_screens` no longer notices a wrong modified flag (blocking)

On main the test compares every status row with Neovim's, so `[+]` is compared on 3,056 screens. On this head `status_row()` compares only the ruler, and `test_core_status` draws the dot in a handful of states, none after an undo past a save.

**Measured**, 1 run each, the plant `undo_seq(b->undo) != b->saved_seq` to `undo_seq(b->undo) > b->saved_seq` in `core_modified()`:

| Tree | Result |
|---|---|
| main 20ed870 | caught: `test_core_screens: 4 of 3056 screens differ` (case 13 after `k:u`, Neovim `f0 [+]`, core `f0`) |
| b17c176 | not caught: `core_screens`, `core_status`, `core_contract`, `core_undo`, `core_visual`, `core_markdown` and the 1,275 recorded sequences all pass |
| b17c176 with the two lines below | caught, the same case |

CLAUDE.md: "Never weaken a check". These two lines before `if (strstr(part, want)) return 1;` keep the comparison (with them all 3,056 screens still match, 1 run; `[+]` is not asked for where the window's width cut the row):

```c
int plus = !!strstr(part, "[+]");
if (plus != core_modified(w->buf) && (plus || !strchr(part, '<'))) return 0;
```

Please add the plant above with it.

### 2. A new file in a repository shows no branch (requested)

**Measured**, 3 runs, `more.c` states `new-git` and `saved-new`: in a repository, `:e new2` shows `NORMAL  ⎇ feature/長い-branch  new2` in lualine and `NORMAL  new2` in the core, and the same after `ix` and `:w`, 4 seconds later.

The cause, read: `git_attach()` returns when `git_real()` (realpath) fails, which it does for a file not made yet, and nothing attaches the buffer again after its first write. gitsigns attaches on BufNewFile and on BufWritePost too. Either the core calls `git_attach(b)` after the first write of a file that did not exist, or package 17 finds the repository from `Buf.full`, which is there for exactly this ("a file not made yet keeps its name"). The second also gives the branch before the first save, as lualine shows it. A case in `test_core_status` and a plant, please.

### 3. `utf-8` appears after a new file's first save (not blocking)

**Measured**, 3 runs, state `saved-new`: after `:w` of a new file lualine still shows no encoding ('fileencoding' stays empty until the file is read again); the core shows `utf-8`, because `b->id.exists` turns true on the write. The comment above the line says what Neovim does ("set by reading a file that exists"); the code tests something else. Fix it or list it as a known difference.

### 4. No O-PENDING pill (not blocking)

**Measured**, 1 run each: with the mode `no` lualine shows `O-PENDING` (`more.txt`, state `mode no`); after `d` the core still shows `NORMAL` (`misc.c`). `e->ks.pending` is there to tell. Worth one line in the PR's "not in this PR" list at least.

### 5. A link to an open file makes a second buffer (not blocking, older than the PR)

**Measured**, 1 run: with `a` open, `:e l` (a symlink to it) and `:e h` (a hard link) leave Neovim with one buffer (`:ls`) and the core with three (`misc.c`). `buflist_findname()` compares the file's id as well as its full name (`buflist_findname_file_id()`, `otherfile_buf()`), and `Buf.id` is already kept. The PR's text says it "compares full names": that is half of it. Two buffers on one file is what the start screen finding was about, so this is worth a follow-up.

### 6. The file name's tail is now written three times (not blocking)

`draw_status()` (draw.c, with its `#ifdef _WIN32`), `kitten_paw()` (kitten.c:57, the same loop, the same `[No Name]`) and `ft_of()` (syntax.c:104). Davy's rule asks for one function both call, through a header; that is thread 0's to add (something like `const char *file_tail(const char *path)` in file.h), and the core and the kitten then drop their copies. Smaller: `if (file_full(path, full)) snprintf(full, sizeof full, "%s", path);` is in core.c twice (`buf_load`, `buf_by_path`).

### 7. PR 84 and this PR cannot both merge as they are (for the merge queue)

**Measured**, 1 run: `git merge-tree` of b17c176 and PR 84's head f4d4ed3 conflicts in `tests/test_core_markdown.c`, `.lua`, `.py` and `.txt`. Both PRs record the .txt again, with different settings (PR 84 the bullets and code blocks, this one 'cursorline'). Whichever lands second has to merge main and record the trace once more with both.

### 8. For Davy's eye: the file name is the first thing to go (not a defect)

lualine cuts from `%<`, which sits right after the mode pill, so in a narrow current window the branch and the file name go before the file type and the encoding. In a repository, a 40-column window on `q.sql` reads `NORMAL < sql · utf-8    1:1   Top`. The core copies lualine exactly here (measured at every width). Other windows keep their names, since they show only the name and the location. If Davy would rather keep the name and drop the encoding first, that is a change to the layout he picked, so it is his call.
