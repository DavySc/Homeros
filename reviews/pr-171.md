## What holds

- **Layout** (`g1 dump ms uni.sql`, `sets.sql`, `pguni.sql`, `wide2.sql`, `big.sql`, 1 run each):
  CJK, a combining accent, a ZWJ family emoji, Latin-1 letters, a NULL next to the text 'NULL', an
  empty string, a tab and a newline in a value (shown as `\t`, `\n`), a 45-character value and a

  every │ of every grid sits in one column (0 misaligned lines by `grid_width`), the faces are the

- **The marks are safe on Postgres**: a SQL_ASCII database with the bytes 0xFD, 0xFE, 0xFF in values

  marks cannot come from data there (1 run).
- **SPC r** (`g1 toggle`): closes and opens the same buffer with the same text, its faces and its

- **A connection the server ends** mid-run (`term.sql`, `sev20.sql`): the grid before it is laid
  out, the status line says "completed with errors" (1 run each).
- **A column name of one cell and later wider values** (`zw3.sql`): no overrun; the value shows as

- The SQL and core tests pass on the merged tree: see "Checks" at the end.

## Speed

-O2, no sanitizers, F5 to "Completion time", 7 alternating runs per side, `make check` running on one
of the 4 cores at the time (so the ranges are wide):

| case | main | PR 171 |
|---|---|---|
| 100,000 rows x 6 columns (`big.sql`), 8.8 MB / 12.0 MB of text | median 146.5 ms (134 to 260) | median 182.7 ms (150 to 218) |
| 10,000 rows x 37 columns (`wide2.sql`), 2.8 MB / 11.0 MB | median 123.5 ms (113 to 481) | median 123.2 ms (113 to 146) |
| 20,000 sets of one row (`many2.sql`) | median 39.6 ms (30 to 58) | median 257.3 ms (209 to 302) |

- The large result is about 36 ms (25%) slower by the medians, and the ranges overlap; the PR's own
  figures (121 against 151 ms) agree. The longest loop turn is the same on both sides (3.8 to 5.1 ms
  in 3 runs each), so the editor stays as responsive while rows come in. For 37% more text in the
  buffer I find that acceptable.
- A redraw of the results window (200 x 50 cells, 300 redraws, 3 runs per side): best 0.031 ms on
  main, 0.056 ms at the end and 0.078 ms at the top with the PR. The faces cost about 0.03 to 0.05 ms
  a frame.
- **E (not blocking, cheap to fix):** many small sets cost about 11 µs each, 6.5 times main. `lay()`
  counts the newlines of all of `s->o` for each set (`for (char *q = s->o.s; ...) g->line += ...`),
  so within one read the cost grows with the square of the sets in it. A line count kept as lines
  are added removes it. 20,000 sets in one script is rare, so this does not block.

## Findings

### A. Blocking: a Postgres notice between rows ends the grid, and the rows after it are lost from it

`pgnotice.sql`: a function that raises a notice, called once per row
(`select pg_temp.n(g) as v from generate_series(1, 5) g`). 3 of 3 runs with the PR:

```
  │ v
──┼──
(0 rows)

── Messages ────────
(CREATE FUNCTION)
NOTICE 00000: row 1
\xFF1
NOTICE 00000: row 2
\xFF2
...
```

The status line says "0 rows". The five rows land in the Messages, each with its 0xFF mark still on
it, so the buffer holds five bytes that are not UTF-8. On main the same script shows the five rows
(3 of 3). Cause: `take()` ends the open set at any line without a mark, and a row that then arrives
with no set open falls through to the messages with its mark. A message while a set is open has to
go to `msgs` without ending the set (only the next names, or the run's end, end it), and a mark must
never reach the buffer. No test has a message inside a set.

### B. Blocking: a run that never logged in shows "✓ Query executed successfully"

`g1 dump "<a connection line>" one.sql`, the status line after F5:

| connection | messages | status line |
|---|---|---|
| wrong password (3 of 3 runs) | Msg 18456 ... Login failed for user 'sa'. | ✓ Query executed successfully · 0 rows |
| unknown host (1 run) | unknown host nohost.invalid | ✓ Query executed successfully · 0 rows |
| closed port (1 run) | send: Connection refused | ✓ Query executed successfully · 0 rows |
| database that does not exist, both servers (1 run each) | Login failed / database "..." does not exist | ✓ Query executed successfully · 0 rows |

Nothing ran, and the line the eye goes to says it went well; the text of the failure is in no error
face either. Cause: the client's own lines (`putz(s, db_net(&s->db)->err)` in `run()` and `next()`,
and the login's Msg, which reaches the buffer through `net.err`) carry no `NET_ERR`, and `drop()`
calls `end()` with `bad` still 0. SSMS shows the failure as an error. Every line that comes from
`net.err` should count as an error (mark and face), with a test per case.

### C. For Davy to know (the PR lists it as a known limit): messages show only when the run ends

`slow2.sql`: `select 1`, then `raiserror('progress 1', 0, 1) with nowait`, then a 2 s wait, then
`select 2`. On main "progress 1" is in the results 0.4 s after F5; with the PR it appears after
2.0 s, with everything else (1 run each). The same holds for an error in the first batch of a long
script: it is not visible until the last batch is done. SSMS's Messages tab fills while the script
runs, and `raiserror ... with nowait` is the usual way to follow a long T-SQL script. A follow-up
should show messages as they come (for instance appended at once while no grid is open, or the
last message in the status line while the run goes). Not blocking, because the design Davy chose
puts the messages after the grids.

### D. Not blocking: nothing shows until 500 rows or the end of a set

A set's rows are held until 500 have come or the set ends. A query that returns its first rows fast
and then works for a long time shows nothing until then; main showed rows as they arrived. I could
not make a server send a few rows early in a test (both servers buffer small sets themselves:
`slow.sql`, `trickle.sql` show 0 bytes on main too), so this is a **hypothesis** for sets under 500
rows that span several packets. A timer (lay out what is held after, say, 200 ms) would cover it.

### F. Not blocking, for Davy to know: a cut value cannot be read or copied

A value over 40 cells, or wider than the first 500 rows of its column, is cut in the buffer itself,
so the rest is gone: `zw3.sql` shows "…" alone for 'xyz' in a column whose first 500 values were
empty, and a 45-character value loses its last 6. `sp_helptext`, a view's definition or a JSON
column cannot be read from the results any more; on main the whole value was there. The cap is part
of the chosen design, so this needs a way to see one whole cell (a key on the cell, or the widths
recomputed on demand) rather than a change here.

### G. Tests the PR lacks (my plants, `review-plants.txt`: 8 of 18 caught, run alone, 1 run each)

Not caught, each a behaviour the PR describes:

- the Messages rule in no face; the "(n rows)" count in no face;
- a later grid's faces computed at the first grid's line (the faces are only checked on the first grid);
- the running status line's text ("Executing query...");
- a last line without its newline lost;
- a wide character counted as one cell (the test's CJK value sits in a column where both counts give
  the same text: put a second row under it);
- a control byte counted as one cell;
- a Messages rule printed with no messages;
- a set of 0 rows showing no grid;
- Postgres's error without its mark (the status line then says "✓"; `test_sql` catches the mark's
  absence only in its own plain text).
