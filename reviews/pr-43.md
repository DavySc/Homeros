## Blocking

### 1. Opened after Lean has started, the page stays empty

`\w` on a file whose Lean server has already answered `initialize` gives a
page that shows "Waiting for Lean server to start..." for ever. That is the
order of use: a file is open before `\w` is pressed.

- Measured with the fake server (`late.c`): bridge opened before the loop
  turns, hello in 3 of 3 runs; opened 1 s after the file, hello in 0 of 3.
- Measured in the real infoview in Chromium (`run-late.sh`): no wait, the
  page shows the tactic state (2 of 2); 8 s wait, "Waiting for Lean server to
  start..." (2 of 2).

Cause: `init` is only set in `tap()`, and `lsp_tap` is only set in
`bridge_open`, so an answer to `initialize` that came earlier is never seen.
`seed()` recovers the diagnostics for that case but not the capabilities.
The unit test and the oracle's `drive.c` both call `bridge_open` straight
after `core_open`, before the loop has turned once, which is why neither saw
it.

Fix (tested, in `fixes.diff`): lsp keeps a Lean server's answer to
`initialize` and gives it out (`const char *lsp_init(const LspDoc *, size_t *)`),
and `seed()` passes it to `tap()`. That is one more declaration in `lsp.h`
(thread 0) and four lines in `lsp.c` (package 13's follow-up). With it
`r43_late 1` gets its hello in 3 of 3 runs and `test_infoview` and `test_lsp`
still pass. The unit test needs this order, and a plant for it.

### 2. A request without the token can make the child hold 64 MB

`requests()` waits for the whole body (up to `BODY_MAX`, 64 MB) before
`request()` looks at the token. Any local process, and any web page that
knows the port, can therefore fill the child's memory with no secret at all.
The port is not secret: Chromium sends `Referer: http://127.0.0.1:PORT/` to
every other origin the page loads from (measured, `referer.mjs`, 2 runs).

Measured (`probe.py memory`): 16 connections, each a `POST /nothing` that
says 64 MB and sends 60: the child's RSS goes from 1 MB to 961 MB. With all
64 connections that is 4 GB.

Fix (tested): once the head is complete, a request that has a body and whose
path is not under the token closes the connection. RSS then stays at 1 MB.
A smaller `BODY_MAX` would also do for what remains (a page's own calls are a
few kB), but I have not measured the largest call a widget makes.

### 3. The package's own plant 5 is caught only some of the time

"the server fuzzer on a page id longer than its buffer" was NOT CAUGHT in my
`planted.sh` run (`plants.log`). Run alone on an idle machine, the same
fuzzer with make's flags caught it in 4 of 5 runs of 60 s (`plant5.sh`),
after 1.1M to 5.2M runs; the fifth did 8.7M runs without finding it. So CI's
planted job fails about one time in three on this plant alone.

The fuzzer has to build `GET /tok/events?page=` and 65 legal characters from
nothing. A check that does not depend on luck: a page id of 65 characters in
`test_infoview.c` (ASan catches the overflow), with the plant pointed at
`test TESTS=infoview`; or a seed corpus for the fuzzer.

### 4. Two undefined behaviours a page's call reaches; the editor's side has no fuzzer

Both fuzzers are on the child and the scanner. Nothing fuzzes `from_child()`
and `call()`, which take the page's bytes inside the editor. A fuzzer for
them (`fuzz_call.c`, a Lean buffer open so edits reach the core) found the
first of these in 20 s:

- `{"id":0,"m":"createRpcSession"}` (no arguments): `s + a0` with `a0 == NONE`
  at `infoview.c:449`, a pointer that overflows (`crash-connect-min`).
- `applyEdit` with an empty `edits` array: `qsort(NULL, 0, ...)` at
  `infoview.c:401`, which glibc declares non-null (`r43_edge empty`, 3 of 3).

Both abort the sanitizer build; the release build gets away with them today.
With the two guards in `fixes.diff` the same fuzzer ran 2.48M times in 151 s
with nothing found. Please take the guards and the fuzzer (as
`tests/fuzz_infoview_call.c`, with a plant).

## Not blocking, but worth doing in this PR

### 5. The opener inherits the editor's pipe

`open_browser()` spawns the opener with the child's stdin and stdout, which
are the editor's pipes, and a browser that `xdg-open` starts keeps them.
Whatever it prints on stdout goes to the editor as protocol lines. A whole
line is ignored (no JSON). Text without a line break is glued to the child's
next line, which is then lost: with an opener that prints
"Opening in existing browser session." and no line break, "+ pageA" never
arrives and the page gets no hello (`r43_edge chatter`, 3 of 3; with a line
break it is fine, 1 run). Which browsers do that I have not measured
(hypothesis: rare). Fix (tested): `/dev/null` on 0 and 1 for the opener.

### 6. The security properties have no check that fails

Seven more plants (`extra-plants.txt`), none caught by `make test
TESTS=infoview`:

| Plant | Caught |
|---|---|
| the server listens on every address (`INADDR_ANY`) | no |
| the token is the same every time | no |
| a body of any length is taken | no |
| the outbox is sent again at every reopening | no |
| a page's older stream stays open beside its new one | no |
| a line break in a call's body reaches the editor's pipe | no |
| a line break in Lean's JSON reaches the child's pipe | no |

The first two are the ones that matter: the loopback bind and the random
token are what keep the page private, and a change that broke either would
pass every check. `probe.py bind` shows one way to check the address
(`/proc/net/tcp`); two children's tokens must differ.

### 7. 64 idle connections lock the page out

Connections that send nothing are never closed and there are 64 slots.
Measured (`probe.py idle`): with 64 open, a request for the page with the
right token gets no answer, still none 20 s later, and 200 again once they
close. No token is needed. It stops the infoview only, not the editor.

### 8. `XDG_RUNTIME_DIR` of exactly 40 characters

`redirect[64]` holds 63 characters; a 40-character directory plus
`/homeros-infoview-XXXXXX` is 64, so the template loses an X, `mkstemp`
fails and the child exits 1 (`probe.py rundir`: 39 works, 40 exits, 41 falls
back to /tmp). `> 39` fixes it (tested).

## Notes (measured, no change asked)

- **Localhost only.** The socket is bound to 127.0.0.1 (`/proc/net/tcp`);
  a connection to the machine's other address is refused.
- **Token and paths.** Ten ways to miss the token (none, as a query, without
  the slash, upper case, 63 characters, one more, absolute-form URI, the
  events and call endpoints without it) all give 404 and nothing reaches the
  editor. Thirty traversal names (`..`, percent-encoded, backslashes, NUL,
  doubled slashes, 5,000-character names) are all refused.
- **Cross-origin and DNS rebinding.** There is no check of `Host` or
  `Origin`: with the token, a request with `Host: evil.example` and
  `Origin: http://evil.example` is served and its call reaches the editor
  (`probe.py origin`). Without the token nothing is, so the token is the
  whole defence, and a rebinding page does not have it. It does not leak by
  Referer in Chromium (origin only, 2 runs); a browser with an older default
  policy would send the whole address to plain-http sites, which
  `<meta name="referrer" content="no-referrer">` in index.html rules out in
  one line. The token is in the browser's history while the editor runs.
- **An answer can be lost when a stream breaks.** An answer already written
  to a stream that then drops unread is not sent again when the page reopens
  it (`probe.py lost`). `Infoview.tla`'s `Break` counts such an answer as
  received, so `Answered` is proved for a stream that loses nothing. On
  loopback the window is the time between the browser dropping the
  connection and the child's next `poll`.
- **Lean dies.** A waiting call is answered with an error, later calls too,
  a keep-alive tick with no server does nothing (`r43_edge leandie`). The
  page is not told the server stopped (VS Code sends `serverStopped`); it
  shows the last state until a server answers `initialize` again.
- **The child dies.** `\w` starts a new one and its page gets the hello
  (`r43_edge kill`). Killed by a signal, the child leaves its 0600 file
  behind (`probe.py exit`); on the editor's EOF it deletes it.
- **The editor's loop.** A stream that is never read costs the editor
  nothing: 200,000 cursor moves at 4.0 us each, worst 706 us (sanitizer
  build); the child's memory grows instead, without bound while the
  connection stays up (138 MB RSS after them, sanitizer build). A 60 MB call
  from the page holds the loop 519 ms, an 8 MB one 62 ms (sanitizer build):
  another reason for a smaller `BODY_MAX`.
- **Diagnostics are re-sent whole per increment.** 1,000 incremental
  publications of one 300-byte diagnostic to one page: 135 to 179 ms in all,
  the slowest 349 to 641 us (5 runs, gcc -O2, `bench_tap.sh`); 5,000: 3.9 s
  in all, the slowest 5.0 ms (1 run); three pages cost three times one.
  vscode-lean4 joins them the same way.
- **A page id of "-"** is legal for `page_of` and makes the call line
  `- {...}`, which the editor reads as "forget". It needs the token and only
  loses that page's call.
- **Linux only.** `serve.c` is POSIX; there is no Windows child, and the PR
  does not claim one. DESIGN.md's phase 3 gate does not say which system.
- **New approaches table.** DESIGN.md already has the infoview as a child
  process on a pipe ("Everything else is a child process on a pipe: ... the
  Lean infoview webview"), so I see no new mechanism to list. `scan.c` is a
  second JSON reader beside `src/lsp/json.c`; whether one can serve both is
  a question for thread 0's next header round.
- `bridge_update` allocates and frees a string on every command in a Lean
  buffer; comparing in a fixed buffer would not.
