## Findings to fix before merge

### 1. CI is red: `test_file_save` needs root

Run 44118240619 on this head fails at `tests/test_file_save.c:300`: `chown(path, 0, 0)` is refused, because the runner is not root. The author's machine and mine are root containers, so the check passes there. The fallback test for a read-only directory and a foreign owner has to run in CI too, without being weakened: the read-only directory half needs no second user (the owner of a 0555 directory cannot create in it either), and the foreign-owner half can run under `sudo` in the workflow or in a user namespace (`unshare -Ur`, where the runner allows it). A silent skip when not root would leave the two plants "read-only directory refused" and "foreign owner lost" uncaught in CI.

### 2. After one failed journal append, later appends go on: replay gives a wrong text, or the journal is refused for ever

`append()` cuts a failed record back and returns -1, the core says E297, and the next change is appended as if nothing was missing. The journal then has a hole. **measured** (`gap.c`, `gap2.c`, 1 run each, disk full simulated by a file-size limit that a 100-byte paste exceeds and a 3-byte edit does not):

```
paste journalled: -1, later edit journalled: 0
buffer at the crash: "XXendXXXX...(95 X)0123456789"
recovered: "01end789"
```

and with the later edit beyond the old text's end, replay returns -1 ("only a bug could write"): `journal_open` fails at every later open with E303, the journal is never removed, and the file has no crash journal until the state file is deleted by hand. A full disk is when this matters. Smallest fix I see: on a failed `journal_edit`, mark the journal as having no base (`based = 0`, as `journal_saved` does), so the next change writes a fresh base or fails again; and let a base whose records do not apply be dropped with a message instead of blocking the journal for ever. Add the plant.

### 3. A power loss soon after `:w` gives a false recovery that refuses to save

`journal_saved()` truncates without a sync, with the comment "should a crash bring the old journal back, it recovers exactly the text just saved, which the core sees equals the file". The core does not see that: `recover()` also requires the journal's FileId to equal the file's, and the journal's is the one from before the save. **measured** (`drive.py powerloss_after_save`, 1 run; the journal's bytes from just before `:w` put back after kill -9):

```
after :w  | "f.txt" 3L, 14B written
reopen    | "f.txt" recovered from the crash journal; the file changed since (:w! overwrites it)
:q        | E37: No write since last change (add ! to override)
:w        | E13: "f.txt" changed on disk since it was read (add ! to override)
```

The buffer equals the file byte for byte. Dropping `same_id` from the test in `recover()` (equal bytes are nothing to recover, whoever wrote them) makes the comment true. `test_file_core`'s "modified exactly when it would save something else" passes today only because its crash never happens after a save with the old journal back; add that case and its plant.

### 4. A file opened through a symlink whose target does not exist yet cannot be saved

**measured** (`drive.py dangling`, 1 run): `:w` and `:w!` both answer E13 and nothing is written. `realpath` fails, the save goes to the link's own name, and RENAME_NOREPLACE finds the link there. **measured** (1 run): `nvim --headless -u NONE -n link +'call setline(1,"hello")' +w +q` creates the target and leaves the link. This is inherited from `ref/file.c` (same code on main), but the file is package 11's now and its comment says "write through a symlink to its target, as Neovim does". Related: with `force`, EEXIST from RENAME_NOREPLACE is reported as SAVE_CHANGED, so `:w!` is told to add `!`.

### 5. An in-place save needs a backup name, so a hard-linked file with a long path cannot be saved, even with `:w!`

**measured** (`drive.py longname`, 1 run, path of 328 bytes): `state_open("backup", ...)` fails with ENAMETOOLONG and both `:w` and `:w!` answer E212. The same holds when the state directory is unwritable or full. Neovim says E510 "Can't make backup file (add ! to override)" and `:w!` writes. For the journal the PR records the name limit as a hypothesis about Davy's paths; for saving, the cost of being wrong is a buffer that cannot be written, so `force` should go on without the backup (or the name should be shortened by a hash).

## Smaller, same PR or a recorded follow-up

### 6. The in-place backup's name is not durable

**measured** (strace of one in-place save, 1 run): `mkdir .../homeros/backup`, `openat(backup, O_CREAT|O_TRUNC)`, copy, `fsync(backup)`, then the file is overwritten. The backup's directory is never fsynced, while the swap path fsyncs its directory and `journal_sync` fsyncs the journal's "or a power loss can lose the whole file". ext4 usually commits the new name with the file's fsync; the code elsewhere does not rely on that. The order test logs the backup's fsync, not its directory's.

### 7. kill -9 between a change's record and the record of its new state loses the change

The UndoHook journals a change with the state from before it; `jdone` appends the new state as a second record. **measured** (`drive.py firstchar` with `kill.so`, SIGKILL before the 5th writev, 1 run): an empty file, `i`, `h` typed, journal holds base and the edit (128 bytes); the reopen shows `"f.txt" 1L, 0B`, no recovery, because the recovered state still says CORE_EMPTY and the text is taken as equal to the empty file. Only a kill between two writes of one command hits it (a power loss cannot, the sync is never between them), so it is rare; but the PR's claim "every reopen recovered the last edit that returned (or the one being written)" does not hold at the core level. One record per change that carries the state after it would close it.

### 8. `make test` can delete the real state directory

`@rm -rf $(XDG_STATE_HOME)` uses the variable, and a command-line value or `make -e` beats the Makefile's `:=`. **measured** (dry run, 2 forms): `make -n test XDG_STATE_HOME=/home/somebody/.local/state` and `XDG_STATE_HOME=... make -n -e test` both print `rm -rf /home/somebody/.local/state`, which is where Neovim keeps shada, undo and swap files. Write the path out: `rm -rf build/state`.

### 9. An outside change between `file_load` and `file_watch` gives no W11

**measured** (`drive.py lateWatch` with `late.so`, which rewrites the file inside `inotify_add_watch`, 1 run): the first edit shows no warning; `:w` is still refused with E13, so nothing is lost. One `file_watch_read` right after the watch is added (a stat) closes it.

## Notes

- **First edit after an open or a save writes the whole buffer inside the command.** **measured** (`base.c`, 5 runs per size, while `make check` was running on the same 4 cores, so read them as upper bounds): 1 MiB 1.8 to 2.1 ms (median 1.8) plus 1.3 to 2.2 ms for the sync a second later; 10 MiB 17.8 to 21.9 ms (median 18.8) plus about 12 ms; 100 MiB 209 to 265 ms (median 212) plus about 100 ms. DESIGN.md's gate is a frame ready under 2 ms p99. This is the design the PR chose (the base is the whole buffer, as Vim's swap file) and it is right for recovery, but the cost is not in the PR's "Costs found" list. Record it there, and measure it on Davy's largest file before phase 0's latency gate; Vim writes its swap blocks after 200 characters or 4 s, outside the keystroke.
- **Journal location.** The move from "next to the file" to `$XDG_STATE_HOME/homeros/journal/` is recorded in `include/file.h`, `src/file/state.h` and the PR text, with the reason (read-only directories and git trees get no stray files; it is Neovim's place). DESIGN.md's "Crash recovery" row still says "next to the file", and its "Backed by" still says "hypothesis: design only". `design/` is not this package's to edit, so the row needs a change through thread 0 once this merges, and Davy should be told (the coordinator has it on its list).
- Windows is pending, as the package's acceptance ("on Linux and Windows") and the PR both say; this PR cannot close package 11.
- The limits the PR names (no xattrs or ACLs on the swap path, leftover temp files after a crash mid-save, in-place backup not offered at the next open) are stated as hypotheses and are fine as follow-ups.
