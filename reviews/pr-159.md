## What the change must do

Two of PR 133's plants in `tests/plants/sql.txt` were caught only when a live
SQL Server answered in a certain order. The new `cancel_tokens()` feeds
`tds_parse` the reply to our own cancel with no server, so both are caught
whatever the server's timing.

## Does the new case exercise the code the plants break?

Read against `src/sql/tds.c` (token(), the DONE and ERROR cases):

- Plant "firstdone" drops `st & 0x20` from the rule that ends a cancel. The
  case gives a final DONE (status 0) while `state == TDS_CANCEL` and requires
  the state to stay TDS_CANCEL. That is the plant's behaviour, not its text:
  any rule that ends a cancel on a DONE without the attention bit fails here.
- Plant "3980" changes the number of the error hidden while `quiet`. The case
  gives a well-formed ERROR token (number 3980, state 1, class 16, empty text,
  server and procedure, line 1: 14 bytes, as the length says) and then the
  DONE with the attention bit, and requires TDS_READY with nothing rendered.
  The clean run passing shows the token is read as 3980 (otherwise it would be
  rendered); the state and `quiet` are the ones `tds_cancel` sets.

## Finding (measured): the new case fails on a clean tree under load

`close_notify()` alone, clean tree, several at a time on 4 cores: 1 of 1,200
runs failed (8 at a time) and 4 of 4,800 (12 at a time), always at
`CHECK(!net_read(&c, &in) && in.n == 6 ...)` with `net_read` returning 0 and
`in.n == 0`. Idle: 0 of 500. An instrumented copy showed, at each of the 4
failures, 255 bytes at the read (one session ticket) and 307 more arriving
within the next 300 ms (the second ticket, the reason, the close_notify).

Hypothesis that fits those counts: Nagle on the server's socket holds
everything after the first ticket until the client acknowledges it; the
delayed ACK timer does that after about 40 ms; the test waits a fixed 50 ms.
So the case that removes a timing-dependent plant is itself timing-dependent
and can turn a train's test job red.

Suggested change (`reviews/pr-159-repro/close-notify-cork.patch`, built by
`fix.py`): no session tickets, TCP_CORK on the server's socket around
`SSL_write` and `SSL_shutdown` so both records leave as one segment, and the
`nanosleep` removed. Measured with it: clean fails 0 of 4,800 under the same
load (12 at a time); the plant is caught 300 of 300.

## The rest (measured at 5ef8f52b)
