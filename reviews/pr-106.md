## Findings

### 1. MUST: the yank flash is drawn over 'hlsearch' matches; Neovim draws the matches over the flash

`"ab ab ab ab"`, `/ab`, `gg0ly3l` (flash over columns 1 to 3, the cursor on column 1):

    Neovim  C C I S S . S S . S S     (flash_search.lua, screenattr, 3 runs; prio.lua agrees)
    core    C I I I S . S S . S S     (flash_search.c, 3 runs)

In Neovim the flash is an extmark and Search and CurSearch are `win_line()`'s search_attr,
which wins over decorations; only the flash's cells outside a match show IncSearch. The PR's
body has this as a hypothesis ("Visual and the yank flash win over Search"); for the flash it
is wrong. It shows in ordinary use: `*` on a word, then `yiw`, flashes in the core and does
not in Neovim. `ks.inc` must keep winning over Search (measured above), so the two areas need
different orders. Please fix and add a case with both a search and a yank (no test has the
two together: the yank recorder never searches, the search recorder never yanks).

### 2. SHOULD: an empty line's end-of-line cell is never CurSearch in Neovim

`"\nx\n"`, `/\n`, cursor on 0,0: Neovim `S`, core `C`. Also `"x\n\ny\n"` with the cursor on
the empty line, and the empty middle line of `"ab\n\ncd\n"` under `/b\n\nc` with the cursor
inside the match (`one.py`, 1 run each; `wide1.txt` cases 290, 355, 459, 508, 576, 590). After
text the cell does follow the match (`"ab\ncd\n"`, `/b\n`, cursor on `b`: `.CC` in both). In
`win_line()` the empty line's cell comes from `get_search_match_hl()`, which only knows
`shl->attr`. One condition in the core; the recorder should gain `\n` on its own.

### 3. SHOULD: a match over several lines is CurSearch on all its lines when the cursor is anywhere in it

`"ab\ncd\n"`, `/b\nc`, cursor on 1,0: Neovim `.CC` / `C`, core `.SS` / `C`; cursor on 0,1:
Neovim the same, core `.CC` / `S`. `"ab\ncd\nef\n"`, `/b\_.*e`: the same on three lines
(`one.py`; `wide1.txt` cases 331, 370, 379, 413, 417, 464, 573). `search()` compares the
cursor with this line's bytes only, and `keys_hl` gives it nothing else. The fix needs
`keys_hl` to say that the match holds `w`'s cursor (the keys know its start and end), which
is a header change through thread 0 and a keys change; it would also let `search()` go. If
that does not fit this PR, say so in `keys.h`'s contract or the test's header as a known
difference and leave it to the next round; do not leave "CurSearch for the match at the
cursor" claimed as matching Neovim.

In all, `search_wide.py` (the PR's recorder with 25 wider patterns: empty matches, classes,
`\_.`, `\n` runs, `\zs`, `\ze`, `\%^`, `\%$`): 600 cases, 572 match, 28 differ, every one of
them finding 2 or 3 (CurSearch against Search; no cell drawn or missing). **measured** (1 run).
So which cells are matches agrees with Neovim on all 1,400 fresh cases.
