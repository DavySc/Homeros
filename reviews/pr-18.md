## Findings

### 1. `git_key` runs before the keys package and is not told to respect a half-typed command (does not block; cheap now)

`main.c` gives every key to `tools_key`, then `git_key`, then `keys_feed`. `tools.h` says of `tools_oil_key` that keys call it "with nothing pending"; `git.h` says nothing of the kind, and `git_key` runs before keys can say. `pending.py` builds the editor with a stand-in `git.c` whose `git_key` takes `x` (magit's discard) and types `3 x dd` on 9 lines: 6 lines are left, so the count meant for `x` landed on `dd` (**measured**, 3 runs; with `ref/git.c` the same keys leave 8). The same holds for an operator, a register or `f`'s character.

af2a18a adds `KeyState.pending` for exactly this state. Asked for: `git.h` says `git_key` takes a key only when `e->ks.pending` is 0 (or, as with oil, keys call it), and `ref/keys.c` keeps `pending` up to date, which it does not yet (`grep -n 'ks.pending' ref/ tests/` is empty). Related, for packages 5 and 17 to settle: keys that `tools_key` or `git_key` take never reach the keys package, so a macro or `.` cannot record them, and replayed keys never reach git.

### 2. Two flags for "something shown changed" (does not block; cheap now)

`core.h` gains `Editor.changed` ("a package changed what is shown between keys: main.c redraws, clears it") and `lsp.h` declares `extern int lsp_dirty` ("set when something shown changed; the main loop draws again and clears it"). One job, two mechanisms, and `main.c` reads only the first. One of them should go before packages 13, 15 and 17 code against both.

### 3. Delete still does nothing in the editor (does not block; needs a follow-up)

The PR's first item is the Delete key Davy missed. `KEY_DEL` is in `keys.h` and `ref/keys.c` acts on it, but nothing sends it: `grep -rn KEY_DEL src/` is empty on the merged tree, in `src/tty` and in `src/win`. `delkey.py` opens a file holding `abc` in the built editor through a terminal, presses Delete (`ESC [ 3 ~`) and `:wq`: the file is still `abc` (**measured**, 3 runs; the same script with `x` gives `bc`). Packages 6 and 9 have to map the key; until they do the trial's complaint stands.

### 4. The key fuzzer cannot press Delete (does not block)

`tests/fuzz_keys.c` checks that no edit splits a character, from a fixed table of keys, and `KEY_DEL` is not in it. Planted (`plant-del.txt`): insert-mode Delete removing one byte too few of a multi-byte character. `make fuzz FUZZERS=keys FUZZ_SECONDS=60` passes (215,754 runs), `make test`'s recorded traces pass, and only live `make conform` sees it (28 of 2,000 differ) (**measured**, 1 run each, at d89cc3b). One more entry in the fuzzer's table closes it.

### 5. The new main-loop lines have no test (does not block)

`if (e.changed) { e.changed = 0; dirty = 1; }`, the key order `tools_key`, `git_key`, `keys_feed`, and `tools_draw` after `core_draw` are in `src/main.c` with nothing that sets `changed` or takes a key, so no check can fail on them yet. The Render plants were kept in step with the edit, which is right. When package 15 or 17 lands, its tests should include one that fails without each of these lines, or thread 0 adds a stand-in module to `tests/` now.

## For Davy: three statements of the design change

None is wrong as far as checked, but they are his rules, changed by agents:

- **"No allocation in the redraw path after start-up" becomes "after first use (buffers grow to the largest frame, then stay)"**, in CLAUDE.md and DESIGN.md. This relaxes a rule rather than records a fact.
- Unicode 18 instead of 16, to match the Neovim the conformance tests run; and the step back follows Helix where Neovim's own stops inside a cluster (checked above).
- The crash journal goes to Neovim's state directory instead of next to the file.

## Notes

- The header says keys call `core_setpcmark` before G and gg; `ref/keys.c` does not. The thin editor has no jump keys, so nothing shows it.
- `core_mark_join` now doubles as "this step is a join" for undo's cursor, and `ref/keys.c` works around its own core ignoring it (the rewrite of the next line). Fine while the reference core lives; worth deleting with it.
- `lsp.h` counts an overlong or surrogate sequence as one character, as `uni_len` does, while its prose says an invalid byte is U+FFFD. What goes to the server for such bytes has to agree with the count; package 13 should test a file with them.
