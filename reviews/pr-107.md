## Findings

### 1. `fold_update` on a buffer with no lines asks the foldexpr for line `(size_t)-1` (reproduced)

`reviews/pr-107-repro/empty.c`: `fold_update(f, 0, 0, 0)`, as the first
update or after every line was deleted, calls `expr(ctx, 18446744073709551615, ...)`.
`update()` sets `top = n = 0`, `l.lnum = 0`, and `level()` passes `lnum - 1`.
Neovim never has 0 lines, but the core does (`core.h`: `CORE_EMPTY`, "the
buffer has no lines"; `text_lines()` 0), and `fold.h` does not say n is at
least 1. The fuzzer keeps n at 1 or more, so it cannot see this, though its
foldexpr would abort on it. Asked: either `fold_update` returns with no folds
when n is 0 (one line, and let the fuzzer reach n 0), or `fold.h` says the
caller passes 1 for the empty buffer (thread 0). **measured**, 1 run.

### 2. 14 lines of `fold.c` are not needed (Davy's rule: the shorter one wins)

`reviews/pr-107-repro/shorter.diff` removes them (536 to 522 lines):

- `manual()`'s `if (!opening && recurse)` branch cannot run: `fold_cmd` calls
  `manual` with (opening, 0), (1, 1) and (1, 0) only, since `fold.h` has no
  zC. gcov: never run, also not by 2.46M steps.
- `Fold.manual` (`w_fold_manual`) only saves `fold_cmd` a loop over the
  top-level folds: when it is 0 every top-level fold is `FD_LEVEL` already
  (a new top-level fold takes `FD_LEVEL` or its neighbour's flag, and anything
  else that sets a flag sets `manual`), so resetting them always gives the
  same result. The field, its five writes and the `fold_dup` copy go.
- `manual()`'s `use_level`: the fold found next is one of `fp->nested`, all
  just set to `FD_LEVEL`, so `fp->flags == FD_LEVEL` alone decides.
- `recurse()`'s `if (!fp) return bot;` is Neovim's `got_int` exit, which this
  port does not have; and `int i` with `fp = a->d + i` after the nested call
  re-reads a pointer the call cannot move (it only touches `fp->nested`).

Evidence that the shorter file behaves the same: the 2,460,000 Neovim steps
match with ASan+UBSan; `tests/fuzz_fold.c` on it, 251,767 runs in 91 s, no
failure; `diff_fuzz.c`, which drives the PR's file and the shorter one with
the same edits, commands and splits and compares every answer, 217,128 runs
in 181 s, no difference (and it fails within 60 s on a planted difference:
the reset loop starting at fold 1). **measured**. The cost is that these
lines no longer mirror Neovim's; the author may keep one with a reason, but
the unreachable branch at least should go.

### 3. The committed trace is too small to guard `merge` and some of `recurse`

Deleting any one of these lines leaves the committed replay green (seed 1,
300 scenarios; `delete-lines.sh` deletes each line in turn): 254 and 255
(joining touching folds), 262, 302, 319 (the `merge` of a following fold).
gcov agrees: seed 1 never runs lines 178 to 183 or 254 to 255. More scenarios
do notice them (**measured**, on my 60,000): 262 and 319 within 1,500
scenarios, 302 within 3,000, 255 and 181 within 6,000, 254 only between
15,000 and 60,000. So the claim "seeds 2 to 115 match" covers these lines,
but what the repo keeps running does not. Asked: make the kept check reach
them, for example a live run of `tests/test_fold.lua` with a few thousand
scenarios beside `make conform` (recording 300 takes 0.5 s here; the
Makefile is thread 0's), or recorded scenarios chosen to hit them, and a
plant on line 254 or 319 to show it.

## Notes (no change asked in this PR)

4. **"The first call does every line" has no test.** Deleting line 330 (the
   `invalid` handling) survives the replay, the fuzzer's shape and 2.46M
   steps, because every first call in the tests already passes the whole
   buffer. Either test it (a first `fold_update(f, 3, 4, n)`) or drop
   `invalid` and let `fold.h` say the first call passes every line.
5. **Out of memory aborts.** `grow()` calls `abort()`; no other file under
   `src/` does (grep: 0), the rest return -1 (`core.h`). The PR says so, and
   `fold_adjust`/`fold_update` return void in `fold.h`, so this is thread 0's
   to accept or change. "The crash journal keeps the text" is a
   **hypothesis**: I did not test an abort against the journal.
6. **Neovim is not deterministic on bigger buffers.** With `long.diff`, 2 of
   1,200 scenarios differ. `history-dependent.steps`: the same steps
   re-recorded in a fresh nvim (`replay.lua`) give a different answer, which
   the module matches. `heap-dependent.steps`: nvim's answer changes with
   glibc's `MALLOC_PERTURB_` (unset, 1, 170 give one recording; 85 and 255
   another, which the module matches). This fits the slot read past the
   nested array that the PR describes: past the allocation Neovim reads the
   heap, the module reads zero. So a live fold check must keep to small
   buffers (none seen in 2.46M steps at up to 25 lines) or it will flake.
   **measured**, each run once per setting.
7. **The declared 'foldminlines' difference, measured.** With edits and
   'foldminlines' 1 (what the editor will run), 98 of 1,500 scenarios differ
   from Neovim at their first difference: 58 where Neovim shows a one-line
   fold closed, 40 where Neovim shows a longer fold open; fold levels never
   differ. Both are Neovim's stale `fd_small`, and the module's answer is
   what the option documents. I agree with keeping the module's behaviour.
8. **`fold_adjust(f, l1, (size_t)-1, FOLD_DEL, -k, 0)`** lowers the kept line
   count by 1, not k (line 398 adds `amount`, which is -1). Neovim never
   deletes with line2 `MAXLNUM`, and I could not make it show in
   `fold_closed`; `fold.h` allows the call, so one of the two should say.
   **hypothesis** that it is harmless.
9. `FOLD_DEL` is -1, so a range moving up one line cannot be passed. No
   caller needs it now (Neovim's `:move` uses `foldMoveRange`, not ported);
   `fold.h` will need a move call when `:m` comes.
10. `fold.c`'s `grow` is the fifth private `grow` under `src/` (git, org,
    sqlfmt, str). Since new slots only need to be zero, its growth law no
    longer has to be `ga_grow`'s; one for the duplicate-mechanism list.
11. Owed by the wiring PRs (packages 4 and 5): a key-level check against
    Neovim (dd, p, J, u, Insert-mode joins with folds), since this PR tests
    `nvim_buf_set_lines`, o, O and A<CR> only.
