**Verdict: changes requested.** Findings 1 to 3 are bugs a user meets on the first day; 4 and 5 are evidence the rules ask for; 6 is a copy.

## Findings

### 1. On the start screen the panel is drawn under the dashboard (measured, 2 runs)

`homeros -t` with no file, Space, wait 0.5 s. Only the last row changes:

```
15|            Quit                                                    q
17|                           ⚡ Homeros loaded in 0.2ms
18|~
23| SPC                         <esc> close  <bs> back
```

After `g` the row reads `SPC » +git` and still no entry shows (`reviews/pr-129-repro/dash-spc.txt`). `src/main.c` calls `keys_draw` before `tools_draw`, and `dash_draw` paints every row but the last. The start screen is where Space is pressed first. No test draws the panel with the dashboard up.

### 2. In Org buffers `c<BS>` and `ci<BS>` no longer do what Vim does (measured, 2 runs each, against main 10d8b65 and nvim 0.12 `--clean`)

The new branch `if (nlead && (k == KEY_ESC || k == KEY_BS))` runs for any half-typed map, so also for `c`, `ci` of `cit`/`ciT`. File `one alpha beta gamma`, cursor moved with `ww`:

| buffer | keys | PR | main | nvim |
|---|---|---|---|---|
| .org | `c<BS>X<Esc>` | `one alphabeta gamma` | `one alphaXbeta gamma` | `one alphaXbeta gamma` |
| .org | `ci<BS>wX<Esc>` | `one alpha X gamma` | `one alpha betagamma` | `one alpha betagamma` |
| .txt | both | as nvim | as nvim | as nvim |

(`reviews/pr-129-repro/org-c-bs.txt`, made by `cmp.sh`.) In the first the change is swallowed (BS, Vim's motion, is eaten and Esc is fed); in the second `ci` falls back to a waiting `c`, so the next `w` becomes `cw`. The comment on `keys_draw` says "only after Space"; the key handling needs the same condition (`lead[0] == ' '`), and a test.

### 3. The panel covers the cursor's line (measured, 2 runs)

A 60-line file, `G`, Space, 24x80: the cursor is at screen row 21 and the panel takes rows 18 to 23, so the line being acted on (think of `SPC h s` on the last hunk) is hidden and the terminal's cursor sits on "D ➜ Dashboard" (`cursor-covered.txt`). which-key's default is `win.no_overlap = true` (config.lua:62), and `check_overlap` (view.lua:484) moves the panel to start below the cursor's row. The PR says it copies which-key's defaults; this one is not copied and not listed as a difference.

### 4. which-key was read, not run (CLAUDE.md, "Evidence")

The PR tags its which-key facts "measured by reading its source". Reading is a hypothesis by the rules ("Run things; do not conclude from reading code"). Reading the same source (v3.17.0) I find points where the PR differs. All **hypothesis**: I tried to run which-key under `nvim` in this container and the step was not permitted, so the author has to measure them.

- Order: the default `sort` is `{ "local", "order", "group", "alphanum", "mod" }` (config.lua:96), and `group` puts groups last (view.lua:33). The PR mixes groups and keys by letter (`, c D e f g h i p u`) and its comment calls that "which-key's order".
- Height: `box_height = math.max(math.ceil(#items / box_count), 2)` (view.lua:344) and the classic preset has `height = { min = 4 }`. `SPC i` here gives one row of entries (measured on the PR side, `spc-i.txt`).
- `<BS>` at the first level: `return state.node.parent or state.mode.tree.root` (state.lua:205), so it goes to the root's panel. Here it closes and feeds Esc, which also ends Visual mode.
- Row: `opts.row = Layout.dim(opts.row, vim.o.lines - opts.height - vim.o.cmdheight)` (view.lua:421). Whether the command line and the status line are covered should be seen on a screen, not derived.

Asked for: nvim with which-key and these maps in a pty, the screen recorded (as test_keys_map.c's header records its Neovim measurement), and each remaining difference either removed or listed in `src/keys/README` as chosen.

### 6. A second way to blank a rectangle

`keys_draw`'s loop `grid_put(g, r, c, (const unsigned char *)" ", 1, 1, ATTR_NONE)` over rows and columns is the body of `box_fill` (`src/tools/pick.c:672`). Under 50 tokens, so `make dupes` cannot see it; the same reasoning that moved `str()` to `grid_str()` applies.

### Notes (not blocking)

- A group that needs more rows than the screen has is cut without a sign (the author lists scrolling as a follow-up). At 4x10 and 6x30 the footer's parts run into each other (`SPC<esc>`); harmless.
- `keys_feed(e, KEY_ESC, 0)` on Esc in Normal mode is the PR's way to drop the count; which-key feeds nothing there (state.lua:200) because the trigger already took the count. Same visible result in the cases I ran (`2 SPC <Esc> x` deletes one character).

## What holds

- **Input latency (measured).** `j`/`k` through `keys_input`, 400,000 keys per repetition, 7 repetitions per run, 5 alternating runs per side, -O2, while other jobs ran: main medians 557, 569, 590, 598, 623 ns; PR medians 584, 585, 585, 597, 600 ns. The gap is inside the run-to-run spread: no measurable difference. `keys_draw` with the panel hidden: 1 ns (one test of `hint`). Shown, on a 60x240 grid: median 6.1 and 6.7 µs in two runs, against 40 µs for `core_draw` of the same grid. The timer is one `loop_timer` slot, cancelled on every exit I could reach.
- **Bounds (measured).** `keys_draw` on every grid from 1x1 to 40x200 (8,000 sizes) at the levels SPC, SPC g and SPC i under ASan and UBSan: clean (`test_wkprobe.c -DSIZES`).
- **The panel itself (measured, pty, 24x80).** Nothing within 150 ms of Space; the panel by 450 ms; `g` and `<BS>` follow at once; a second `<BS>` closes.
- **Owners.** `include/keys.h`, `include/grid.h`, `src/main.c` (thread 0): one declaration each and one call. `src/grid/grid.c` (6): `grid_str`, a one-line wrapper. `src/tools/dash.c` (15): `str()` deleted, four calls renamed, no other change. Finding 1's fix is in thread 0's `main.c`.
