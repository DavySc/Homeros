## Checked by reading (hypothesis until seen on Windows)

- Colour format: `BASE` and `TEXT` are `COLORREF`s made with `RGB()`, which
  is what `DWMWA_CAPTION_COLOR` and `DWMWA_TEXT_COLOR` take.  No conversion
  needed, none written.
- Attribute numbers in zig's headers: 20, 35, 36 (printed by the probe,
  measured), as Microsoft documents them.
- Older Windows: the return values are not read, so a DWM that does not
  know an attribute (35 and 36 before Windows 11 build 22000; 20 before
  Windows 10 2004) answers an error and the window opens as before.  The
  code path is the same as the probe's attribute 999, but Wine answers S_OK
  to everything, so the error path itself was not run: **hypothesis**, from
  the API's contract (it only returns an HRESULT).
- Set before `ShowWindow`, so no white bar flashes first.  **hypothesis**.
- The look (base bar, light text, light caption buttons, also when the
  window is inactive) is a **hypothesis** until Davy sees the trial build
  on Windows 11; the PR says so itself.

## One mechanism, minimal code, duplication

- No second way: the backend had no title bar code, and the colours are the
  backend's existing constants, not new literals.  `dwmapi.h` and
  `-ldwmapi` were already there (pacing).
- `make dupes` passes (in `make check`).
- Shorter?  Dropping the dark-mode call would save two lines, but it is the
  only one of the three Windows 10 understands, and on Windows 11 it is
  what the comment says makes the caption buttons light.  I could not run
  either claim, so I do not ask for the cut.  The alternative in the PR
  (a drawn title bar) is far more code.  Nothing to remove.
- The comment says why, and names the rejected alternative.
