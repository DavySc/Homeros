## Blocking

### 1. A heading in list item 7, 8 or 9 is not drawn

`draw_line` allows only list and quote markers before a heading, with `memchr(" \t>-+*.)0123456789", *s, 15)`. The string has 18 characters; 15 stops after `6`. So a heading after any list number that contains 7, 8 or 9 stays as typed. **measured**, against Neovim 0.12.6 with render-markdown v8.14.0:

```
$ reviews/pr-56-repro/build.sh $PWD mdcmp.c /tmp/mdcmp -O1 -g -fsanitize=address,undefined
$ /tmp/mdcmp reviews/pr-56-repro/recorded/cases4.txt
case 1 [ordered list 6 to 9] row 2 S:
  nvim [  2 7. 󰲡 seven                                    ]
  core [  2 7. # seven                                    ]
case 2 [ordered list 7 alone] row 0 S:
  nvim [  1 7. 󰲡 seven                                    ]
  core [  1 7. # seven                                    ]
case 3 [nested 8] row 1 S:
  nvim [  1   8.  󰲣 eight                                 ]
  core [  1   8. ## eight                                 ]
```

In the first case `6. # six` and `20. # twenty` are drawn, and `7.`, `8.`, `9.`, `19.` and `7)` are not. With 18 in place of 15 the three cases match Neovim and the PR's 300 screens still match (**measured**, 1 run each). The PR's recorder only ever writes `1. ` as a list marker, so its test cannot see this.

### 2. Most of the new drawing code has no check that can fail

CLAUDE.md: "A check you have never seen fail proves nothing." The 300 recorded screens are all one window, `nowrap`, one buffer, with `1. ` the only list number. `reviews/pr-56-repro/mut.sh` applies 16 changes to `draw.c` that the PR's 11 plants do not cover. **13 of 16 pass `test_core_markdown`** (**measured**, 1 run each, `mut-e56b19d.log`). Eight of those 13 change a screen that live Neovim shows otherwise (this review's recorded cases notice them):

| Change to draw.c | PR's test | Changes a screen Neovim shows |
|---|---|---|
| the bar only on a wrapped heading's first row (`rows = 1`) | passes | yes |
| the bar painted below the window's last row (`r + k < w->h` dropped) | passes | yes, into the window below |
| another buffer's window: its own cursor line raw | passes | yes (towards Neovim after `:e`, away from it after CTRL-W: finding C) |
| another buffer's window: rendered though scrolled sideways | passes | yes |
| another buffer's window: follows the current buffer's mode | passes | yes |
| visual mode rendered | passes | yes (the PR says this rule is untested) |
| the bar painted over the `<<<` of a top line shown from skipcol (`cover` dropped) | passes | yes |
| `skip` dropped from the bar's column | passes | yes (windows scrolled sideways or from skipcol) |
| no guard for a grid smaller than the window | passes | a heap overflow (below) |

So the wrap loop, the three rules for another buffer's window, the visual rule, the `cover` test and the grid guard are code that `make check` cannot see broken. The behaviour itself is right in every one of these (the review's cases match Neovim there); what is missing is the check.

`fuzz_core` cannot see it either. The PR's evidence says "fuzz_core and fuzz_keys ran 60 s each and found nothing", but `tests/fuzz_core.c` opens files named `f0`, `f1`, `f2`: no grammar, no heading face, so `draw_heading` never runs there. `draw_heading` writes `g->c[y * g->cols + x]` itself, behind its own bounds test. `reviews/pr-56-repro/fuzz_md.c` is fuzz_core on `*.md` files with headings:

- e56b19d: 133,152 runs in 181 s, nothing found; 77466f8 (same draw.c): 197,829 runs in 301 s, nothing found. **measured**.
- with `|| y >= g->rows || x >= g->cols` removed (in a copy of 77466f8): heap-buffer-overflow within 300 s (`crash-8bad044b…`). **measured**, 1 run. So this fuzzer can fail, and the guard is needed.

Asked for: wrap, a split on the same buffer, a second buffer and other list numbers in the recorder; a plant for each rule above; a fuzzer that draws headings (one of fuzz_core's files named `.md` would do; that file is thread 0's).

### 9. Simplicity and duplication

- **Duplicated bounds test.** `draw_heading` repeats `put_cell`'s test and its comment word for word ("a window can reach past a terminal that shrank (see grid_put)"; `y >= g->rows || x >= g->cols`). CLAUDE.md since 74440bd: "A review flags duplicated code as a finding." One helper that returns the window cell or NULL would serve both.
- **`v - m0 <= (size_t)n`** can be `<`: the cell after the marker is always a blank already (a space, a tab's first cell, or past the line's end), so the extra `grid_put` of a space changes nothing. With `<` all 300 PR screens and the 156 review screens of rounds 1 to 5, 7 and 8 are unchanged. **measured**.
- **A wrong name in a comment.** "nf-md-format_header_1 to 6: U+F0CA1 to U+F0CAB by twos". The code points are render-markdown's defaults (read from its `settings.lua`), but they are `nf-md-numeric_1_circle_outline` to `6`; `nf-md-format_header_1` is U+F026B (Nerd Fonts' `glyphnames.json`). **measured**.
- `test_core_markdown.c` and `.py` each carry the 12 colours that `ref/theme.c` also holds. That is the repo's habit for tests (`test_grid_diff.c` says "not computed from the shared table"), so no finding.
- Nothing else in `draw.c` looked removable. Of the 16 mutations, 11 change a screen and one overflows the grid. Reading on past a cut line (`break` dropped) changes only the time. Two showed nothing here and are needed by reading, not by a run (**hypothesis**): `&& syn` (without it `fc` is read uninitialised in a buffer with no grammar) and `k != 1 ||` (a marker character with a combining mark).

## Not blocking

**A. The icon in a window scrolled past the marker.** With one buffer in two windows and the other window scrolled sideways (or, with wrap, showing its top line from skipcol), Neovim paints the overlay at that window's first text column, over the text:

```
case 4 [side 2 + CTRL-L] row 1 S:
  nvim [  1 󰲡 One                    │  1 󰲡 ne                      ]
  core [  1 󰲡 One                    │  1  One                      ]
case 24 [skipcol other buffer + CTRL-L] row 0 S:
  nvim [2<<< 󰲣 word word word word wo│1                             ]
  core [2<<<rd word word word word wo│1                             ]
```

`mdcmp recorded/cases8.txt`. The core's picture is the saner one; copying Neovim here would hide text. List it under "Known differences".

**B. The last cell before a wide character that does not fit.** Neovim leaves the row's last cell without the heading background, with wrap (the `>` cell) and without (the cut cell); the core paints it:

```
case 1 [wide at edge + CTRL-L] row 1 B:
  nvim [....RRRRRRRRRRRRRRRRRRRRRRRRR.]
  core [....RRRRRRRRRRRRRRRRRRRRRRRRRR]
```

**C. "Another buffer keeps its look" depends on how it was left.** After `:vs` and `:e o.txt` Neovim keeps the old cursor line raw in the Markdown window; after CTRL-W to another buffer's window it renders every line. The core always does the second. The PR states the rule as measured, but its recorder has no second window.

```
case 18 [leave by :e in a split + CTRL-L] row 2 S:
  nvim [3   ### Three                │~                             ]
  core [3     󰲥 Three                │~                             ]
```

**D. `o<Esc>` as one burst.** Sent within render-markdown's 100 ms debounce, Neovim stays unrendered in normal mode (checked: `mode()` is `n` 3 s later, and still after CTRL-L) until the next cursor move. With the two keys 0.7 s apart it renders, as the core does. Not to be copied.

**E. A setext heading whose text starts with emphasised marker characters**, such as `*1* # b` over `===`: the core draws the `#` as a level-1 icon, Neovim does not. The comment in `draw_line` covers inline faces that are not marker characters; `*`, digits, `.`, `)` inside one get through. Contrived.
