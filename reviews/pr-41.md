## Findings

### 1. A child that keeps writing holds `loop_once` in its completion routines (blocking)

`on_read` re-arms the zero-byte read itself. When the child has more output waiting, that read completes at once, its routine is queued, and the alertable wait runs it before it returns: the comment's "one buffer's worth per wake" does not hold. `loop.c` does one read per stream per poll and then runs the watches.

measured, 5 runs (`run.sh flood`: a child writing 1 MB blocks without end, a key due 300 ms in, `loop_once(0)` in a loop for 2 s):

| | longest single `loop_once(0)` | most bytes handed on in one call | key due at 300 ms ran at |
|---|---|---|---|
| PR | median 1916 ms (890 to 2028) | 184 MB to 430 MB | median 1181 ms (334 to 1974) |
| with `fix.diff` | median 6 ms (2 to 8) | 65,536 in all 5 | 300 ms in all 5 |

So a chatty child (a build's output, `:!` on a large file, a language server sending a big reply) freezes keys, timers and drawing for as long as it writes, and Ctrl-C does not reach a command because none is running: the loop never comes back. On Windows itself this is a hypothesis, but the mechanism is the documented one (all queued routines run before an alertable wait returns), so I expect the same or worse.

Fix (in `fix.diff`): `on_read` reads once and does not re-arm; `loop_once` arms the read of every open stream that has none in flight, before its wait. A stream that ends there sets the timeout to 0, since its end was just reported. `proc_spawn` no longer starts the reads, which also removes finding 4.

### 2. A `proc_write` during the exit's drain completes on the slot's next child (blocking)

`report` cancels the I/O in flight, waits for the routines, then drains the pipes, and the drain calls the consumer. If the consumer answers with `proc_write` (a language client answering a server's request does exactly that) and something the child started still holds its stdin, `write_next` starts a write that stays pending. `report` then closes the handle, frees the slot, and the write's routine runs later against whatever child has the slot by then.

measured, 5 of 5 runs (`run.sh stale`): the next child in the slot is `cat`; it is sent "abc", and 500 ms later "def". With the PR, the second `proc_write` returns -1 and cat echoes 3 bytes: the first child's completion closed the second child's stdin. A trace of one run shows why: `on_write` runs twice for the slot, `outoff` becomes 6 of 3, and `write_next` asks `WriteFileEx` for 18446744073709551613 bytes (capped to 1 GB) from offset 6 of a 4,096-byte buffer. Wine refuses that call with error 1784 and the stdin is closed. Where 1 GB after the buffer happens to be readable, heap memory goes to the child instead.

Fix (in `fix.diff`): `proc_write` returns -1 while `c->reaping` is set. With it, 5 of 5 runs echo "abcdef". The same guard covers a write to this child from another child's routine while `report` sleeps in `SleepEx`.

### 3. The drain in `report` can be tested under Wine, and is not (should be added with the fix)

The PR says the drain cannot be exercised under Wine. It can: let a watch function sleep over the child's whole life, so the exit is seen while the output is still in the pipe.

measured (`run.sh drain`): 5 of 5 runs deliver "hello" and code 7 in the first `loop_once`, in the right order. With the drain line removed (`for (; left && ...) {}`), 2 of 2 runs deliver 0 bytes and the probe fails. So the drain is correct, and a test and a plant for it exist now; please move both into `tests/test_loop_win.c` and `tests/plants/loop.txt`, and drop the "not checked under Wine" sentence from the PR text. The flood and stale probes should become tests with plants too (the plants are the two halves of `fix.diff` reverted).

### 4. A stream's end can be reported inside `proc_spawn` (hypothesis; gone with fix 1)

`proc_spawn` calls `read_next`, which calls the consumer when `ReadFileEx` fails. On Windows a broken pipe fails that call at once, so a child that exits before the editor's thread runs again would get its callback before the caller has the id. Not reproduced under Wine: 3 of 3 runs with a 300 ms pause after `ResumeThread` and a child that exits at once report nothing early (Wine delivers the break through the routine). `loop.c` never calls back outside `loop_once`.

## Checked and found sound

- **The 64-handle limit** (read, and the PR's 32-children test): at most 16 watches and 32 process handles, 48, plus the message queue; `MsgWaitForMultipleObjectsEx` takes 63. Pipe I/O needs no handle.
- **Cancellation at the exit** (measured by every exit in the test, and by `drain`): `CancelIoEx` on each stream in flight, then `SleepEx` until every routine has run, so no handle is closed with I/O in flight on this path. Finding 2 is the one way around it.
- **Partial reads and broken pipes** (read, and the PR's `big`, `head1`, `noin` roles): `take` reads at most what `PeekNamedPipe` counts, so it cannot block; a broken pipe ends the stream from either the routine's error or `ReadFileEx`'s failure; a write to a closed stdin closes it and `proc_write` returns -1.
- **Handles** (read only, not measured: Wine's `GetProcessHandleCount` is a stub): every path of `proc_spawn` closes the child's ends and, on failure, ours and the job; `report` closes the pipes, the process and the job.
- **Window messages** (the PR's test, and the plant removing `MWMO_INPUTAVAILABLE` is caught): a message seen but left queued wakes the wait; `loop_waiting` and `loop_breakcheck` are not alertable, so no pipe routine runs inside a command (plant caught).
- **Timers** (the PR's test): rounded up, never early. An early return of the wait only costs one more pass.

## For the first run on Davy's laptop (hypotheses, not defects of this PR)

- The wait's timeout counts clock ticks (15.6 ms by default), so a `loop_timer` can fire up to one tick late. Frames do not depend on it (package 9 uses a high-resolution waitable timer); the Esc timeout does, harmlessly.
- While a window is dragged or resized, Windows runs its own message loop inside `DefWindowProc`, so `loop_once` does not run and pipes and timers wait until the drag ends.
- `CreateProcessW` looks in the editor's own directory and the current directory before PATH, which `posix_spawnp` does not; and it finds `.exe` only, so `npm` (a `.cmd`) needs its full name.
- The exit code of a killed child (143) follows what libuv reports to Neovim after `uv_process_kill`; I did not run Neovim on Windows to confirm it.
