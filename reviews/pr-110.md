## Verdict

**Changes requested at 9a69115.** The colours and folds themselves hold up: 0 of 1,920 cases differ from Neovim over three seeds, and every hand-made edge case I tried gives Neovim's answer. Six things need a change before this joins a train (findings 1 to 6); finding 7 is a cost that must be settled before the folds are wired into the editor, and the last section is three costs of SystemVerilog Davy should know about.

## Findings

1. **A plant in the PR does not apply, so `make planted` exits 1. Measured, 1 run.** `tests/plants/syntax.txt` line 61 ("injection patterns of languages we lack are dropped from the query") still replaces the line `if (!hl && (P->skip = (unsigned char)lacked(st, ns, Q->q))) continue;`, which this PR deletes with `lacked()`. The PR renamed its case (11 to 13) but kept it. `reviews/pr-110-repro/run-plants.sh` (planted.sh's loop) prints `BROKEN PLANT` for it, and planted.sh sets `rc=1` there, so the plant shard that holds it would be red on the train. Either delete the line (its mechanism is gone) or re-aim it at what replaced it (see finding 5c: no plant sees the replacement today).

2. **A `define body is plain here and coloured in Neovim with nvim-treesitter. Measured, 1 run each.** SystemVerilog's injections query injects `(macro_text)` as language "verilog". nvim-treesitter's `plugin/filetypes.lua` (the pinned version, line 49) registers `systemverilog = { 'verilog' }`; that line is the only reason a verilog buffer uses the systemverilog parser at all, which is what this PR copies for `.v`. With that registration Neovim parses the macro body as SystemVerilog (2 trees); without it (the oracle's `--clean` plus `build/syntax/src/nvim`, which has no `plugin/`) it does not, and neither does Homeros, so the test agrees with itself and not with Davy's Neovim:

   ```
   `define ADD(x) assign y = x + 8'hff;
   kkkkkkk.kkkp.p......................   nvim --clean (the oracle today), and Homeros (faces.c: #######.####.#......)
   kkkkkkk.kkkp.p.kkkkkk.v.o.v.o.nnnnnp   nvim with the registration (macro.lua FILE 1)
   ```

   Asked: `resolve()` reads "verilog" as systemverilog, and `tests/test_syntax.lua` makes the same registration, so the corpus (Verilator's tests are full of `define) checks it. The same alias then also colours a ```` ```verilog ```` fence in Markdown as Neovim does. That Davy's my-nvim loads nvim-treesitter's `plugin/` directory is a **hypothesis** (it is how the plugin is loaded from nixpkgs); if he says it does not, drop this and `.v` should then get no tree-sitter colours either.

3. **The fuzzer aborts on a correct answer. Measured, 1 run.** `tests/fuzz_syntax.c` aborts when `syntax_foldexpr` answers more than 20. For Markdown the answer is the count of `#`, as MarkdownFold() gives it: 21 `#` and a space answer 21 here and `>21` in Neovim (`cases/h21.md`, both sides in `folds-*.txt`). `reviews/pr-110-repro/fuzz-h22.bin` (32 bytes: Markdown, 21 `#`, `1. `, then an edit that deletes `1.` and adds a `#`) makes `fuzz_syntax` die with "deadly signal" at that abort. 30 seconds of fuzzing did not find it; a nightly or the 24 h gate can. The check should hold for the tree-sitter languages only (where 'foldnestmax' clamps), or go.

4. **Two rules in the fold code have no check. Measured: both plants pass `make test TESTS=syntax`; the code itself matches Neovim on my cases.**
   - 'foldnestmax': planting 21 for 20, and planting `(e > 0)` for `(e && v <= 20)`, both pass. `cases/deep.c` (24 nested blocks) gives `>1 … >20 20 20 …` on both sides today, so the code is right; it wants that case in test_syntax (a fixed case like 6 and 10) and the two plants.
   - Markdown, "a setext underline needs text above it": removing `a < z &&` passes. `cases/set.md` (an empty line above `===`) gives Neovim's `0 0` today; add the line to case 10 with the plant.

5. **Lines that can go (Davy's rule: the shorter one wins). Measured: each removal passes `make test TESTS=syntax`, and all five together give byte-identical answers on my 17 `.v` cases and 21 fold cases (`probe-short` against `probe`).**
   - a. `md_fold`: `h < z &&`, and `b < y &&` twice. `z` and `y` are the offsets of the two lines' newlines (`l + 1 < text_lines(t)` is tested before `y` is used), and a newline is none of ' ', '=' and '-', so the loops and tests stop there on their own.
   - b. `verilog()`: `- (l < n)`. Every pattern that looks at the line's end is `%s*$`, and `%s` takes the newline; the others never reach it.
   - c. `fold_tree`: `if (!passes(src, &m, &Q->pat[m.pattern_index])) continue;`. No folds query compiled in has a predicate (Markdown's has the `#trim!` directive only, and a Markdown root never runs the query). The package's own rule is that an unreached query feature is deleted and comes back with the language that needs it and its test.
   - d. `syntax_foldexpr`: `while (syntax_update(s, s->t, NULL) == 2) ;` can be the one call. With `stop` NULL nothing returns 2: every `return 2` sits behind `stop()` or `s->stop && s->stop()`.
   - Also not caught, for the author to delete or test as they see fit: `&& er < (int64_t)s->nfold` (a fold cannot end past the last line while the text ends in a newline, which the core keeps); in `vim_words`, `len[j] == 0 ||` and `|| s[n - 1] != '$'`; and `P->skip |= (unsigned char)w;` itself: with it removed the one unknown form (Rust's re2c) is compared as a literal word, never matches, and nothing changes. So the PR's sentence "any other match? form skips its pattern" is true but unchecked, and finding 1's plant has nothing to aim at unless a case is added.

6. **The build prints an error. Measured.** `make` prints `sed: can't read build/syntax/src/queries/markdown_inline/folds.scm: No such file or directory`: build.mk runs the `inherits` sed before it tests that the file exists. Test first.

7. **The folds cost more than the reparse they follow, on every edit, and the contract puts that inside the key. Measured, 5 alternating runs of 60 edits each side, `foldcost.c` and `foldcost.lua`, a space typed at the start of the same random lines, on 4 cores that were also running `make check` and two plant jobs (so absolute figures are upper bounds; the sides alternate).** The PR's evidence has no timing for `syntax_foldexpr`.

   | file | here: reparse, median per run | here: `syntax_foldexpr` after it | Neovim: edit + reparse + fold levels (CPU) | Neovim: time the edit holds the editor |
   |---|---|---|---|---|
   | stack.c, 29 KB, 912 lines | 0.29 to 0.37 ms | 1.27 to 1.54 ms | 0.97 to 1.07 ms | 0.18 to 0.20 ms |
   | 489 KB of C, 14,700 lines (tree-sitter's lib, concatenated) | 2.2 to 2.9 ms | 22.6 to 25.1 ms | 4.3 to 5.1 ms | 0.25 to 0.26 ms |
   | t_math_synmul_mul.v as .sv, 330 KB, 3,005 lines | 39.9 to 44.8 ms | 43.7 to 50.2 ms | 62.8 to 65.5 ms | 0.14 to 0.15 ms |

   Why: `syntax_update` zeroes the whole fold table after every parse, and the next `syntax_foldexpr` runs the folds query over every tree from byte 0. Neovim's `_fold.lua` recomputes only the rows of the changed ranges (`on_changedtree`), and does it after an asynchronous parse, so the key returns in 0.2 ms with the old levels and the new ones arrive later. Here `syntax.h` says `syntax_foldexpr` "brings the parse up to date first" and is called from `fold_update` after a change: once that is wired, each Normal-mode edit pays the reparse without `stop` plus the fold pass before its frame, which on a 29 KB C file is already about the 2 ms frame gate (DESIGN.md, phase 0) and on the large C file is 5 times Neovim's total work.

   This PR adds no caller (PR 107 has none in `src/` either), so it changes no frame today, and I do not ask for the redesign in this PR. Asked here: put the measurement in the PR and in `syntax.h`'s comment, so the wiring is done knowing it. To settle with thread 0 and package 20 before `fold_update` calls it from the edit path: recompute only the changed rows as Neovim does (tree-sitter's changed ranges are already in hand after a parse), or let `syntax_foldexpr` answer from the last finished parse and have the loop call `fold_update` when `syntax_update` returns 1, which is Neovim's shape. Sent to the "Build code folding" thread.

## What was checked, by running it

- **Colours and folds against Neovim. Measured.** `make check`'s run (seed 1, 320 cases) and two more seeds here with `CASES=100` (`SEED=101`, `SEED=102`, 800 cases and about 1.5 MB each): 0 cases differ in colours, 0 in folds, 0 of 3,303 and 3,424 frames between an edit and its parse, 0 sliced parses without syntax errors.
- **Every capture name the two new highlights queries use is in the face table** (read from the queries: all are Neovim's standard ones; `@none`, `@spell`, `@nospell` colour nothing on both sides). The table is shared by the C side and the oracle, so a name outside it would have been invisible to the test; there is none.
- **Every `match?` in the compiled-in queries is one of the two forms `vim_words` reads** (9 in CMake's highlights), except Rust's re2c injection, whose language we lack. Neovim puts `\v` in front of a `match?` pattern, so `(a|b)` groups as the PR assumes.
- **`.v` detection, 17 more cases. Measured, 1 run.** Line 500 with and without its newline, line 501, a comment opened and closed on one line, a comment opened mid-line, CRLF, a NUL, a non-ASCII byte, tabs, `module m #(`, `(*` after `//`: all 17 verdicts equal Neovim's `vim.bo.filetype` (`v-cases/`, `probe.c`).
- **Folds, 21 hand-made files. Measured, 1 run, `probe.c` against `folds.lua`.** CMake (if/elseif/else, foreach, while, function, macro), GLSL, Lua, Rust (consecutive `use` lines), SystemVerilog (consecutive `include lines, which is the quantified capture; class, function, task, generate, begin/end, a multi-line `define), 24 nested C blocks, Markdown (ATX to level 21, setext with every near-miss, a fence): equal to Neovim. Three files differ and none is a defect: a text without a final newline (the core always keeps one), a CRLF file read raw (the file package strips CR as Neovim's dos format does), and Nix with Lua injected, below.
- **Folds of injected code depend on what has been drawn, as in Neovim. Measured.** With only the root parsed Neovim answers `>1 >2 2 2 2 2 2 2 >2 2 2 1` for `cases/inj.nix`, as Homeros does before the window is drawn; after `parse(true)` it sees the Lua inside (`>3 >4`). `vim.treesitter.foldexpr()` parses with no range, so it too only has the injections the highlighter has visited. Not a difference; said so nobody is surprised.
- **The two shared headers.** `include/fold.h` and the `syntax.h` hunk are byte for byte PR 107's (9c3408f); `git merge-tree` of the two heads is clean.
- **My plants, 22, `review-plants.txt`, log beside it: 9 caught, 13 not.** Caught: a one-line fold counted, a quantified `@fold` ended at its first node, `#` without a space, `.v`: the last partial line, a block comment that never ends, `(*` after a comment start; a `match?` suffix compared at the wrong length; the fold table leaked. Not caught: findings 4 and 5, and two that no check can see: `!started(s)` (only an allocation failure leaves it false after the update) and `line >= n` (the table has a spare slot, so `line == n` reads a zero).

## Costs of SystemVerilog, for Davy (not asked of this PR)

- **The binary grows from about 4.9 MB to 27.8 MB. Measured (`size`).** tree-sitter-systemverilog's `parser.o` is 22.9 MB of read-only tables (its `parser.c` is 65 MB); CMake's is 76 KB. It is the grammar nvim-treesitter uses, so matching Neovim means this grammar.
- **A process with any `.sv` open holds about 26 MB more. Measured, 1 run each, `foldcost` (the library set of the editor without a window):** max RSS 39.7 MB on a 31-byte `.sv`, 13.3 MB on a 29 KB `.c`.
- **The first `.sv` of a session freezes the editor for about half a second after its first frame. Measured, 3 runs, `qcompile.c`, loaded machine:** tree-sitter compiles the highlights query in 416 to 516 ms, the injections query in 32 to 40 ms and, new with this PR, the folds query in 59 to 78 ms; `syntax_update` does not ask `stop` meanwhile. The PR reports the first figure and Neovim's 480 ms for it; the other two add about 100 ms it does not mention. CMake's three take 18 ms together.
