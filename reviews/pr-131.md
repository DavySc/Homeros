Reviewer: separate Fable 5.2 thread, 2026-11-23. Head reviewed: 018ebaa (main 10d8b65 plus one commit; main had not moved, so the head's tree is the merge tree).
Repro files: `reviews/pr-131-repro/`. Tools: `tools.nix` (zig, Wine and the rest) and CI's apt line. 4 cores.

Contract: `include/file.h`'s `file_watch`, `file_unwatch`, `file_watch_read`; `core.h`'s `Buf.watch` and `core_watch`; `loop.h`'s `loop_watch`/`loop_unwatch`. The questions asked: the count per folder, several buffers in one folder, a folder opened again, the Linux backend (one mechanism), and what the Windows job in CI shows.

## Verdict

**Changes requested at 018ebaa: the code is right, the test is not yet.** I found no bug in `src/file/win.c`, `src/file/file.c` or `src/core/core.c`. But on real Windows the new test passes without the fix (finding 1), so the Windows job in CI shows less than the PR says, and two more planted bugs get through (findings 2 and 3). `reviews/pr-131-repro/test.diff` (17 lines in `tests/test_git_win.c`) closes findings 1, 2 and 4; with it every plant below is caught on real Windows and under Wine. With that diff, finding 3's check and plant, and finding 5's wording, I approve without another full pass.

## Findings

1. **On real Windows the test passes without the fix: three of the PR's four plants are not caught there** (blocking; **measured**, 1 run each, run 45212358251).

   | plant | Wine, PR's test | Windows, PR's test | Windows, with `test.diff` |
   |---|---|---|---|
   | core: `:bd` keeps its folder's watch | caught :192 | **NOT CAUGHT** | caught :201 |
   | core: a freed buffer keeps its folder's watch | caught :197 | **NOT CAUGHT** | caught :207 |
   | file: win: closes with its first buffer | caught :195 | caught :195 | caught :205 |
   | file: win: a folder's watch never closes | caught :192 | **NOT CAUGHT** | caught :201 |
   | review: a closed folder keeps its slot | **NOT CAUGHT** | **NOT CAUGHT** | caught :197 |
   | review: the last slot dropped, not the closed one | caught :197 | **NOT CAUGHT** | caught :197 |
   | review: a folder's second buffer is not counted | caught :195 | caught :195 | caught :205 |
   | review: core: a closed watch stays in the loop | caught :195 | caught :195 | caught :197 |

   The reason is in the probe: build 26100 removes a folder whose handle is open at once (POSIX delete), so the parent's `RemoveDirectory` succeeds whether or not Homeros closed the watch. The symptom the PR describes (error 145) is Wine's. What the open watch does block on real Windows is renaming or moving the parent folder (error 5, access denied), which is the thing a user meets in Explorer. So the fix is worth having on real Windows too, but the test has to ask for it: `test.diff` adds `MoveFileA(px, pz) && MoveFileA(pz, px)` before each removal, and then the rename catches on Windows what the removal catches under Wine. The last column was also run under Wine: 8 of 8 caught, and the head passes on both.
   **Hypothesis**, not measured: Windows 10 before version 1809, and file systems other than NTFS, behave as Wine does.

2. **A folder opened again after its last buffer went is not tested** (blocking, same diff). With `d[i] = d[--nd];` deleted, the closed folder keeps its slot and a file opened there again gets the closed handle: the PR's test passes on both systems. `test.diff` opens `a` again after `:bd`, changes it outside and waits for `changed`: the head passes, the plant fails at line 197 (Wine and Windows). The same step catches "the last slot dropped" on Windows.

3. **Linux: nothing checks that `file_unwatch` leaves the shared fd in the loop** (should be fixed here; it is the PR's own Linux line). With `file.c`'s `file_unwatch` returning 1, the core takes the one inotify fd out of the loop at the first `:bd` and no buffer sees an outside change after it. `make test TESTS="core_contract file_core"` and the pty scripts that target runs (`watch:`, `hang-up`, `start:`) all pass with that plant. `test_unwatch_linux.c` (open a and b, `:bd` a, change b outside, wait in `loop_once`) passes on the head and fails with the plant at its line 26. Its six lines of body fit in `test_core_contract.c` next to the shared-fd check, with the plant
   `file: file_unwatch says it closed inotify's fd~test TESTS=core_contract~~src/file/file.c~int file_unwatch(int fd) { (void)fd; return 0; }~int file_unwatch(int fd) { (void)fd; return 1; }`.
   The other Linux tests call `core_watch` by hand, so they cannot see the loop.

4. **One failed run makes every later run under Wine fail** (small, same diff). The new folders are named by the process id alone, and under a fresh Wine server that is 32 every time. After a run that fails inside item 4, the folders stay in the prefix's Temp and the clean head then fails at line 181 (`CreateDirectoryA`), until `build/win/prefix-git` is removed. Measured: a plant run, then the head: fails at 181; folders removed: passes. `planted.sh` and CI start from a fresh copy, so only a developer's second run is hit. `test.diff` names them after `top`, which carries the tick count as the test's other folders do.

5. **Wording** (small). `file.h` says an open handle "keeps other programs from removing or renaming the folder". Measured: the folder itself can be removed and renamed on both systems; it is the parent that cannot be renamed (Windows) or removed (Wine). The PR text and `tests/plants/core.txt`'s "so Windows cannot remove the folder" say the same about Windows, and the test's comment already says "under Wine". Suggested: "as an open one keeps the folder's parent from being renamed (and, under Wine, removed)".

6. **Least code, one mechanism**: nothing to cut. `file_unwatch` is 9 lines on Windows and one on Linux; `buf_unwatch` is the one place the core gives a watch back, called from the two places a buffer's text goes. A count per folder is the usual answer and I found no shorter one that keeps one handle per folder. `d[]` moving to file scope is needed. Side effect worth having: the loop's 16 watch slots on Windows and the 64-folder table no longer fill for the session.

Not asked for here, for thread 0's list: after `core_free` on Linux the inotify fd stays in the loop with the freed editor as its context until the next `buf_load` (as before this PR; **read, not run**). The editor has one `Editor` for the process, so only tests can meet it.
