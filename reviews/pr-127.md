## The questions asked

### 1. Is a ratio of two timings robust enough, or is a work count required?

The check: after one walk to line 99,999 of 100,000 (time d[0]), four lines are shown going up the text (time d[1]); `CHECK(d[1] < d[0])`. With checkpoints the four lines restart from a checkpoint at most 4,096 lines back. Without them each of the four walks from the top, so d[1] is about twice d[0].

`ratio.c` runs only that check, many times in one process (measured; d[1]/d[0]):

| | n | min | median | max | wrong side of 1 |
|---|---|---|---|---|---|
| head, idle | 300 | | 0.118 | 0.175 | 0 |
| head, beside 6 looping `test_org` | 600 | | | 0.174 | 0 |
| head, beside 8 spin loops | 600 | | | 0.210 | 0 |
| plant, idle | 300 | 1.32 | 2.00 | | 0 |
| plant, beside 6 looping `test_org` | 600 | 1.256 | | | 0 |
| plant, beside 8 spin loops | 600 | 1.092 | | | 0 |

- No false failure in 1,500 clean runs, and the clean side has a margin of 4.7 times at its worst. **A false red from this check is not a practical risk (measured).**
- No miss in 1,500 planted runs, but the worst planted run came within 9% of passing, on a machine with twice as many busy loops as cores. So a miss is possible in principle; I put it near 1 in 10,000 under heavy load (hypothesis, from the tail of 600 runs). `CHECK(2 * d[1] < d[0])` would give about 4 times on both sides (clean max 0.21 against 0.5, plant min 1.09 against 0.5) and costs nothing. Optional; follow-up 2.
- The runner's speed cancels: both times are the same kind of work on the same machine in the same few milliseconds. That is what the absolute bound lacked. Locally the plant is still caught first by the first frame gate (23 to 24 ms against 20), which is exactly the margin CI's runner removed.
- Train 23's CI run with this head leading is green on all 18 jobs (coordinator, 14:05 UTC), so the plant is now caught on the runner that missed it.

A work count would be exact, but it cannot be had from the test alone: `test_org` links `org.o`, the scan is static, and CI has no performance counters. It would need a counter in `src/org/org.c` and a line in `include/org.h` (thread 0), which is product code that exists only for a test, against "no line of code that isn't absolutely necessary". Given the measurements above I do not ask for it.

### 2. Do the retries hide a real flake or weaken the gate?

- **They do not weaken the gate against slow code (measured).** A gate passes if any of 3 fresh tries is under the bound, so it compares the best try. I built 19 timing plants one by one with a probe that prints every try (`mkprobe.py`), 5 runs each: every plant fails its gate on all tries. Best try over bound: plant 91 30 times, 117 9.5 times, 148 3.8 times, 118 2.5 times, 103 1.7 to 1.8 times, 133 1.5 times, 104 1.15 times (and ratio 1.96 to 2.03), the other twelve 5 to 400 times.
- **They do not cure the flake (measured).** Slowness on a busy machine lasts longer than three tries.
  - The head's `test_org` beside the `make check` build (load about 3): 27 of 100 runs failed, every one on an absolute bound, none on the ratio check.
  - Main's and the head's `test_org`, unchanged, in turn, beside the fuzzers and the plant run (load 2.2 to 3.2), 60 runs each: main failed 21, the head 18. No measurable difference in total. The parts differ: main failed only frame gates (21); the head failed frame gates 10 times (the retries halve that) and the long-line gate 8 times, which main never failed.
  - Idle, the head passed 35 of 35, but its worst gate's best try reached 0.97 to 0.99 of its bound in 4 of 30 runs.
- **Why the long-line gate now fails.** The PR puts every long-line unit under a definition `[fn:1] d`, which is the right text for item A. The unit `a[fn:1] ` now takes 69 to 92 ms of its 100 ms bound here (about 51 ms on main). Follow-up 1 covers it.

So the retries are harmless and help a little, and the flake under load remains as it is on main. CI runs `make test` alone on its runner, where the head is green.

## Follow-ups (package 16's next PR; none blocks this one)

1. **Replace the absolute CPU-time bounds by same-runner comparisons, as this PR did for the checkpoint plant.** They are flaky in both directions:
   - false red: 18 to 27 failures per 100 runs beside a build (above), and the long-line unit `a[fn:1] ` has 1.1 to 1.4 times of headroom idle;
   - false green: plants 133 (1.5 times over its bound) and 103 (1.7 to 1.8 times) have margins as thin as the one CI just missed (1.55 times). A runner twice as fast lets them through (hypothesis from the measured margins; CI caught both today).
   A pattern that works: time the gated work against a reference of known shape on the same text (a plain walk, or the same unit at half the length for the linear-time claims) and bound the ratio.
2. Optional: `CHECK(2 * d[1] < d[0])`, which balances the margins of the ratio check.
3. `cover()`: `z < r[0] ||` is unreachable as far as 40,000 texts show; drop it or add the text that needs it (CLAUDE.md: shorter wins).
4. The report's own numbers: the PR body's "1 run in 6 failed on a quiet machine" I did not see idle (0 of 35), only under load.
